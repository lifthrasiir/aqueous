# aqr-mp3 (`mp3r`)

A lossless MP3 recompressor: MPEG audio Layer III files (MPEG-1, MPEG-2 and MPEG-2.5,
including free format) are stored smaller and restored bit for bit, in the family of
packMP3. Speed comes first: the target is 100 MB/s of MP3 file single-threaded on an
Apple M4, both ways; compression ratio is pursued only where it does not cost that.

## Results

Apple M4, one thread, `mp3r bench -n 2` (best of two runs per file). FMA `fma_small`
directories 100–155, which the built-in tables were not trained on (they were trained
on 000–099):

| Set | Files | Input | Output / input | Compress | Decompress |
|---|---|---|---|---|---|
| FMA 100–155 | 3489 | 3.61 GB | **0.8521** | **104.9 MB/s** | **114.3 MB/s** |

Every file round-trips (`bench` also checks the coded path when the container falls back
to storing).

## Usage

```sh
cargo build --release

mp3r c [-t N] in.mp3 out.m3r         # compress
mp3r d [-t N] out.m3r back.mp3       # decompress
mp3r bench [-n ITERS] [-t N] [-v] FILE|DIR... # round trip check, ratio, throughput, per-stream sizes
mp3r info FILE|DIR...                # frames, junk, tail / raw / gap bits, symbol counts
mp3r fuzz [-n N] [-s SEED] [-t N] FILE|DIR... # mutated inputs (flips, cuts, deletions, insertions)
train [-a] OUT FILE|DIR...           # trains the built-in tables (every file with -a, else every second)
```

`-t N`: threads; `c` and `d` default to the available cores, `bench` and `fuzz` to 1 (`fuzz`
then also checks that the output equals the one-thread output). See [Threads](#7-threads).

```rust
let packed = aqr_mp3::compress(&mp3);              // never fails: stores what it cannot code
assert_eq!(aqr_mp3::decompress(&packed)?, mp3);    // checked against an xxh3 of the original
let packed = aqr_mp3::compress_threads(&mp3, 8);   // the same bytes for any number of threads
assert_eq!(aqr_mp3::decompress_threads(&packed, 8)?, mp3);
```

Any input is accepted. Whatever is not an MP3 frame is kept verbatim (zstd), and so is any
main data that cannot be reproduced.

## Design

### 1. Decomposition

- **Segmentation**: a run of frames starts where three compatible frames (same version and
  sample rate) follow each other, or the file ends; everything between runs is junk.
  An ID3v2 tag is skipped as a whole. Free format runs get their frame length from the
  distance to the next matching header and store it per run.
- **Reservoir**: the main data of all frames (after the side information) is concatenated
  into one buffer `R`. A frame's main data starts `main_data_begin` bytes before its
  payload and spans its `part2_3_length`s. A frame is *placed* when that span starts at or
  after the previous placed frame's end and ends within its own payload. Only placed frames
  are decoded; every other bit of `R` (stuffing, ancillary data, Xing / LAME tag frames,
  data of frames cut off at the start of a clip) is a gap stored verbatim.
- **Granules**: scalefactors, then big values and count1 quadruples. A quadruple is
  decoded only while it fits; what is left is the tail (stuffing inside part2_3_length).
  A granule that cannot be decoded (missing table, big values past the end, ...) is
  stored verbatim. Huffman decoding of a prefix code is unique, so re-encoding the decoded
  values reproduces the bits exactly.
- **Not stored**: `part2_3_length` (re-derived from the re-encoded size plus the tail),
  `main_data_begin` (predicted as "right after the previous frame's data", residual coded),
  CRCs (recomputed; a flag, or the stored value if it was wrong), headers (XOR with the
  previous one, zstd).

### 2. Coefficient model

- Pair symbols `(min(|x|, 15), min(|y|, 15))` in the granule's own Huffman table alphabet,
  quadruple symbols, and for escapes (values ≥ 15 in tables with linbits) the bit length
  of the escape together with its second highest bit. Signs and the remaining escape
  bits are raw bits.
- Pair context: (table_select, magnitude bucket, other channel class):
  - the magnitude bucket (2 per octave, 24 + "none") of the neighbourhood of the pair in
    the previous granule of the same channel (lines k−2..k+3, weighted), scaled by the
    change of quantizer step size between the two granules (global_gain, scalefactors,
    pre-emphasis, scalefac_scale; 2^(−3d/16) in fixed point);
  - the magnitude class (6) of the other channel at the same lines (channel 1 only).
  - Nothing decoded in the same granule enters the context, so there is no serial
    dependency between pairs when decoding. Adding the previous pair gained 0.53 pp of
    ratio but made decompression roughly 40% slower (measured under load); the pair two
    back gained 0.37 pp for −14% decompression, −9% compression.
- Quadruples: (count1 table, nonzero lines of the previous granule, other channel);
  escapes: (table, bucket); scalefactors: (size, previous scalefactor of the granule,
  same scalefactor of the previous granule).
- Static tables trained on FMA (4511 files), built into the binary (290 KB). Adaptive
  per-file models lost to them: learning costs more than they gain at these context
  counts.

### 3. Side information

Granule fields (block types, table selects, region counts by the band where the big
values end, big values and gain as deltas, scalefac_compress, flags, count1 quadruple
count, tail length) and frame fields (placement, main_data_begin residual, private bits,
scfsi) go through an adaptive binary range coder with contexts from the previous granule.
Encoders differ in how they set these fields, so per-file adaptation pays here. 1.7% of
the input.

### 4. Entropy coding

- **rANS** with 12-bit probabilities, 64-bit state, 32-bit renormalisation, 8
  interleaved states.
- **Alias tables** for decoding: one 64-bit entry per bucket holds the cutoff, both
  symbols' frequencies, the alias and its rank offset. A symbol costs one load and a few
  selects, without branches. A sorted-symbol LUT with a fallback search mispredicted on
  21% of the symbols and was 2× slower.
- **Encoder**: per context an inverse map (rank → slot, 4096 entries), built on first use
  of the context and kept for the process; division by reciprocal multiplication.
- **Tables** are built lazily: the decoder's alias tables on first decompression (about
  5 ms), the encoder's inverse maps per context used. Identical tables (unused contexts)
  are shared.

### 5. Speed

- **Fused passes**: compression decodes MP3 Huffman codes and emits model symbols in one
  pass (the sign bits are copied from the MP3 stream into the raw stream); decompression
  turns decoded symbols directly into Huffman bits (the raw sign bits follow the codes
  unchanged). No coefficient arrays in between. The failure path rolls the coder back.
- **Huffman decoding**: register bit buffer with branchless refill; an 11-bit LUT
  resolves code and signs (tables without linbits) or the code (with linbits, escapes
  extracted from the same 64-bit window).
- **Contexts** of a granule are computed in one pass before coding it, per band.
- **Bit writers**: branchless 8-byte stores for the reconstructed main data; a 32-bit
  word writer for the many short raw writes of the encoder.
- **Coder state** (rANS states, bit buffers) is copied into locals for each granule.

### 6. Container

The full specification is [FORMAT.md](FORMAT.md).

```text
magic 69 04 7e 30 fd da ("aQR+MP3" in base64), version(u16 LE = 0), mode(u8)
mode 0 (stored): the input verbatim
mode 1 (coded):
  u64 LE length, u64 LE xxh3 of the original
  byte streams: segments, junk, headers, CRCs, tail bits, raw granules, gaps, side
                (each varint(len << 1 | zstd) [varint raw len] data; zstd level 1)
  varint bit lengths, rANS word count, raw bit count; rANS words; raw bits
```

- `compress` never fails: panics and anything larger than the input fall back to stored.
- Decompression checks length and xxh3, and bounds every size it reads, so corrupted input
  gives an error rather than a crash or a huge allocation.

### 7. Threads

`-t N` (`compress_threads`, `decompress_threads`; `mp3r c` and `mp3r d` default to the
available cores): the output is the same bytes whatever the number of threads, and one
thread, or an input below 64 KiB, runs the code above unchanged. The coefficient model
carries state from granule to granule and the rANS chain is serial, so the model pass
(compression) and the rANS decoding with the Huffman re-encoding (decompression) stay on
the calling thread, in order. Around them (`src/par.rs`):

- **Compression** (one helper thread, whatever N ≥ 2): the helper builds the tables and
  hashes the input while the file is split into frames; compresses the file structure
  streams (segments, junk, headers, CRCs) with zstd and then builds the encoder's inverse
  maps of the contexts the side information says may be used (the Huffman tables, count1
  tables and scalefactor sizes of the file, most used first) while the model pass runs;
  then compresses the other streams while the rANS words are produced.
- **Decompression**: the side information (adaptive range coder, independent of the rANS
  stream) is decoded on its own thread, ahead of the main pass, in batches of frames; with
  3 or more threads another builds the tables, the decoder's alias tables and the rANS
  decoder while the streams are unpacked and the headers read (with 2, the side
  information thread builds the tables first); the output (headers, side information,
  CRCs, main data) is assembled in up to N pieces, one per 1024 frames.
- Errors are the same as with one thread, in the same order of precedence.
- Not done: splitting the Huffman re-encoding from the rANS decoding (it is a table lookup
  and a write per symbol, about the cost of handing the values over), and a chunked model
  pass for compression (granules depend on the previous granule of the channel and on
  scalefactors of any earlier granule; it would need warm-up, state validation and
  splicing of the symbol and bit streams).

## Verification

- `mp3r bench`: every file round-trips through the container and through the coded path.
- `mp3r fuzz`: bit flips, truncation, deletion and insertion; both paths must round-trip
  without panics (with `-t`, also through the threads, with the one-thread output).
- `cargo test --release`: unit tests (bit I/O, Huffman tables and a random round trip for
  every table, rANS, reciprocals, range coder), `tests/regress.rs` and `tests/threads.rs`.
- The held-out FMA set above (3489 files) and fuzzing of FMA and synthetic files pass.

## Tried and dropped

| Attempt | Outcome |
|---|---|
| zstd on serialized fields | About 1% gain; the coefficient data needs a model |
| Adaptive multi-symbol contexts | Worse than static tables at useful context counts |
| Current-granule neighbours in the pair context | −0.53 pp ratio but about −40% decompression (serial chain); lag 2: −0.37 pp, −14% |
| 4 buckets per octave, 8 position classes, position classes at all | No gain once the other channel became its own dimension |
| 14-bit probabilities | ~0.1 pp, but the encoder's inverse maps would grow to 160 MB |
| Sorted-symbol coarse LUT for rANS decoding | Mispredicts (21% mixed buckets), 2× slower than alias tables |
| Prior smoothing of the trained tables | No gain with 4500 training files |
| Range-coded (adaptive) scalefactors | About the same ratio as static rANS, slower |

## Open issues and limitations

- **Gap to packMP3**: about 3 pp of ratio (0.849 vs 0.819). Per-file tables for the most
  used contexts are estimated at 0.5–0.6 pp but cost table construction at decompression.
- **Encoder diversity**: tested on FMA (uploads from many encoders, clipped with
  `ffmpeg -acodec copy`) and LAME 3.100. No files from FhG, iTunes, Xing, Helix or Shine
  have been checked specifically; any oddities still round-trip (stored verbatim where
  needed), but may compress less.
- **Mixed blocks** are decoded with minimp3's band layout; MPEG-2.5 8 kHz short blocks may
  differ between decoders (ffmpeg uses a different region boundary). Either way bits are
  reproduced exactly; only the model may be worse.
- **Layer I/II** and MP3 inside other containers (MP4, MKV, WAV) are stored as junk.
- **Memory**: about 30–40 MB, mostly tables.
