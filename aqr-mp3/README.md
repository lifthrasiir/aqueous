# aqr-mp3 (`mp3r`)

A lossless MP3 recompressor: MPEG audio Layer III files (MPEG-1, MPEG-2 and MPEG-2.5,
including free format) are stored smaller and restored bit for bit, in the family of
packMP3. Speed comes first: the target is 100 MB/s of MP3 file single-threaded on an
Apple M4, both ways; compression ratio is pursued only where it does not cost that.

## Results

Measured on 2026-10-24 on an Apple M4, one thread, through `aqr-show` (see the
[top-level README](../README.md#how-it-was-measured)): each file archived at level `mid` with
its round-trip check, then extracted. Ratios are tentative, since the decoder modules are not
in the archives yet. Memory is the peak RSS of that process (input, archive and output
included) over the input size. 402 files of FMA (401 MB, about 1 MB each).

- **One file per archive (worst): 0.893.** The built-in tables are the module's resource
  (131 KB raw, about 38 KB archived), stored in every archive that uses the module; a 1 MB
  track pays for it (against 0.971 under `zstd -3`). Before the contexts shared tables, the
  resource was 1.5 MB raw and about 340 KB archived, and every file was kept as it is (0.975).
- **The resource shared (best)**, as by many files of one archive (`aqr-show -r`: the formulas
  taken where they pay without it, its block left out): **0.855**, at **46 MB/s** compressing
  and **119 MB/s** decompressing. With a table per context it was 0.855 too (0.0002 better) at
  20 and 104 MB/s: the encoder's inverse maps (8 KB per table used) and the decoder's alias
  tables now fit in far less memory.
- Memory: about 61 MB + 6.4× the file (a fit over concatenations of the sample, 9 to 120 MB,
  each coded as one file with `-e`; the sample's files take 32–59 MB, median 41 MB). The same
  concatenations took 28–52 MB more with a table per context (102 MB + 6.4×). The fixed part
  is the tables (the frequencies, the decoder's alias tables, and the encoder's inverse maps
  of the tables used, 4 MB at most); what follows the file is the archive's mostly (the file,
  its streams, their verification and the output). aqr-mp3 on its own peaks at about 3× the
  file encoding (the reservoir, the frames, the raw bits and the rANS words) and 2.4×
  decoding (the output and the words), on top of the tables. It was about 140 MB + 14.7×
  before runs (below) and the assembly as the reservoir is rebuilt.

The comparison with packMP3, `zstd -19` and `xz -9` on the same files is `tools/compare.sh
PACKMP3 WORKDIR DIR...`.

## Usage

```sh
cargo build --release

mp3r bench [-n ITERS] [-t N] [-v] FILE|DIR... # round trip check, .aqr ratio, throughput, per-stream sizes
mp3r info FILE|DIR...                # frames, junk, tail / raw / gap bits, symbol counts
mp3r fuzz [-n N] [-s SEED] [-t N] FILE|DIR... # mutated inputs (flips, cuts, deletions, insertions)
cargo run --release --example memprobe FILE... # peak heap of encoding and decoding (LOG=MB: allocations)
train [-a] [-k K] OUT FILE|DIR...    # trains the built-in tables, K of them (500), on every file with -a, else every second
```

`-t N`: threads, default 1 (`fuzz` then also checks that the formula equals the one-thread
formula). See [Threads](#6-threads).

The crate is a module of entry formulas (aqr-formula), `mp3-recons`; archives are written
and read through `aqr-compress` and `aqr-decompress`.

```rust
let f = aqr_mp3::formula::encode(&mp3, 8);         // None: not worth a formula; the same for any number of threads
// f.eval(..) with aqr_mp3::formula::decode as the module gives mp3 back
```

Any input is accepted. Whatever is not an MP3 frame is kept verbatim in a stream, and so is
any main data that cannot be reproduced.

## Design

### 1. Decomposition

The format is specified in [FORMAT.md](FORMAT.md). Only main data that decodes is modelled:
a granule that cannot be decoded (missing table, big values past the end, ...) is stored
verbatim, as is every bit outside placed frames. Huffman decoding of a prefix code is
unique, so re-encoding the decoded values reproduces the bits exactly. What can be derived
(`part2_3_length`, CRCs, a predicted `main_data_begin`, headers as differences) is not
stored.

### 2. Coefficient model

- Contexts use only the previous granule of the channel and the other channel, never
  anything decoded in the same granule, so there is no serial dependency between pairs when
  decoding. Adding the previous pair gained 0.53 pp of ratio but made decompression roughly
  40% slower (measured under load); the pair two back gained 0.37 pp for −14%
  decompression, −9% compression.
- Static tables trained on FMA (4511 files), built into the binary (33 KB). The 6537
  contexts share 500 tables: contexts of one alphabet size are merged greedily, the pair
  costing the fewest bits on the training set first. On the held-out FMA files this costs
  0.018 pp of ratio (ideal code lengths) for a resource of 131 KB instead of 1.5 MB raw,
  38 KB instead of 340 KB archived. Merging is free down to about 1500 tables (the rare
  contexts gain what the frequent ones lose), and log-quantizing the frequencies (steps of
  2^(1/8)) would save 10 KB more for 0.004 pp. Adaptive per-file models lost to static
  tables: learning costs more than they gain at these context counts.

### 3. Side information

Adaptive binary range coding with contexts from the previous granule. Encoders differ in
how they set these fields, so per-file adaptation pays here. 1.7% of the input.

### 4. Entropy coding

- **rANS** with 8 interleaved states.
- **Alias tables** for decoding: one 64-bit entry per bucket holds the cutoff, both
  symbols' frequencies, the alias and its rank offset. A symbol costs one load and a few
  selects, without branches. A sorted-symbol LUT with a fallback search mispredicted on
  21% of the symbols and was 2× slower.
- **Encoder**: per context an inverse map (rank → slot, 4096 entries), built on first use
  of the context and kept for the process; division by reciprocal multiplication.
- **Runs**: the stream restarts every 1024 frames (16 words each, 0.006% of the archive),
  so the encoder holds the symbols (4 bytes each, about 1.2 per byte of input) of one run
  rather than of the file.
- **Tables** are built lazily: the decoder's alias tables on first decompression (about
  5 ms), the encoder's tables on first compression and its inverse maps per context used.
  Contexts of one table share its alias table and inverse map. Decoding with the built-in
  resource uses the process's tables; another resource gets its own.

### 5. Speed

- **Fused passes**: compression decodes MP3 Huffman codes and emits model symbols in one
  pass (the sign bits are copied from the MP3 stream into the raw stream); decompression
  turns decoded symbols directly into Huffman bits (the raw sign bits follow the codes
  unchanged). No coefficient arrays in between. The failure path rolls the coder back.
- **Assembly** (one thread): each frame is written out once its side information is
  complete and its payload final in the reservoir, which is kept from the next frame's
  payload on only.
- **Huffman decoding**: register bit buffer with branchless refill; an 11-bit LUT
  resolves code and signs (tables without linbits) or the code (with linbits, escapes
  extracted from the same 64-bit window).
- **Contexts** of a granule are computed in one pass before coding it, per band.
- **Bit writers**: branchless 8-byte stores for the reconstructed main data; a 32-bit
  word writer for the many short raw writes of the encoder.
- **Coder state** (rANS states, bit buffers) is copied into locals for each granule.

### 6. Threads

`-t N` (the `threads` of `formula::encode` and `formula::decode`): the formula is the same
whatever the number of threads, and one thread, or an input below 64 KiB, runs the code
above unchanged. The coefficient model carries state from granule to granule and the rANS
chain is serial, so the model pass (encoding) and the rANS decoding with the Huffman
re-encoding (decoding) stay on
the calling thread, in order. Around them (`src/par.rs`):

- **Encoding** (one helper thread, whatever N ≥ 2): the helper builds the tables while the
  file is split into frames, and then builds the encoder's inverse maps of the contexts the
  side information says may be used (the Huffman tables, count1 tables and scalefactor
  sizes of the file, most used first) while the model pass runs.
- **Decoding**: the side information (adaptive range coder, independent of the rANS
  stream) is decoded on its own thread, ahead of the main pass, in batches of frames; with
  3 or more threads another builds the tables, the decoder's alias tables and the rANS
  decoder while the headers are read (with 2, the side
  information thread builds the tables first); the output (headers, side information,
  CRCs, main data) is assembled in up to N pieces, one per 1024 frames, from the reservoir
  held whole.
- Errors are the same as with one thread.
- Not done: splitting the Huffman re-encoding from the rANS decoding (it is a table lookup
  and a write per symbol, about the cost of handing the values over), and a chunked model
  pass for encoding (granules depend on the previous granule of the channel and on
  scalefactors of any earlier granule; it would need warm-up, state validation and
  splicing of the symbol and bit streams).

## Verification

- `mp3r bench`: every file round-trips through its `.aqr` archive and through the coded path.
- `mp3r fuzz`: bit flips, truncation, deletion and insertion; both paths must round-trip
  without panics (with `-t`, also through the threads, with the one-thread formula).
- `cargo test --release`: unit tests (bit I/O, Huffman tables and a random round trip for
  every table, rANS, reciprocals, range coder), `tests/regress.rs` and `tests/formula.rs`.
- The held-out FMA set (3489 files) and fuzzing of FMA and synthetic files passed with the
  former container format.

## Tried and dropped

| Attempt | Outcome |
|---|---|
| zstd on serialized fields | About 1% gain; the coefficient data needs a model |
| Adaptive multi-symbol contexts | Worse than static tables at useful context counts |
| Current-granule neighbours in the pair context | −0.53 pp ratio but about −40% decompression (serial chain); lag 2: −0.37 pp, −14% |
| 4 buckets per octave, 8 position classes, position classes at all | No gain once the other channel became its own dimension |
| 14-bit probabilities | ~0.1 pp, but the encoder's inverse maps would grow to 160 MB |
| Sorted-symbol coarse LUT for rANS decoding | Mispredicts (21% mixed buckets), 2× slower than alias tables |
| Prior smoothing of the trained tables | No gain with 4500 training files |
| Range-coded (adaptive) scalefactors | About the same ratio as static rANS, slower |

## Open issues and limitations

- **Gap to packMP3**: about 3 pp of ratio (measured with the former container format).
  Per-file tables for the most used contexts are estimated at 0.5–0.6 pp but cost table
  construction at decompression.
- **Encoder diversity**: tested on FMA (uploads from many encoders, clipped with
  `ffmpeg -acodec copy`) and LAME 3.100. No files from FhG, iTunes, Xing, Helix or Shine
  have been checked specifically; any oddities still round-trip (kept verbatim where
  needed), but may compress less.
- **Mixed blocks** are decoded with minimp3's band layout; MPEG-2.5 8 kHz short blocks may
  differ between decoders (ffmpeg uses a different region boundary). Either way bits are
  reproduced exactly; only the model may be worse.
- **Layer I/II** and MP3 inside other containers (MP4, MKV, WAV) are stored as junk.
- **Memory**: about 61 MB of peak RSS through `aqr-show` whatever the file (see Results), the
  encoder's inverse maps 4 MB of it at most. The tables are also the resource every archive
  carries (about 38 KB archived). Decoding with more than one thread still holds the
  reservoir whole.
