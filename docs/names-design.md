# 파일명 해석과 변환 (해제 시)

아카이브의 이름을 파일시스템의 이름으로 바꾸는 정책과 그 사용자 인터페이스. 이름의 저장 형식
(`wtf-8`/`raw`)과 해제의 일반 요건은 스펙의 "Entry names"와 "Extraction"에, ZIP 이름의 출처
순서는 "Entry names from ZIP"에 있다.

## 단계

이름 하나는 해제 때 네 단계를 거친다.

| 단계 | 하는 일 | 옵션 |
|---|---|---|
| ① 해석 | 인코딩이 선언되지 않은 바이트열을 Unicode로, 또는 바이트 그대로 | `-E` |
| ② 분리 | 경로를 이름들로 (`/`, DOS 호스트면 `\`) | (①을 따름) |
| ③ 정규화 | NFC/NFD | `--normalize` |
| ④ 사상 | 이 파일시스템이 쓸 수 없는 이름의 처리 | `--bad-names` |

기본값은 모두 `auto`이며, 결정한 바(추정, 대체, 정규화)는 아카이브마다 보고한다.

## 옵션

```
-E, --encoding=ENC[,ENC…]   auto | raw | system | WHATWG 레이블 (shift_jis, euc-kr, gbk, big5, ibm437, utf-8, …)
    --normalize=FORM        auto | nfc | nfd | keep
    --bad-names=POLICY      auto | keep | replace | fail
```

`-C`는 tar 계열의 `-C DIR` 관례대로 `--directory`에 쓴다.

### `-E`: 해석

선언되지 않은 이름만 대상이다. 선언된 것(ZIP의 UTF-8 플래그와 0x7075, 7z와 RAR5와 RAR의 Unicode
이름, aqr의 `wtf-8`)은 다시 해석하지 않는다. 다만 선언과 달리 유효한 UTF-8이 아닌 이름(UTF-8
플래그를 잘못 세운 ZIP)은 선언되지 않은 것으로 본다.

대상은 출처에 따라 두 부류로 나누고, 해석하는 곳도 다르다.

- 코드 페이지 텍스트: 선언 없는 ZIP, ALZ, 코드 페이지 없는 EGG, Unicode 이름이 없는 RAR 1.5–4.x.
  만든 기계의 코드 페이지로 쓴 텍스트다. aqr-unpack이 목록을 읽을 때(②의 분리 전에) 해석한다.
  해석하지 못한 이름은 `raw` 이름(C1)으로 트리에 넣는다.
- 파일시스템 바이트: aqr의 `raw` 이름, UTF-8이 아닌 tar 이름. 파일시스템에서 가져온 바이트이고
  스펙이 말하는 왕복 수단이다. 해제기(aqr의 `extract.rs`)가 파일을 만들 때 해석한다.

`auto`는 이름마다가 아니라 아카이브마다 한 번 정한다(tar처럼 목록이 없으면 처음 알려진 항목들로).

1. 대상 이름이 모두 유효한 UTF-8이면 UTF-8.
2. 아니면 유효한 UTF-8인 이름은 UTF-8로 두고(다른 도구가 UTF-8로 덧붙인 항목; 레거시
   인코딩의 비ASCII 이름이 우연히 UTF-8로 유효한 일은 드물다), 나머지로 후보를 고른다.
   후보는 shift_jis, euc-kr, gbk, big5, (시스템 코드 페이지), ibm437. 점수는 비ASCII 문자당
   평균이다. 각 문자 체계의 상용 문자(가나, 상용 한글 음절, 그 후보의 상용 한자 목록)는 높게,
   반각 가나와 PUA와 상자 그림 문자와 기호는 낮게 친다. 로캘의 언어(Windows는 ANSI 코드
   페이지, 그 밖은 `LANG`)가 가리키는 후보에 조금 더하고, 디코딩하지 못하는 이름의 비율만큼
   뺀다(무엇이든 디코딩하는 ibm437이 이것만으로 이기지 않게). euc-kr과 gbk처럼 바이트 구조가
   겹치는 쌍은 상용 문자 비율로 갈린다. 상용 문자 목록은 `aqr-foreign`의
   `charset/common.rs`에 있다.
3. 1등이 모든 이름을 디코딩하지 못하거나, 점수가 낮거나, 2등과의 차가 작으면 "확신 없음"이다.
   형식에 관례가 있으면 그것이 먼저다: ALZ는 ALZip이 쓰는 CP949가 모든 이름을 디코딩하면 그것.
4. 코드 페이지 텍스트는 확신이 없어도 최선 후보로 디코딩하고 추정이라고 보고한다.
5. 파일시스템 바이트는 바이트 이름을 쓸 수 있는 곳(Linux와 BSD, ④ 참고)이면 해석하지 않고
   바이트 그대로 쓴다. 같은 환경에서 풀면 원래 바이트가 나와야 하기 때문이다. 쓸 수 없는
   곳(macOS, Windows)이면 2–4와 같이 해석한다.

그 밖의 값:

- `raw`: 해석하지 않는다. 바이트를 쓸 수 없는 곳에서는 ④로 넘긴다.
- `system`: 이 시스템에서 그 형식이 관례적으로 쓰는 코드 페이지(Windows에서 ZIP과 ALZ와 RAR은
  OEM, aqr과 tar는 ANSI; 그 밖에서는 로캘의 인코딩).
- 레이블 하나: 그것으로 디코딩한다. 실패한 이름은 ④로 넘기고 하나씩 보고한다.
- 레이블 여럿: `auto`의 후보를 그것들로 한정한다.

`-E`는 모든 입력에 같이 적용되고, 중첩된 아카이브는 각각 따로 판정된다.

### ② 분리

경로 전체를 ①의 인코딩으로 디코딩한 뒤 코드 포인트 단위로 나눈다. cp932의 `表`(95 5C)나
`ソ`(83 5C)처럼 둘째 바이트가 0x5C인 문자가 구분자가 되지 않게 하기 위해서다. WHATWG의
`shift_jis`는 cp932이고 0x5C를 U+005C로 디코딩하는데, 일본 Windows에서 ¥로 보이는 그 문자가
구분자이므로 그것이 맞다.

해석하지 않는 이름도 문자 경계는 필요하다. `auto`의 최선 후보(확신이 없더라도)로 경계를 찾아
나누고 각 이름은 원래 바이트로 되돌린다. 어느 후보로도 디코딩되지 않으면 `/`에서만 나누고 0x5C는
이름에 남긴다(entry name이 금하는 것은 `/`뿐).

### `--normalize`: 정규화

- `auto`: Windows와 Linux에서는 조합만 하는 NFC. 정준 분해된 열을 조합하되, 싱글턴 분해 대상
  문자(U+F900–FAFF와 U+2F800–2FA1F의 CJK 호환 한자, U+2126 Ω, U+212A K, U+212B Å 등)는 바꾸지
  않는다. 엄격한 NFC는 일본어 이름의 호환 한자를 바꿔 버리고, HFS+의 NFD도 그 영역은 분해하지
  않는다. macOS에서는 `keep`(파일시스템이 정규화를 구분하지 않는다).
- `nfc`, `nfd`: 엄격한 정규화.
- `keep`: 그대로.

정규화로 같은 디렉터리의 이름이 겹치게 되면 기존 충돌 규칙대로 뒤의 것을 만들지 않고 보고한다.
Windows의 `Folding::Full`은 원래도 정규화를 접어서 비교하므로 이것이 새 제약은 아니다. 아카이브에는
만든 OS가 기록되지 않아 출처로 판단할 수는 없지만, NFC가 아닌 이름은 대부분 macOS에서 온다.

### `--bad-names`: 쓸 수 없는 이름

| | 바이트 이름을 쓸 수 있는 곳 | macOS | Windows |
|---|---|---|---|
| lone surrogate | `keep`: WTF-8 바이트(ED A0 80) | `replace`: U+FFFD | 네이티브 UTF-16 |
| 해석되지 않은 바이트 | `keep`: 바이트 그대로 | `replace`: `%XX` | `replace`: `%XX` |
| `<>:"\|?*`, 끝의 점과 공백, 장치 이름 | — | — | `replace`: `_` |

- `-E auto`에서 바이트 이름을 해석하지 않는 것은 바이트를 그대로 쓸 수 있을 때, 즉 바이트
  이름을 쓸 수 있는 곳이고 `--bad-names`가 `auto`나 `keep`일 때다.
- 바이트 이름을 쓸 수 있는 곳은 Linux와 BSD이되, 해제하는 곳의 파일시스템이 이름을 접는
  것(`Folding`이 `Exact`가 아닌 것: vfat, exFAT, HFS, 대소문자를 접는 ext4와 CIFS 등)은 뺀다.
  그런 파일시스템은 대개 UTF-8을 강제하기 때문이다.
- `keep`이 왕복을 지키는 이유: 압축기는 WTF-8로 유효한 바이트를 `wtf-8` 이름으로
  저장한다(`aqr-formula`의 `tree.rs`의 `name_from`). 그래서 Windows에서 압축하고 Linux에서
  풀었다가 다시 압축해 Windows에서 풀면 원래 이름이 된다.
- `%XX`는 macOS가 HFS에서 하는 방식과 같다. 해석되지 않은 바이트와 함께 이름의 `%`와 0x5C도
  `%25`, `%5C`로 쓴다(`names::escaped`; Windows에서는 0x5C가
  구분자로 읽히기 때문이다). 그래서 이름 둘이 겹치지 않는다. 대체는 일방향이며, 보고로 알린다.
- `keep`을 할 수 없는 곳의 `keep`은 `replace`다. `fail`은 대체가 필요한 이름이 있으면 해제를
  실패시킨다(스펙의 "fail or report" 중 fail).

## 보고

아카이브마다 결정을 한 줄씩 standard error에 쓴다(`-q`면 쓰지 않는다). 해석은 확신이 없을
때만, 정규화는 바꾼 이름이 있을 때 그 수를 쓰고, 대체한 이름은 이름마다 쓴다(스펙이 요구한다).

```
old.zip: 214 names of no declared encoding read as shift_jis (guessed; also possible: euc-kr; -E to choose)
win.aqr: 3 names with lone surrogates written with U+FFFD (--bad-names)
mac.aqr: 1204 names composed (NFC)
```


## 시나리오

| 시나리오 | 기본값 | 명시 |
|---|---|---|
| Shift_JIS ZIP, 0x5C를 둘째 바이트로 가진 문자 | 아카이브 전체를 shift_jis로 추정, 디코딩 후 분리 | `-E shift_jis` |
| Windows의 lone surrogate를 다른 OS에서 | Linux는 WTF-8 바이트, macOS는 U+FFFD + 보고 | `--bad-names=replace`/`fail` |
| macOS의 NFD 이름을 Windows에서 | 조합만 하는 NFC | `--normalize=keep`/`nfc` |
| Linux의 깨진 바이트 이름을 같은 환경에서 | 바이트 그대로 | `-E raw` |
| 그 아카이브를 Windows에서 인코딩 지정해 | 추정 디코딩 | `-E euc-kr` |
| 인코딩이 틀리게 선언된 ZIP(UTF-8 플래그인데 UTF-8 아님) | 선언 없는 것으로 보고 추정 | `-E …` |
| 한 아카이브에 선언된 이름과 선언 없는 이름이 섞임(다른 도구로 항목 추가) | 선언 없는 것들만으로 판정 | `-E …` |
| 링크 대상 | 이름과 같은 ①③④를 이름마다 적용(링크가 가리키는 이름과 같아야 한다) | |
| Linux에서 vfat, exFAT, SMB 등으로 해제 | 바이트 이름을 쓸 수 없는 곳으로 보고 `replace` | `--bad-names=fail` |
| 구조가 겹치는 인코딩(euc-kr과 gbk, gbk와 big5) | 상용 문자 비율로 정하고, 차가 작으면 추정이라고 다른 후보와 함께 보고 | `-E …` |

## 남은 것

- 명령줄로 고른 경로와 `--rename`은 아직 저장된 이름과 비교한다. ①③을 거친 이름과 비교하고,
  정규화를 무시하고 맞춰야 한다(macOS 터미널은 NFC로 입력하는데 아카이브의 이름은 NFD일 때).
- 디코딩하면 길이가 는다(cp932의 2바이트가 UTF-8의 3바이트). Linux의 NAME_MAX(255바이트)를 넘는
  이름은 지금은 OS 오류로 실패한다.
- 보고와 목록에서 제어 문자와 bidi override(U+202E)를 이스케이프하기.
- 이름이 아닌 텍스트: ZIP 주석, tar의 uname/gname, 확장 속성의 이름.
- 압축 쪽(aqr-pack): lone surrogate나 `raw` 이름을 ZIP과 tar에 쓰기, 옛 도구를 위한 cp932 ZIP
  (`--format zip -E shift_jis`).
- `--ipc`: 확신이 없을 때 후보와 표본 이름을 이벤트로 보내 프런트엔드가 고르게 하기.
- `-t`(aqr 아카이브의 목록)는 저장된 바이트를 그대로 보인다. 해석한 이름을 보이는 것은 아직
  아니다.
- `-v`로 해석하거나 정규화한 이름마다 원래 이름과 새 이름을 보이기.
