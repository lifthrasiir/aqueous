# macOS 앱 번들: 남은 일

macOS 앱(`Foo.app` 꼴의 디렉토리)을 `aqr`로 압축한 결과와, 최적에 가까워지려면 더 필요한 도구를
적는다. 2026-10-30에 이 Mac의 `/Applications`에서 고른 앱 7개를 재 보았다.

## 측정

Apple M4, 커밋 `f2e1d44`의 `cargo aqr -c -v`(level mid, 나머지 기본값). 파일별 몫은 `-v` 로그에서,
번들 안의 분류와 Mach-O 내부 구분은 따로 쓴 스크립트(번들의 일반 파일을 매직과 확장자로 나누고,
Mach-O를 슬라이스, 섹션, `__LINKEDIT`의 load command별 범위, 코드 서명의 블롭으로 자른 것)로 냈다.
스크립트는 남기지 않았다.

| 앱 | 성격 | 원본 MB | `tar \| zstd -3` MB | aqr MB | aqr / 원본 | aqr / zstd |
|---|---|---|---|---|---|---|
| Secretive | Swift, 3 아키텍처(x86_64, arm64, arm64e) | 35.6 | 6.46 | 3.23 | 0.091 | 0.500 |
| Deskflow | Qt, arm64만 | 67.8 | 26.19 | 19.81 | 0.292 | 0.756 |
| Windows App | Microsoft, universal | 270.3 | 131.83 | 111.06 | 0.411 | 0.842 |
| Discord | Electron 42 | 503.2 | 205.04 | 153.88 | 0.306 | 0.750 |
| Pages | Apple iWork | 686.1 | 276.41 | 202.16 | 0.295 | 0.731 |
| Blender | arm64, Python 내장 | 934.5 | 295.43 | 242.65 | 0.260 | 0.821 |
| Google Chrome | 프레임워크 버전 3벌 | 2280.0 | 1055.17 | 607.38 | 0.266 | 0.576 |
| **합계** | | **4777.5** | **1996.5** | **1340.2** | **0.281** | **0.671** |

- 원본은 번들의 일반 파일 크기의 합이다(symlink 제외, 같은 내용 파일 포함).
- Chrome 번들에는 `Google Chrome Framework.framework/Versions/`의 156.0.8078.47, .49, .76이
  모두 있다(각 526 MB, universal). 업데이트 뒤 재시작하기 전까지 Chrome이 남겨 두는 것이다.
- Secretive는 같은 바이너리와 리소스가 중첩 번들(LoginItems, XPCServices)에 반복되어, 같은 내용
  파일의 공유가 크게 듣는다.
- `-v`의 파일별 바이트는 여러 파일이 든 solid 블록의 평균 비율로 매긴 것이라, 작은 범주의 aqr
  수치는 어림이다. 아래 Mach-O 내부의 비중은 부분별로 이어 붙인 바이트의 zstd -3이다.

## 종류별

aqr 결과에서 Mach-O 파일이 75%(783 MB)이다. 나머지는 Pages의 JPEG 64 MB, 분류되지 않은 파일(대부분
Blender의 정적 라이브러리, WOFF2, gettext 카탈로그) 61 MB, Chromium `.pak` 53 MB, Pages의 binary plist 18 MB 순이다.

Mach-O 내부(같은 내용 파일 제외, 원본 2829 MB)의 zstd -3 비중:

| 부분 | 원본 MB | zstd -3 MB | 비중 |
|---|---|---|---|
| 코드(arm64) | 1128.2 | 465.2 | 41.7% |
| 코드(x86-64) | 897.3 | 406.4 | 36.4% |
| `__TEXT,__const` | 221.4 | 124.6 | 11.2% |
| 코드 서명의 페이지 해시 | 23.3 | 23.2 | 2.1% |
| `__unwind_info`, `__eh_frame` 등 | 41.8 | 21.8 | 2.0% |
| `__cstring` 등 | 80.2 | 18.2 | 1.6% |
| `__DATA*,__const` | 100.9 | 15.7 | 1.4% |
| 기호 테이블(strtab, symtab) | 210.7 | 18.0 | 1.6% |
| 그 밖 | | | 2% 미만 |

- 기호 테이블은 앱에 따라 크게 다르다. strip되지 않은 Secretive와 Windows App에서는 Mach-O의
  18–29%이고 Chrome과 Discord에서는 거의 0이다.
- `__TEXT,__const`의 큰 몫은 Blender의 `libOpenImageDenoise_core.dylib`(46.5 MB, 신경망 가중치,
  aqr 92.6%)와 Chrome 프레임워크이다.
- universal 바이너리의 슬라이스 사이 공유는 문제가 아니다. aqr은 fat 파일 안에서 이미 공유를
  잡는다. 슬라이스를 따로 압축한 것보다 Windows App −9.8%, Electron Framework −7.1%, WebRTC
  −7.3%로, zstd `--long=31`(−7.3%, −5.4%)과 같거나 낫다.

## 할 일

효과가 큰 순서이다.

### 1. 큰 스트림을 파일 사이에서 나누기

거의 같은 큰 바이너리(같은 프로그램의 다른 버전) 사이의 공유를 지금은 거의 얻지 못한다.

- `merge_classes_within`(`aqr-formula/src/lib.rs`)은 같은 클래스의 스트림을 `-b`(16 MiB)까지
  이어 붙이고, 그보다 긴 스트림은 자르지 않고 혼자 둔다. Chrome arm64 슬라이스 하나(251.7 MB)의
  스트림은 `arm64/CODE` 214 MB, `recs/raw` 35 MB이고 나머지는 4 MB 이하라, 대부분의 바이트가
  다른 버전의 같은 스트림과 만나지 못한다. 스트림은 각각 따로 zstd로 압축되고 LDM 윈도우도
  2^27(`WINDOW_LOG_MAX`)에서 끝난다.
- 두 버전(.47, .49)의 arm64 슬라이스를 한 아카이브로 묶으면 150.78 MB로, 하나(79.48 MB)의 두 배보다
  5% 작을 뿐이다. 그 5%는 작은 스트림이 합쳐진 몫이다. 같은 B를 `zstd -3 --long=31 --patch-from=A`로
  압축하면 혼자(107.5 MB) 대비 64.5 MB이다.
- `-b 1G`로 묶으면 오히려 189.42 MB로 커진다. 원인은 모른다(레벨 고르기를 볼 것).

`arm64/CODE` 두 개(각 214 MB)로 배치를 비교했다. 각 스트림을 aqr의 `external()`처럼 따로
압축했다(zstd -7, 윈도우는 길이만큼 2^27까지, 8 MiB부터 LDM).

| 배치 | 합계 MB |
|---|---|
| 각자 통째로(지금) | 124.66 |
| 16 / 32 / 64 MiB로 잘라 각자 | 127.33 / 126.11 / 125.16 |
| 같은 위치의 8 MiB 조각끼리 16 MiB 스트림으로 | 78.34 |
| 같은 위치의 16+16 / 32+32 / 64+64 MiB | 78.23 / 77.83 / 77.54 |
| 이어 붙여 윈도우 2^27 / 2^28(zstd CLI) | 127.63 / 97.77 |

- 자르는 비용은 작다(16 MiB에서 +2.1%). 코드 스트림에서 파일 안의 긴 문맥은 거의 쓰이지 않는다.
- 자르기만 하면 공유가 생기지 않는다. 지금의 first-fit은 조각 하나로 16 MiB를 채우기 때문이다.
  대응하는 조각을 한 스트림에 짝지어야 한다. 8+8 MiB는 `-b`의 상한을 그대로 지킨다(B를 혼자
  읽을 때 A의 8 MiB를 함께 푼다).

조각을 나누는 법과 짝짓는 법(세 쌍, B의 몫이 B를 혼자 통째로 압축한 것 대비):

| | Chrome .47→.49 | Chrome .49→.76 | Electron 42→43 |
|---|---|---|---|
| 고정 8 MiB, 닮음으로 짝짓기 | **−78%** | **−46%** | **−18%** |
| CDC(1–8 MiB, 2–8 MiB), 닮음으로 | −63~65% | −37~40% | −16~18% |
| CDC, 같은 상대 위치로 | −24~34% | −27~28% | −12~14% |
| 참고: `zstd -7 --patch-from`(윈도우 2^28) | −47% | −28% | −17% |

- Electron 42는 Discord의, 43은 VS Code의 것이다(크기가 140 → 148 MB).
- 닮음: 32바이트 buzhash의 하위 12비트가 0인 위치의 해시를 조각의 앵커로 삼고, B 조각의 앵커가
  A 조각에 있는 비율로 1:1 탐욕 매칭했다(5% 미만은 짝 없음).
- CDC는 고정 조각보다 낫지 않았다. 코드가 옮겨지면 바이트가 넓게 바뀌어 내용 경계도 흔들리고,
  조각이 작아 문맥도 짧다. 수 MB의 어긋남은 16 MiB 스트림 안에서 LZ가 흡수하고, 그보다 큰
  어긋남은 닮음 짝짓기가 다른 위치의 조각을 골라 메운다.

했다(`merge_plan`, `aqr-formula/src/pieces.rs`): 한 클래스에 `-b`의 절반보다 긴 스트림이 k개(최대
4개) 있으면 `-b`/k의 고정 조각으로 자르고, 앵커(64바이트 gear hash의 상위 12비트가 0인 위치)를
공유하는 비율이 큰 짝부터 서로 다른 스트림의 조각을 k개까지 묶는다(큰 쪽 앵커의 10% 이상). 묶이지
않은 조각은 스트림마다 하나로 이어 두고, 묶인 조각이 없는 스트림은 지금처럼 통째로 둔다. 묶음은
`-b` 안이라 B를 혼자 읽을 때 함께 푸는 것도 `-b` 안이다.

| | 전 MB | 후 MB |
|---|---|---|
| Chrome 프레임워크 arm64 .47+.49 | 150.78 | 100.26 (−33.5%) |
| 같은 것 .47+.49+.76 | 226.93 | 141.91 (−37.5%) |
| Google Chrome 앱 | 607.38 | 410.69 (−32.4%) |
| Discord | 153.88 | 147.06 (−4.4%) |
| Windows App | 111.06 | 109.33 (−1.6%) |
| Blender | 242.65 | 242.04 (−0.3%) |

- 문턱 5%에서는 Chrome이 1 MB 더 줄었지만 Blender가 기준보다 0.4 MB 커졌다(관계없는 큰 dylib의
  조각이 5–10%로 묶였다). 20%에서는 Chrome이 421.56 MB였다.

크게 삽입되거나 지워진 버전 쌍으로 `aqr` 자신의 빌드(arm64)를 쟀다. 10-27, 10-28, 10-29의 커밋
`880665b`, `9e610a7`, `3d37dae`이고, `__text`가 12.3, 13.3, 14.0 MB인데 파일은 21.0, 20.0, 21.1 MB여서
코드는 늘고 다른 부분은 줄었다. B의 몫은 쌍에서 A 혼자를 뺀 것으로, B 혼자와 비교했다.

| A → B | 전 MB | 후 MB | B의 몫 전 → 후 | 참고: `__text`의 `zstd -3 --patch-from` |
|---|---|---|---|---|
| 10-27 → 10-28 | 11.96 | 10.08 | −6% → −36% | −38% |
| 10-27 → 10-29 | 12.46 | 10.74 | −5% → −30% | −33% |
| 10-28 → 10-29 | 11.91 | 9.64 | −19% → −52% | −37% |
| 셋 모두 | 17.50 | 13.54 (−22.6%) | | |

- 10-29와 10-30(`abfec08`) 사이에서는 하나도 묶이지 않았다(14.33 MB 그대로). 그 사이에
  `rust-toolchain.toml`이 생기고 release 프로필이 fat LTO, codegen unit 하나에서 기본값으로 바뀌어,
  코드 배치가 통째로 달라졌다(`--patch-from`도 −5%). 같은 경로에서 빌드한 것끼리도 그랬으므로 빌드
  경로 탓은 아니다. 이 경우를 메우려면 2의 함수 단위 짝짓기가 필요하다.

남은 것:

- 짝짓기의 probe: 문턱 근처의 짝을 조각 trial 압축으로 정하면 위의 1 MB 둘을 다 얻을 수 있다.
- `-b 1G`가 커지는 원인.

### 2. 참조 버전의 주소 공간으로 BL·ADRP 대상을 다시 쓰기

aqr-exe의 ARM64 필터는 BL과 ADRP의 대상을 절대 주소로 바꾼다. 이것이 버전 사이의 delta를
해치지는 않는다. 필터를 거친 스트림 전체가 원래 `__text`보다 혼자도, delta(`zstd -7
--patch-from`)도 작다.

| | 원래 `__text`: 혼자 → delta | 필터: 혼자 → delta |
|---|---|---|
| Chrome .47→.49 | 86.5 → 47.5 MB (54%) | 71.3 → 34.2 MB (48%) |
| Chrome .49→.76 | 86.5 → 63.4 MB (73%) | 71.3 → 49.5 MB (69%) |
| Electron 42→43 | 59.2 → 51.0 MB (86%) | 49.1 → 40.9 MB (83%) |

남는 것은 코드가 옮겨져 대상 주소가 바뀌는 몫이다. Courgette처럼 B의 대상을 A의 주소로 다시
쓰면 크게 준다. 어림한 방법:

- 함수: BL 대상에서 다음 BL 대상까지. BL·ADRP 즉시값을 지운 워드의 해시가 양쪽에서 유일하게
  같고 길이가 같은 함수를 짝짓는다.
- 짝지은 함수의 같은 자리에 있는 BL 대상과 ADRP 페이지가 A → B의 대응표에 다수결로 표를 던진다.
- B의 대상 중 역상이 있는 것을 A의 주소로 다시 쓴다. BL·ADRP마다 1비트로 어느 쪽인지 알리고,
  대응표는 A의 대상과 페이지 순서로 이동량(B − A)의 차분을 보낸다. 둘 다 zstd -19로 셌다.

1의 배치(고정 8 MiB, 닮음) 위에서 `arm64/CODE`의 B 몫:

| | 짝지은 A 코드 | BL 대응 | ADRP 대응 | 1만 | 1 + 다시 쓰기(부가 정보 포함) |
|---|---|---|---|---|---|
| Chrome .47→.49 | 30% | 88% | 54% | 14.02 MB | 4.99 + 0.48 = **5.47 MB (−61%)** |
| Chrome .49→.76 | 17% | 76% | 24% | 33.37 MB | 18.46 + 0.74 = **19.20 MB (−42%)** |
| Electron 42→43 | 8% | 56% | 4% | 35.17 MB | 31.25 + 0.53 = **31.78 MB (−10%)** |

`--patch-from` 위에서도 −60%, −42%, −14%였다. 1과 2는 거의 더해진다.

대응표의 모양(A 순서로 정렬한 BL 대상의 이동량):

| | 항목 | 일정 구간 | 10+ 구간에 든 비율 | 상위 1000 구간 | B 순서가 뒤집힌 곳 |
|---|---|---|---|---|---|
| Chrome .47→.49 | 295,214 | 5,794 | 97% | 95% | 653 |
| Chrome .49→.76 | 211,505 | 34,491 | 67% | 45% | 5,989 |
| Electron 42→43 | 84,810 | 31,185 | 27% | 22% | 4,861 |

- 패치 버전 사이(.47→.49)는 거의 상수 구간을 이은 함수이다(흔한 이동량 0, +112, −32 워드).
- .49→.76은 이동량이 조금씩 계단으로 바뀐다(27648, 27664, 27696, …). 구간은 많지만 이동량의
  차분은 작다.
- Electron 42→43은 함수 배치가 바뀌었다(구간 길이 중앙값 1).
- ADRP 페이지는 .47→.49에서 3,401개 중 3,242개가 이동량 0, .49→.76에서 대부분 −12이다.

할 일:

- aqr-exe에 참조 이미지의 대응표를 입력으로 받는 모듈(ARM64, x86-64)을 둔다. 디코더는 A의 이미지,
  대응표, 플래그로 B를 되돌린다.
- 짝짓기를 넓힌다. 지금은 해시 일치에만 기대 A 코드의 8–30%만 짝짓는다. 상수 구간 안에서 짝 없는
  함수를 이웃의 이동량으로 짝짓고(패치 버전), 확정된 짝에서 호출 관계를 따라 퍼뜨린다(재배치된
  major 버전, Courgette의 방식).
- 대응표는 0.12–0.29 MB라 표현은 급하지 않다.
- 재 보지 않은 것: 지역 분기 스트림(B0–B3 등), x86-64, ADRP 다음의 `ADD`/`LDR` 하위 12비트.

### 3. 코드 서명 유도

- Mach-O의 `LC_CODE_SIGNATURE`에서 CodeDirectory의 페이지 해시(SHA-256, 4 KiB나 16 KiB 페이지마다)는
  23.2 MB가 줄지 않고 남는다. 결과 전체의 1.7%이고, 모두 이미지에서 계산할 수 있다. 서명된 앱이면
  모두 해당한다. special slot, 요구 사항, 엔타이틀먼트, CMS 블롭(zstd 뒤 0.25 MB)은 작다.
- `_CodeSignature/CodeResources`(XML plist, 번들 파일마다 SHA-1과 SHA-256의 base64)는 전체로는
  0.35%이지만 파일이 많은 Pages에서는 결과의 2.3%(4.6 MB)이다. 번들의 다른 엔트리 여럿을 입력으로
  받으므로 "가변 인자 없음"과 맞게 짜야 한다(`git-pack-index-recons`처럼 집합으로).
- `aqr-exe/README.md`의 Limitations에 페이지 해시가 이미 적혀 있다.

### 4. LZFSE와 LZVN

- `Assets.car`의 LZFSE 렌디션은 대개 앱 아이콘이다. 앱마다 1–1.6 MB(Discord, Blender, Secretive,
  Chrome)로 하나로는 작지만 거의 모든 앱에 있다.
- 같은 코덱이 decmpfs, `.aar`, `.xip`, DMG(ULFO)에 쓰인다(`file-formats.md`). 참조 구현이 공개되어
  있어 aqr-lz4, aqr-snappy처럼 인코더를 재현할 수 있다.

### 5. Electron의 asar

asar는 JSON 헤더(Chromium pickle 안) 뒤에 파일들을 이어 붙인 것이다. 헤더에는 파일마다 이름,
크기, 오프셋과 `integrity`(파일 전체와 4 MiB 블록마다의 SHA-256, 16진수)가 있다. aqr은 asar를
알아보지 못하고 한 파일로 다룬다(스캔으로 안의 실행 파일은 찾는다). 위 7개 앱의 표본에는
Discord의 3.6 MB짜리 하나뿐이어서, 설치된 앱의 asar 둘을 따로 쟀다.

| | 원본 MB | 헤더 JSON(`integrity`) | 파일 | zstd -3 | aqr, asar 그대로 | aqr, 푼 트리 | aqr, 헤더만 |
|---|---|---|---|---|---|---|---|
| OpenMTP `app.asar` | 157.95 | 8.22 (6.33) MB | 31,484개 | 30.02 | 23.54 | 20.57 | 1.41 |
| VS Code `node_modules.asar` | 61.44 | 1.48 (1.11) MB | 5,517개 | 12.04 | 10.02 | 11.09 | 0.28 |

- OpenMTP는 `.node`(네이티브 모듈 17개, 60.0 MB, Mach-O와 PE)와 JS(27,438개, 52.7 MB)가 대부분이다.
  VS Code는 JS, source map, JSON이다.
- 헤더의 `integrity`는 파일 내용에서 계산할 수 있고, 이름, 크기, 오프셋은 트리에서 나온다. 헤더를
  유도하고 파일을 풀어 넣으면 OpenMTP는 23.54 → 20.6 MB 남짓(−12%)이 된다. 헤더만 따로 압축하면
  1.41 MB로, aqr 결과의 6%이다. VS Code는 경로 순서로 이은 파일들(9.73 MB)과 메타데이터만 남아 9.9 MB
  남짓(−1%)이다.
- VS Code는 풀면 오히려 커진다(10.02 → 11.09 MB). 디렉토리로 넣은 파일들이 같은 바이트를 한 파일로
  이은 것보다 크다. 파일을 경로 순서로 이은 한 파일은 aqr 9.73 MB(asar 안의 순서도 같다),
  `sort_key`처럼 확장자 순서로 이은 것은 9.97 MB이다. 디렉토리 쪽 solid 블록의 합이 9.97 MB로
  후자와 같고, 메타데이터가 0.17 MB, solid 밖에 따로 둔 파일들(WOFF, PNG, xsv 등)이 0.8 MB 남짓이다.
  `-b`를 64 MiB, 256 MiB로 키워도 11.03 MB여서 블록 상한 탓은 아니다.

할 일:

- `asar-recons`: 헤더를 트리, 크기, 내용의 해시로 유도한다(`integrity`의 블록 크기, 순서, 키 순서,
  `unpacked`와 `executable` 같은 그 밖의 필드는 기록한다). 파일은 asar 안의 순서대로 하나의 스트림으로
  두되, 알아보는 형식(Mach-O, PE, PNG 등)은 지금처럼 각각 재압축한다.
- 디렉토리 쪽: 확장자 먼저의 정렬이 node_modules 같은 트리에서는 경로 순서보다 2.5% 나쁘다. solid 밖에
  따로 둔 작은 파일들의 몫이 큰 까닭도 볼 것. asar와 상관없이 aqr의 디렉토리 압축 문제이다.

### 6. 텍스트, 특히 JavaScript

JS는 asar 바이트의 대부분이고(Discord 85%, VS Code `node_modules.asar` 약 66%, OpenMTP 35%. OpenMTP의
나머지는 네이티브 모듈 60 MB와 source map 16.6 MB), asar 밖에도 있다(VS Code의 `out/`, `extensions/`에
162.5 MB, 879개, 번들되고 minify된 것으로 줄 평균 430 B). VS Code 전체의 aqr 결과 364 MB에서 asar
밖의 JS가 30.8 MB, asar가 10.0 MB로 11% 남짓이다. 보통의 Electron 앱에서는 Electron Framework가 훨씬
커서 비중이 더 작을 것이다.

각 묶음의 JS를 경로 순서로 이은 한 파일(MB):

| | 원본 | zstd -3 | aqr | PPMd o16(7zz) | xz -9e | aqr / xz |
|---|---|---|---|---|---|---|
| OpenMTP asar의 JS | 52.8 | 7.01 | 4.18 (`wrt-recons`) | 3.67 | **3.49** | +20% |
| VS Code `node_modules.asar`의 JS | 39.7 | 6.97 | 5.58 (`wrt-recons`) | 4.92 | **4.59** | +21% |
| VS Code의 minify된 JS | 162.5 | 42.06 | 25.26 (그대로) | 22.97 | **19.59** | +29% |

aqr이 JS에서 LZMA보다 20–29% 크다. VS Code에서 이 차이를 메우면 9 MB 남짓(앱의 2.5%)이고, JS만이
아니라 텍스트 전반에 걸린다. JS 전용 모델이 xz보다 얼마나 더 줄지는 재지 않았다.

먼저 변수를 나열하고, 거기서 아이템을 골라 구현한다.

- 백엔드
  - zstd의 엔트로피 단계: 리터럴이 문맥 없는 Huffman이다. LZMA는 리터럴을 앞 바이트와 위치로 문맥
    모델링하고(lc/lp/pb), 최근 거리(rep match)를 따로 부호화하며, 최적 파싱을 한다. 그중 어느 것이
    차이의 대부분인지.
  - aqr이 고르는 zstd 레벨과 매개변수: 샘플로 고르는 레벨(`plan_by`, `pick`), 윈도우, LDM. `-l high`는
    재지 않았다.
  - `-D`(블록별로 학습한 사전)는 재지 않았다.
  - 풀기 속도의 제약: aqr의 목표는 200 MB/s 이상이다(`10gb-todo.md`). LZMA류의 풀기는 그보다 느리므로,
    차이를 메우는 방법은 이 제약 안에서 골라야 한다. 비교 상대의 풀기 속도도 같이 잴 것.
- 변환
  - `wrt-recons`가 minify되지 않은 JS에는 걸리고 minify된 162.5 MB에는 걸리지 않았다(이득이 없다고
    판정했는지 볼 것). 단어 사전이 JS 식별자와 키워드에 맞는지.
  - JS 전용: 토큰화(식별자, 문자열, 숫자, 구두점을 스트림으로), 식별자 사전, minifier가 만든 짧은
    이름의 규칙성, 공백과 줄바꿈 규칙. 무손실이어야 하므로 파서는 원문을 바이트 그대로 되돌려야 한다.
  - source map(`.map`)도 함께 들어 있다(OpenMTP asar에 2,002개, 16.6 MB; VS Code asar에 679개, 6.6 MB).
  - `.d.ts`, `.cts`, `.mts`, JSON, CSS, HTML, Python 등 다른 텍스트에도 같은 백엔드가 걸린다.
- 배치
  - 파일 순서: 확장자 먼저(`sort_key`) 대 경로 순서(5절, 2.5%).
  - solid 블록 상한(`-b`)과 블록 안의 문맥 길이. VS Code의 트리에서는 블록을 키워도 거의 같았다.
  - 같거나 거의 같은 파일: node_modules의 같은 패키지 여러 버전, 확장마다 번들된 같은 라이브러리.
- 다른 곳의 JS
  - Chromium `.pak` 안의 gzip, Brotli로 압축된 JS와 HTML(9절의 Brotli).
- 비교 상대: xz -9e, PPMd 말고도 brotli -q 11(큰 윈도우), 문맥 혼합류(paq8, cmix)를 상한으로 재어
  둘 것. zstd의 높은 레벨은 CLAUDE.md대로 재지 않는다.

### 7. 기호 테이블

- strip되지 않은 바이너리에서 strtab과 symtab이 Mach-O의 18–29%(zstd -3)이다.
- 이전의 aqr은 xz 수준이었다. Windows App 본체 arm64 이미지(56.0 MB)에서 두 표(7.10 + 14.91 MB)가
  결과 11.42 MB 중 2.08 MB, Secretive 본체에서 427 KB 중 120 KB였다(표를 0으로 지운 이미지와의 차).

했다(`exe-recons/macho-symtab`, aqr-exe FORMAT.md §S): nlist를 필드별로 나누고, 값은 디버그 맵의
stab(함수마다 `N_BNSYM`, `N_FUN` 둘, `N_ENSYM`)과 앞의 엔트리로 예측하며(함수 크기는 다음 기호
주소로), 이름은 다음 문자열, 같은 값의 이름, 뒤로의 참조로 적는다. `ld64`의 strtab은 외부 기호를
먼저 훑은 첫 사용 순서 그대로여서 `n_strx`는 모두 유도되고, 문자열은 그 순서로 front coding한다.
결과는 aqr-exe README의 Results(Windows App 본체 −6.0%, 앱 −1.9%; Secretive −9.0%, Deskflow −6.0%,
Blender −2.0%).

남은 것:

- lld의 strtab: 꼬리를 공유하고(문자열 안을 가리키는 `n_strx`) 순서도 다르다. Electron Framework의
  것이 슬라이스마다 0.9 MB 남짓, Chromium 프레임워크의 것은 작다. WebRTC.framework(4.4–4.6 MB)는
  외부 기호를 먼저 훑은 순서도, 기호 순서도 아니다.
- 남은 비용의 대부분은 문자열이다(위 이미지에서 front coding 뒤 zstd -7 1.13 MB, 접미사에 xz -9 0.84
  MB). C++와 Swift의 맹글링 구조나 텍스트 쪽 백엔드(6)가 다음이다.
- 외부 기호의 값(이름 순서의 주소)이 기호 표 스트림의 3분의 1이다. 지역 기호와 stab을 먼저 풀면
  이름으로 예측할 수 있을 것이다(재지 않았다).

### 8. `deepmap2`

- `assetutil --info`로 본 `Assets.car` 렌디션의 압축은 `deepmap2`, `lzfse`, `zip`, 없음이다.
- Windows App의 `Assets.car`(72.2 MB)는 거의 `deepmap2` 이미지(71.8 MB)이고, aqr로 65.9 MB에
  머문다. 그 앱 결과의 59%이다. Pages에는 약 4 MB가 있다. 다른 앱에서는 작았다.
- Apple의 비공개 코덱이라 공개 명세가 없다. 리버스 엔지니어링을 할지, CoreUI를 블랙박스
  오라클로만 쓸지 먼저 정해야 한다(LZO 때처럼 원칙이 필요하다). 그 전에 표본을 넓혀 얼마나 흔한지
  본다.

### 9. 보류

- Brotli: Blender의 `Noto Sans CJK Regular.woff2`(11.4 MB, 그대로 저장), Chromium `.pak`의 Brotli
  엔트리(Chrome 15 MB(버전 3벌 합), Discord 3.9 MB). Discord의 `resources.pak` 6.65 MB는 aqr로 줄지
  않는다. `file-formats.md`에서 어려운 쪽으로 분류했다.
- 신경망 가중치: 표본에서 OIDN 하나(46.5 MB)뿐이다.
- Pages의 binary plist 117 MB(언어 디렉토리마다 374개씩)는 aqr 18.4 MB(zstd 30.3 MB)이다. 구조 모델은
  측정을 더 해 보고 정한다. `.cshelpindex` 9.5 MB는 줄지 않는다.
- Chromium `.pak`의 엔트리 표(6바이트 × 엔트리)는 Chrome 13.9 MB, Discord 4.4 MB이다.

## 보존

압축률이 아니라 충실도의 문제이다. `aqr`은 확장 속성(`xattrs`)과 리소스 포크(`forks`)를 저장하고
푼다(spec §xattrs, §fork-streams). 따라서 `com.apple.cs.*`에 둔 Mach-O가 아닌 실행 파일의 서명과
quarantine, provenance 속성이 남는다. 남은 것:

- decmpfs의 투명 압축은 저장 방식이라 보존하지 않는다. 풀면 디스크를 더 쓴다.
