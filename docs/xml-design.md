# XML의 골격과 값 묶음 (aqr-xml)

레코드로 된 XML(위키·Q&A 사이트의 덤프, 지도의 변경분, 서지)을 골격과 문맥별 값 묶음으로 나누어,
묶음마다 그에 맞는 코더가 코딩하게 한다. 형식은 `codecs/aqr-xml/FORMAT.md`가 정하고, 프로토타입의
측정과 코퍼스는 `codecs/aqr-xml/README.md`에 있다. 이 문서는 정한 것과 그 이유, 남은 문제를 적는다.

출발점은 cmix-neif-2.0의 enwik9 전처리기(prep9)의 README다(코드는 GPL이라 읽지 않았다). 그 8단계가
페이지마다의 리비전 정보(id, 시각, 기여자)를 본문에서 빼어 파일 앞의 블록 하나에 모은다. 이를
enwik9에 매이지 않게 일반화하면 XMill(Liefke, Suciu 2000)이 된다: 태그는 골격에, 값은 경로별
컨테이너에.

## 1. 정한 것

### 1.1 모듈은 나누고 합치기만 한다

모듈 `xml-recons`는 골격과 묶음에서 XML을 다시 만들 뿐, 값을 코딩하지 않는다. 각 묶음은 `Kind::Text`인
내용 스트림이다. aqr-compress가 그것을 차례로 다시 압축한다. 숫자나 시각의 열은 `table`(aqr-xsv,
aqr-log)이, 그 밖의 텍스트는 aqr-wrt가 맡고, aqr-wrt는 묶음 전체에 사전 하나를 쓴다.

aqr-jsonl은 숫자를 모듈 안에서 aqr-num으로 코딩하지만 여기서는 그러지 않는다:

- 프로토타입에서 숫자를 앞 값과의 차이로 코딩한 것이, aqr-compress가 같은 묶음을 aqr-log로 코딩한
  것보다 컸다(README, "Prototype"). 열 코딩은 이미 aqr-log·aqr-xsv에 있고, 그쪽의 개선이 그대로 온다.
- 모듈이 작다. 모듈의 바이트는 아카이브마다 드는 비용이다.

다시 볼 때: 묶음이 수백 개를 넘어 스트림마다의 비용(표, 내용 재압축의 고정 비용)이 보일 때. 그때는 작은
숫자 묶음을 모듈 안에서 코딩하는 것을 잰다.

### 1.2 문맥은 두 단계

텍스트의 문맥은 (부모, 원소)이고, 속성값의 문맥은 (원소, 속성)이다(FORMAT §4). 그래서 enwik의
`page/id`, `revision/id`, `contributor/id`가 따로 모이고, Stack Exchange의 `row@Id`, `row@CreationDate`도
그렇다. XMill의 기본은 경로 전체다. 하지만 깊은 문서(treebank는 문장의 구문 트리다)에서는 경로마다
묶음이 생겨 묶음이 너무 많아진다. 두 단계는 프로토타입이 쓴 것이고, 코퍼스에서 다른 깊이와 비교하는
것은 남은 일이다(§3).

### 1.3 골격은 텍스트 그대로

골격은 원문에서 값을 빼고 구조를 특수 바이트 0x01–0x05로 표시한 것이다(FORMAT §5). XML 1.0 문서에는
이 바이트들이 나올 수 없으므로 이스케이프는 드물다.

- 짝이 맞는 끝 태그는 CLOSE 1바이트다.
- 시작 태그는 OPEN 뒤에 원문 그대로 둔다. 모듈은 OPEN과 END 뒤에서만 태그 문법을 읽는다.
- 주석, CDATA, 처리 명령, DOCTYPE은 그냥 바이트다. 모듈이 그 안의 `<`를 알 필요가 없다.

태그 이름 사전이나 구조 스트림처럼 구조를 따로 코딩하지는 않는다. zstd가 골격을 이미 잘 압축한다:
enwik8은 3.5 MB → 19 KB, DBLP는 125 MB → 2.0 MB(전체의 6%)다. 개선 후보로 둔다(§3).

### 1.4 값의 구분은 LF, 아니면 길이

묶음의 값에 LF가 하나도 없으면 값마다 LF로 끝낸다. 있으면 길이를 `lens`에 따로 둔다. 구분자가 NUL이면
aqr-wrt가 텍스트로 받지 않는다(텍스트 아닌 바이트는 1/1000까지). 프로토타입에서 그 탓에 DBLP가
+2.9%였고, LF로 바꾸자 −4.3%가 되었다. 본문처럼 LF가 있는 값은 대개 길어서 길이 값이 적다(enwik8의
본문은 12,345개).

### 1.5 세그먼트

aqr-jsonl처럼 64 MiB 이상의 세그먼트로 자르고, 세그먼트마다 적용이 하나다. 자르는 곳은 열린 원소가
하나 이하가 되는 끝 태그 뒤(레코드의 끝)다. 세그먼트 시작에서 열려 있는 원소의 이름은 params에 둔다.
문맥의 묶음 번호는 세그먼트마다 새로 매긴다.

### 1.6 메모리 계획

계획은 params의 `containers`(묶음 수)와 `depth`(스택의 한계), 입력과 출력의 길이를 따른다. 문맥에서
묶음을 찾는 표는 묶음 수로 크기가 정해지는 해시 표로 한다. 정확한 배치는 모듈을 쓸 때 정하고
`plans_hold`로 확인한다(`docs/arena-design.md`).

## 2. 고르기

aqr-compress의 `table`(`crates/aqr-compress/src/made.rs`)에서 aqr-jsonl과 같은 자리에 둔다. 파일이
XML로 시작하면(BOM, `<?xml`, 또는 `<`와 이름) aqr-xml을 시도한다. 하지만 줄마다 레코드 하나가 속성으로
든 파일(Stack Exchange의 `Votes`·`Badges`, OSM의 변경분)은 aqr-log가 이미 줄 전체를 템플릿과 열로
나누므로, aqr-xml이 이득을 내지 못한다(README의 표: −1%에서 +2%). 그래서 aqr-log와 aqr-xsv 사이를 고르는
`log_or_table`처럼 표본에서 둘을 코딩해 작은 쪽을 고른다.

- 작은 파일은 묶음마다의 비용으로 손해를 본다(`se-coffee`의 `Badges` 1.6 MB가 +22%). 최소 크기는
  코퍼스에서 정한다.
- 표본 비교는 aqr-xml과 aqr-log를 다 코딩해 보는 비용이 든다. 비교는 XML로 시작하는 파일에서만 한다.

## 3. 남은 문제

- **문맥의 깊이**: 두 단계와 세 단계, 경로 전체. 같은 원소 이름을 부모와 상관없이 한 묶음으로 두는
  것도 비교한다(DBLP의 `inproceedings/author`와 `article/author`는 같은 사람들이다).
- **골격의 구조 코딩**: DBLP에서 골격이 6%다. 시작 태그의 속성 목록을 그 원소의 최근 목록 번호로
  부르는 것(aqr-jsonl의 키 목록처럼)을 잰다.
- **모듈 안의 숫자**: §1.1의 재검토 조건.
- **prep9에서 가져오지 않은 것**: revision id 순으로 정렬해 순서를 공짜로 얻는 것, IPv4를 4바이트로
  쓰는 것, 기여자별 주석 번호. 앞의 둘은 enwik9의 구조에 매이고, IPv4는 묶음을 aqr-log가 받으면 주소
  슬롯이 맡는다.

## 4. 단계

1. 모듈과 인코더(FORMAT 확정, 왕복과 손상 입력 테스트, `plans_hold`).
2. aqr-compress에 연결하고 고르기(§2).
3. 코퍼스로 측정(크기, 속도, 최대 메모리)하고 README의 표를 실제 `aqr`의 수치로 바꾼다.
4. §3의 개선을 하나씩 잰다.
