# 10gb 코퍼스: 남은 일

Matt Mahoney의 10 GB 벤치마크(http://mattmahoney.net/dc/10gb.html, 10gb.zpaq를 `~/tmp/10gb`에
푼 것(`/tmp`는 정리 작업이 지운다), 파일 79,431개, 10.00 GB)를 `aqr`로 압축한 결과와 남은 일을 적는다. 끝낸 일의 자세한 경과와
측정은 커밋 메시지와 이 문서의 git 이력에 있다.

## 목표

- **주 목표**: 2.4 GB 이하. 풀기는 200 MB/s 이상, 메모리 2 GB 이하로, 임시 파일 없이 스트리밍하며
  파일 단위 랜덤 액세스를 유지한다. 압축은 10코어 M4에서 40 MB/s 이상이다.
- **확장 목표**: 2.27 GB 이하(Insighter와 동급).
- 견줄 상대는 Insighter(`other-projects.md` 1절)이다. 2026-10-26의 주장으로 2,271,616,726 B, 압축
  42.6 MB/s에 메모리 12.7 GB, 풀기 81.3 MB/s(2.2 GB였던 때)이고, 풀 때 임시 파일이 필요하다.
  압축률은 가깝게 하고 풀기 속도, 메모리, 랜덤 액세스에서 앞서는 자리이다.

## 코퍼스

- 10gb.zpaq는 zpaq 7.15 아카이브(3,701,584,921 B, 버전 하나, 엔트리 83,437개)이다. 모든 코어로
  `zpaq x`가 86 s이다.
- 최상위 디렉토리: `hg19`(인간 참조 유전체 FASTA, 3.24 GB), `benchmarks`(enwik8/9, silesia, gimp 등,
  2.00 GB), `mingw`(gcc 4.4–4.8 배포판 여러 벌, 1.58 GB), `www.mattmahoney.net`(사이트 미러, 1.21 GB),
  `2011`(같은 사이트의 2011년 미러, 0.73 GB), `progs`(Windows 프로그램 폴더, 0.68 GB), `cygwin`(0.50 GB),
  `zeropad`(0으로 채운 파일 하나, 0.05 GB).
- 파일 13,820개(916 MB)가 다른 파일과 바이트 단위로 같다. 대부분 사이트 미러 두 벌 사이이다.
- 다른 파일의 내용을 그대로 담은 것:
  - `enwik9.zip`, `enwik8.zip`, `silesia.zip`(Info-ZIP 2.3 `-9`)은 `benchmarks`의 해당 파일들을 담는다.
    `enwik8`은 `enwik9`의 앞 100 MB이다.
  - `benchmarks/gimp.tar`는 `benchmarks/gimp-2.0.0`을 묶은 것이다.
  - mingw의 `*.tar.lzma` 123개(XZ Utils `-6`)의 멤버는 모두 설치된 파일과 같다.
    `mingw480/x32-4.8.0-release-win32-sjlj-rev1.7z`(37.1 MB)를 풀면 374 MB가 `mingw480` 트리와 같다.
  - `mingw_benchmark.zpaq`(88 MB)는 `mingw44`와 같고, `silesia.zpaq`(48 MB)는 silesia를 담는다.
  - `enwik9.pmd`(184.0 MB)와 `enwik8.pmd`(21.4 MB)는 PPMd var.J(order 10, 256 MB, restore method 1)이다.
- 파일별 zstd -3으로 3% 넘게 줄지 않는 고유 파일은 1.60 GB이다. ZIP류 613 MB, JPEG 173 MB, PNG·GIF
  30 MB 말고는 PPMd 205 MB, ZPAQ 190 MB, LZMA 72 MB, 7z 37 MB, RAR 13 MB, UPX+NSIS 설치 파일 54 MB,
  `benchmarks/simple/w8002`(100 MB, 난수) 등이다.
- RAR 83개(13.4 MB, 같은 파일이 많다)는 aqr-rar가 푼다(2026-11-01). 대부분 오래된 WinRAR의 높은 차수
  PPMd라 따로는 이득이 거의 없다: PPMd 스트림은 level 9에서만 시도하고, 거기서 −1.4%(세 개 채택)이다.
  mid에서는 하나도 채택되지 않는다(LZ 스트림 하나를 분해해 보는 데 압축 5 s).
- 통째로 압축한 기준값: `tar | zstd -3 -T10` 4.68 GB(33 s), `--long=31`을 붙여 4.17 GB, 파일별
  zstd -3(같은 파일 제외) 4.06 GB, zpaq 7.15(10gb.zpaq) 3.70 GB.

## 측정

검증 포함), 둘 다 `--stats --stats=FILE.json`을 켜고 `/usr/bin/time -l`로 쟀다(JSON은
`crates/aqr/cache/10gb/{c,k}L-f6f22f7a-r{1,2}.json`). 각 레벨을 두 번 재어 빠른 쪽을 적었고
괄호는 다른 한 번이다. 시간은 aqr 자신이 찍는 초이다. 측정 전에 `uptime`과 `ps`로 다른 부하가
없음을 확인했다(1코어를 넘는 것은 없었고 `claude` 자신 외에는 1% 안팎).

```
cargo aqr -c -f -L -o ~/tmp/bench10/L.aqr ~/tmp/10gb --stats --stats=...
cargo aqr -K ~/tmp/bench10/L.aqr --stats --stats=...
```

쪽의 것이다. 모든 압축 실행은 79431 파일, 10.00 GB이고 `-K`도 같다.

- 이전(`9e43bca`, 11-04)의 mid는 2,465,370,809 B, 165.7 s, footprint 3.25 GB이고 `-K`는 33.9 s, 2.23 GB였다.
  이번 mid는 +15.9 MB(pe +12.2, lzma +2.7, ar +1.7 MB; 파일별 `archived`를 그때의 JSON과 견준 것),
  압축 footprint 3.25 → 2.54 GB, `-K` 33.9 → 29.1 s이다. 낮은 레벨의 이전(`4abcae6`, 11-05)은 `-2`
  2,707,394,473 B(93.5 s, 14.3 s), `-1` 3,881,155,667 B(29.6 s, 5.5 s), `-0` 8,979,559,362 B(29.6 s,
  4.1 s)이고, 그 앞의 `83097ad`는 2,497,965,328 B이다. `-1`, `-0`의 크기는 그대로이다.
- **`-2`는 3.030 GB로 `4abcae6`보다 +322 MB 커졌다.** `enwik9.zip`(322.59 MB)이 recompress되지 않고
  통째로 들어간다: `--stats`의 fallback이 `zip-recons`가 요구하는 하한 311.82 MiB를 `-2`가 쓰지
  않았다고 한다(`kept: false`, mid는 같은 파일을 132.8 MB로 줄인다). 원인은 보지 않았다.
- `-9`: 압축은 worker가 평균 67.4% 일한다. 56.1–77.8 s에 worker 하나만 돈다(lzma-recons, 하한
  856.75 MiB라 하한에 쓰이지 않고 혼자 돈다). heap 최대 5.20 GB는 예산(2 GB)의 260%이고 그중 5.00 GB를
  zip이 26.6 s에 쥔다. pe가 바이트의 13.1%로 시간의 35.7%를, zip이 7.2%로 29.7%를 쓴다. spill 최대
  1.65 GB. 풀기는 74.0% 일하고, 10.5–12.4 s에 1.6 worker(`enwik9`의 wrt-recons), 한 파일에 오래
  붙는 것은 `silesia.zip` 11.3 s, `tdm-gcc-4.5.0.exe` 10.6 s, `enwik9.zip` 10.4 s이다.
- `-5`(mid): worker 65.8%, heap 최대 2.25 GB(analyze 1.36 GB, 105 s). lzma-recons 하나(37.1 MB,
  856.75 MiB 필요)가 하한에 쓰이지 않는다. pe가 바이트의 13.1%로 시간의 30.6%를, zip이 7.2%로
  21.0%를 쓴다. 풀기는 68.1%이고 6.4–8.4 s(wrt-recons of `enwik9`)와 27.4–29.1 s(rar3-recons of
  `all_HKCC.rar`)에 worker가 1–2개이며 `tdm-gcc-4.5.0.exe` 7.9 s, `gcc-core-4.6.1…tar.lzma` 6.5 s,
  `enwik9.zip` 6.3 s가 오래 간다.
- `-2`: worker 60.3%, pe가 시간의 41.0%. 풀기는 74.3%이고 10.6–12.4 s에 worker 하나
  (`all_HKCC.rar`의 rar3-recons). fallback은 위의 `enwik9.zip` 하나.
- `-1`: worker 48.6%, 걸림돌로 지적되는 것이 없다(`nothing stands out`). `-K`는 83.4%이고 같은 내용의
  `-`(압축되지 않는 파일, 바이트의 11.0%)가 시간의 62.8%를 쓴다.
- `-0`: worker 36.0%, 12.1–13.4 s와 14.3–15.5 s에 worker 하나(write), 3.0–3.9 s에 1.2개. 두 번째
  실행은 19.9 s(CPU는 같고 sys가 25.2 → 16.4 s로 달랐다)로 편차가 크다. `-K`는 80.0%이다.
- I/O 한계를 다시 보았다. `--stats` JSON을 스레드·초로 합산하면 `read`는 `-1`에 17.4, `-0`에 23.0
  스레드·초로, 11-05에 적은 약 80보다 훨씬 작다(세는 방법이 달랐을 수 있다; 그때의 값은 다시 맞춰 보지
  않았다). 그래도 압축의 CPU 시간이 `-1`은 user 63.9 + sys 27.0 = 90.9 s, `-0`은 7.9 + 25.2 = 33.1 s로
  10코어·19.4/15.5 s의 47%, 21%뿐이고 `-0`의 시간이 sys(읽기)에 따라 15.5–19.9 s로 흔들리므로
  `-1`/`-0`의 압축은 여전히 입력 읽기가 정한다고 본다(별표 유지). `-K`는 `-0`이 CPU 6.5 s(user 4.5 +
  sys 1.9)를 3.3 s 벽시계에 쓰고 worker는 80% 일한다고 찍으므로, 11-05와 같이 매핑된 아카이브의 페이지를
  기다린다(별표 유지). `-1`의 `-K`도 CPU 10.3 s를 4.7 s에 쓰는데 worker는 83%라 기다림이 섞인다.
  `-2`의 `-K`는 CPU 65 s를 12.4 s에 써서(5.2코어) 읽기에 묶이지 않는다.

## 종류별

커밋 `ed0869f`(2,599,590,226 B, `-v`의 로그)이다. 그 뒤 `7c73922`가 `.tar.lzma`의 퇴행을 고쳐 −15.9 MB가
되었다(6번). 같은 내용 파일 13,820개는 한 번만 셌다. 종류는 경로, 확장자와 탐지한 포맷으로 나눴고,

      형식의 content로 자르며(그 파일들은 tar의 멤버처럼 설치 파일과 같은 깊이), `together`가 블록과
      그 멤버(tarball은 풀어서, ZIP은 엔트리)로 트리와 잇는다.
    - 10gb(M4, level mid): 2,482,993,970 → 2,464,914,978 B, 명령어 8.024 → 8.016 T, 풀기 40.8 s. 두
      설치 파일과 두 트리의 몫이 60.45 → 35.28 MB이다. 두 트리만(194.4 MB, 한 배치)으로는 설치 파일이
      +19.1 → +12.4 MB이고, 블록을 파일로 따로 두면 +11.2 MB였다.
    - 남은 것: 두 설치 파일의 w32api `include` tar.gz(1.63 MB씩)는 aqr-flate가 받지 않아 그대로 남는다
      (까닭은 보지 않았다). `together`가 gzip 파일을 trailer의 CRC(tar 전체)로만 잇는 것은 NSIS 밖의
      `.tar.gz`에도 해당한다.
    - 나머지 8개(언인스톨러, Firefox의 helper)는 모두 0.9 MB 밑이고(합쳐 1.7 MB), 압축된 것은 NSIS의
      LZMA solid 데이터 수십 KB씩이라 재현할 값어치가 없다.

지금 2.558 GB이다(2026-10-30, aqr-ppmd 뒤 2,557,815,082 B). 주 목표 2.4 GB까지 158 MB가 남는다.
확실한 편인 것(2번의 에뮬레이션, 3번, 4번, 6번의 나머지, 8번의 나머지)이 합쳐 130 MB 남짓이고, 그 밖에는 7번(ZPAQ)이 크다. PPMd 없이는 확장 목표에
못 미친다.

## 메모리

- 압축의 최대는 enwik 묶음(1.46 GB) 배치이다(`ffb9393`에서 2.96–3.49 GB). 다른 배치는 2.7 GB 밑이다.
  남은 것: 검증의 `enwik9` leaf는 두 블록에 걸친 부호화된 텍스트를 이어 붙인 사본(503 MB)과 텍스트
  (1 GB)를 갖는다. 미리 평가는 `enwik9.zip`의 inflate된 1 GB를 flate-set의 입력으로 갖는다. macOS
  malloc의 1 MiB 밑 블록 조각(0.2–0.4 GB)도 있다.
  - 크고 적용이 꼭대기에만 있는 식을 모두 미리 평가하지 않으면 0.5 GB 남짓 줄지만, hg19가 29.6 →
    33.4 s로 느려진다(FASTA 디코딩이 놀던 코어에서 검증 단계로 옮겨 간다).
- 풀기(`921778d`에서 2.60 GB, 목표 2 GB): `aqr`는 leaf를 무게(식이 말하는, 한꺼번에 드는 가장 많은
  바이트, 적용의 메모리 한도를 넣어)의 합이 프로세스의 budget(`-M`, 기본 2 GB; 검증도 같은 것을 쓴다) 안일
  때만 동시에 푼다(`Archive::set_budget`, `aqr_common::budget`). budget은 신고된 무게와 실제 heap(64 KiB 이상
  블록) 중 큰 쪽을 보며, 압축의 batch와 LZMA match finder도 같은 budget에서 들어간다. 첫 leaf가 기다리는 동안에는 뒤의 leaf가
  예산 안에서 앞지른다(`Gate`).
  - 무게가 가장 큰 leaf는 `enwik9.zip`과 `enwik9`(각 3.46 GB), `mingw480`의 7z(2.46 GB), 그다음
    1.87 GB이다. 예산을 넘는 leaf는 아무것도 돌지 않을 때 혼자 들어가고, 도는 동안에는 앞지를 자리도
    없다. 무게는 크게 잡혔지만 그 leaf가 혼자 돌 때의 실제 heap도 2.0–2.2 GB(`--stats`)라서, 무게를
    고쳐도 2 GB 안에서 옆에 들일 자리는 거의 없다. 줄이려면 leaf 자체가 덜 들어야 한다(1 GB 텍스트와
    0.5 GB 코드된 텍스트를 함께 갖는다).
  - `enwik9`의 wrt 디코딩은 `enwik9`와 `enwik9.zip`의 leaf가 따로 한 번씩 한다(leaf는 다른 leaf의
    출력을 못 쓴다). `921778d`부터 각각 0.35 s라 크지 않다.

## 따라가지 않는 것

- GB 단위의 solid와 임시 파일을 쓰는 풀기: R5, R6과 충돌한다. 텍스트를 16 MiB 프레임으로 나눈
  손해는 solid 대비 4%이다(zstd -19 `--long`, 80.0 → 83.2 MB).
- FastLZMA2나 PPMd 백엔드: 같은 텍스트에서 zstd -19 `--long`(80.0 MB)과 xz -6(78.8 MB)의 차이가
  1.5%이다. 병목은 저장 계층이 아니라 레벨과 묶음이다.
- solid JPEG: 이 코퍼스에서는 이득이 없다.
- LZMA와 PPMd 인코더의 재현(5번, 6번).
