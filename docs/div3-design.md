# DIV3 (MS-MPEG4 v3)와 AVI의 무손실 재압축

**[구현]** AVI 안의 DivX 3 영상(`DIV3`)과 AC-3 음성을 파싱해 문맥 모델로 다시 부호화한다
(`aqr-jpeg`와 같은 방식). 코드는 `codecs/aqr-div3`(영상, AVI), `codecs/aqr-ac3`(음성),
`crates/aqr-walk`(공유: 한 번 쓰는 문법 걷기 `Io`, 구간 부호화기, 해시 모델)에 있고, 형식은 각
`FORMAT.md`/README가 규정한다 (여기서 되풀이하지 않는다). 모듈은 `div3-recons`(2), `ac3-recons`(1),
둘 다 part module. 끝낸 일의 경과는 git 이력에 있다.

## 테이블 확보 방법 (결정: 2026-11-11)

MS-MPEG4 v3에는 공개 명세가 없고 VLC 테이블(DC, CBP, 계수 6벌, 움직임 벡터 2벌 등)이 필수다. 공개
구현은 LGPL이라 테이블을 복사할 수 없다 (PD 정책). 그래서 **설치된 ffmpeg 디코더를 블랙박스
오라클로 탐침**해 prefix 코드를 사실(데이터)로 역추출했다. 소스는 읽지 않는다. 도구는
`scripts/div3-probe/`(PyAV로 프레임당 약 1 ms; 조작한 비트열의 작은 AVI를 디코딩해 화소에서 부호의
뜻을 읽음), 코드 생성은 `scripts/div3-gen.py`. 표를 얻은 과정의 요약과 함정:

- 부호 트리 걷기의 잎 판정: 접두사 뒤에 run 0 기호를 붙여 블록을 끝낸 뒤, 다음 비트를 뒤집었을 때
  차이가 DCT 기저 하나(잔차 ≤ 2.0)인지 본다. 놓친 잎은 가짜 잎을 만들어 폭발하므로 재현율이
  중요하다. 길이에 따른 Kraft 절단은 진짜 긴 부호를 잘라 내므로 쓰지 않는다 (시도했고 버렸다).
- ffmpeg 인코더는 I 프레임에서 `rl=2, rlc=1, dc=1`만 쓴다 (정답 검증용으로만 쓸 수 있다). 인코더의
  양자화가 요청한 진폭과 다른 레벨을 내므로 레벨은 디코더로 읽어야 한다. 인코더가 만든 문자열의
  접두사만으로는 CBP 표가 완성되지 않았다 (한 번 틀린 표를 얻음: 부호 길이를 꼬리 문자열 맞춤으로
  다시 구해 해결).
- **함정**: 상태를 가진 디코더 하나로 패킷을 차례로 디코드하면 실패한 I 프레임이 이전 화면을 이어받아
  (오류 은닉) 같은 출력으로 보인다. 출력의 같음을 쓰는 검사는 패킷마다 새 디코더로 한다.
- 평평한 참조에서는 P 프레임의 움직임 부호 길이를 구별할 수 없다 (질감 있는 참조가 필요).
- 마지막 검증은 파싱이 프레임 끝에서 정확히 끝나는지이다.

알아낸 문법 중 코드/FORMAT.md에서 놓치기 쉬운 것: inter 블록은 색차 intra AC 표와 같은 표를 쓰고(6개
AC 표는 사실 휘도 intra 3 + inter/색차 3), P의 MB 종류 부호는 I 프레임과 달리 계수 플래그를 이웃으로
예측하지 않는다. 휘도 DC의 평균은 127.5이다.

## 남은 것

(README의 "Left"와 같다.)

- 파싱 실패: P 프레임의 약 0.5% (늘 MV 표 0)는 그대로 저장된다. 표에 빠진 부호가 있는 듯하다.
- q=2 P 프레임이 q 3–5와 같은 표를 쓰는지 미확인.
- 이웃 블록의 계수와 예측 MV 문맥, 문맥 혼합 (이득은 더 크나 속도가 든다), SIMD.
- DivX 3 문법만 탐침했다. 다른 fourcc(`mp43`, `div4`…)나 다른 컨테이너의 AC-3는 안 했다.
