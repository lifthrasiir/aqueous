# DIV3 (MS-MPEG4 v3)와 AVI의 무손실 재압축

AVI 안의 DivX 3 영상(`DIV3`)과 AC-3 음성을 파싱해 문맥 모델로 다시 부호화하는 계획.
`aqr-jpeg`와 같은 방식(허프만/VLC로 부호화된 계수를 산술 부호화로 바꾸고, 비트 단위로
같은 스트림을 재구성)이며, 아직 구현이 없다. 측정은 모두 추정이 아니라 아래 표의 실측만 적었다.

## 첫 표본

`mari.avi` (CD 이미지에서 꺼낸, 끝이 잘린 영화; 코퍼스 `F:\Data\aqr-corpus\aqr-div3`,
측정 전용): 640x352, 23.976 fps, Nandub 1.0rc2가 만든 것.

| 스트림 | 내용 | 크기 | 비중 |
|---|---|---|---|
| `00dc` | DIV3 (I/P 프레임, B 없음) | 468.8 MB, 103,584 청크 | 69% |
| `01wb` | AC-3 5.1, 384 kbps | 207.4 MB, 103,584 청크 | 31% |

`aqr -c`는 이 이미지를 100.0%로 저장한다 (포맷 처리가 없음). 컨테이너(JUNK, 청크 헤더)는
무시할 크기.

## 구성 요소

1. AVI 디먹서: `movi`의 청크를 스트림별로 나누고 나머지(헤더, `idx1`, JUNK, 순서)는 레코드로.
2. DIV3: 프레임 파싱, 계수/움직임 벡터를 문맥 모델로 재부호화, 동일 비트열 재구성.
3. AC-3: 공개 명세(ATSC A/52)로 구현할 수 있다. 비교 오라클은 ffmpeg.

## DIV3 테이블 확보 (결정: 2026-11-11)

MS-MPEG4 v3에는 공개 명세가 없고, VLC 테이블(DC, CBP, 계수 6벌, 움직임 벡터 2벌 등)이
구현에 필수다. 공개 구현은 LGPL이라 테이블을 복사할 수 없다 (PD 정책). 그래서
**설치된 ffmpeg 디코더를 블랙박스 오라클로 탐침**해 prefix 코드를 사실(데이터)로 역추출한다.
소스는 읽지 않는다.

탐침의 원리: 조작한 비트열을 담은 작은 AVI(`scripts/div3-probe/avi.py`)를 ffmpeg로 디코딩해
나온 픽셀(DC 평균, 단일 계수의 IDCT 패턴)에서 부호의 뜻을 읽는다. 16x16 I 프레임이
오라클로 디코딩됨은 확인했다. 확인한 I 프레임 머리는
`00` + qscale(5) + `10111` + rl_chroma(0/10/11) + rl(0/10/11) + dc_table(1)이다.

## 순서

1. 탐침: DC → CBP → 계수 표(intra/inter) → 움직임 벡터 → P 프레임의 MB 종류.
2. 파서 + 같은 비트열 재작성기(탐침한 표로), 실제 프레임 전부에서 왕복 확인.
3. 문맥 모델, 크기 측정 (목표: 영상 5% 이상).
4. AVI 디먹서와 공식(formula) 연결, AC-3.

## 진행 상황 (2026-11-11)

`scripts/div3-probe/`의 도구들이 ffmpeg 디코더(PyAV, 프로세스 없이 프레임당 약 1 ms)를 블랙박스로
써서 표를 뽑는다. 아직 코덱 코드는 없다.

| 표 | 상태 | 파일 |
|---|---|---|
| DC (휘도/색차 × dc_table 0/1) | 끝. 119 레벨 + escape(뒤에 8비트), Kraft 합 1 | `dc_raw.json` |
| AC, 휘도 intra, `rl` 0/1/2 | 걷기 끝. 123/185/101개 기호, ESC 접두사 `0010110`/`001001010`/`0000011`. 각 표에 쓰이지 않는 부호 구멍이 조금 있다 (디코드 오류) | `ac_labeled_rl*.json` |
| AC, 색차 intra | 휘도와 **다른** 표다 (같은 번호끼리 17/75만 일치). 아직 안 걷음 | |
| CBP (I 프레임 mb_i) | 일부 (64개 중 16개). 색차 쪽 꼬리 가정이 틀려 막힘 | `cbp_i_*.json` |
| P 프레임: 머리, MB 종류, MV 표 2개, inter AC | 시작 전 | |
| 스캔 순서, escape 1/2/3 문법 | 시작 전 | |

방법에서 알게 된 것:

- 부호 트리 걷기: 접두사 `p`가 완전한 부호인지는 `p`+`0`/`1`+나머지 두 디코드의 차이가
  DCT 기저 하나(반올림 허용, 잔차 최대 1.05)이고 두 출력의 그 계수 합이 0인지로 본다
  (`ac_probe.py::flip_leaf`). 같은 run의 두 레벨은 부호가 같아서 걸러진다. 놓친 잎은 그 아래에
  가짜 잎을 만들어 폭발하므로 재현율이 중요하다 (K=24 나머지, 30% 이상이면 통과).
- ffmpeg 인코더(`enc.py`)는 I 프레임에서 늘 `rl=2, rlc=1, dc=1`만 쓰고, 계수 하나짜리 프레임으로
  (위치, 레벨)의 부호를 그대로 준다. 검증용 정답으로 쓸 수 있다 (`enc_ac.py`). 다른 표 번호는
  디코더 탐침으로만 얻는다.
- 휘도 DC의 평균은 127.5이다 (인코더 프레임과 화소가 1씩 다르다). 비교는 평균을 뺀 모양으로 한다.
- 실제 파일(`mari.avi`)의 처음 6000프레임: I 43개(q=4/5, `rl/rlc/dc`의 모든 조합이 나옴), P
  5957개(q=2). P가 99%이므로 P 프레임 문법이 본체다.
- 같은 비트열의 파싱이 프레임 끝에서 정확히 끝나는지가 마지막 검증이다 (그러려면 표가 모두 필요).

### 갱신 (같은 날, 이어서)

- 색차 intra AC 표 `rlc` 0/1/2 (148/168/162개, ESC `000001101`/`101101001`/`00000110`)를 걷고 라벨했다
  (`ac_chroma.py`, `ac_label_c.py`).
- 스캔 순서: 부호 쌍으로 푼 결과 지그재그 (대각선, 시작 `(0,1),(1,0),(2,0),(1,1),(0,2),(0,3)…`; 휘도
  블록 3 기준, 다른 DC 예측 방향은 전치) (`scan.py`, `scan_idx_block3.json`).
- I 프레임 CBP: 64개 부호를 얻었으나(`cbp_i_codes.json`) **틀리다**. 실제 프레임 191의 MB0 `0011100110`이
  표에 없고, 다른 두 값(V=58, 59)의 부호를 그 부호로 바꿔도 같은 화소가 나온다. 원인은 모르겠다
  (ac_pred가 코딩 안 된 블록을 평탄하지 않게 만드는 것과, 계수 플래그가 이웃 예측과 XOR되는 것이
  탐침의 "평탄도 = 플래그" 가정을 흐리는 것이 의심된다). 이 표는 평탄도가 아닌 다른 관측으로 다시 뽑아야 한다.
- `div3.py`는 I 프레임 파서의 프로토타입이다. 프레임 0은 끝까지 파싱되어 남는 비트가 23이다
  (확장 머리 17 + 패딩, 기대대로). 이는 DC 표, 색차/휘도 AC 표, escape 문법 가정, ac_pred 위치가
  맞다는 첫 증거다. 프레임 52는 AC 표의 쓰이지 않는 구멍 근처 부호(`0010111001010`)에서, 191과 215는
  CBP에서 막힌다.

### 갱신 2: CBP에 대해 알아낸 것, 그리고 함정

- **함정**: `fast.Dec`은 상태를 가진 디코더 하나로 패킷을 차례로 디코드한다. 실패한 I 프레임은 이전 화면을
  이어받아(오류 은닉) "같은 출력"으로 보일 수 있다. 출력의 같음을 쓰는 검사는 패킷마다 `Dec.new()`로
  디코더를 새로 만들어야 한다 (프레임당 약 0.03 ms 더). DC/AC 표 걷기는 오류를 `bad`로 걸러서 영향이
  작았고, 실제 프레임 0의 파싱으로 확인되었다.
- 실제 I 프레임 669개의 MB0 앞 16비트 중 74%만 `cbp_i_codes.json`의 부호와 맞는다. 안 맞는 것은 이 표가
  "비어 있다"고 한 구간(`0101001`, `0101011`, `0011100010`, `0000110001`, …)이다. 그 구간의 부호를
  디코더가 받아들이고, 블록 3 같은 한 블록의 플래그만 다음 비트로 갈린다. 즉 **인코더가 만든 64개 문자열의
  접두사로는 표 전체가 안 나오고**, `V → 부호`가 한 가지가 아니거나 표가 64개보다 크다. 다음 시도는
  실제 프레임의 MB0 접두사를 모아 (669개) 부호 트리를 데이터에서 직접 세우고, 디코더로 플래그를 확인하는 것이다.

### 갱신 3

- I 프레임 CBP: 인코더 문자열에서 `부호 + (ac_pred 0) + 영(0) DC + 기준 AC + 확장 머리 + 패딩`의 꼬리를
  문자열로 맞춰 부호 길이를 구했다 (`cbp_i_codes2.json`: 64개, 접두사 무충돌, Kraft 합 정확히 1).
  이전 표(`cbp_i_codes.json`)는 폐기. 이 표로 실제 I 프레임 669개를 파싱하면 22개가 끝까지 맞는다
  (대부분 작은 프레임). 실패는 AC에서 난다: `run past block` 261, 그리고 `000000000xxx`로 시작하는 부호
  (AC 표의 9개 영 구간)에서 막힌다.
- AC 표 걷기의 잎 판정을 고쳤다: 뒤에 알려진 마지막(last=1) 기호를 붙여 블록이 깨끗이 끝나게 한다
  (`ac_probe.py::flip_leaf_t`). 표별 기호 수 105-184, 중복 제거와 Kraft 절단 (`ac_label2.py`).
  하지만 인코더가 만든 32x32 잡음 프레임(정답 소비량을 아는)에서 파싱이 17/60만 맞는다 — 표에 빠진 깊은
  부호(예: rl2의 `00001110…` 구간)와 거짓 잎이 남아 있다.
- 인코더로 (run, level, last)를 정확히 얻는 시도(`enc_table.py`): 인코더의 양자화가 요청한 진폭과 다른 레벨을
  내기 때문에 디코더로 실제 레벨을 읽어야 하고, 그래도 rl2는 74개, 색차 rlc1은 119개 부호밖에 안 나왔다
  (Kraft 0.82/0.78). 표를 완성하려면 이 방법의 빠진 기호를 걷기 결과와 맞대어 채워야 한다.
- 다음에 할 일 (순서대로): (1) rl2/rlc1 표를 인코더 + 걷기로 완성하고 잡음 프레임 파싱을 100%로,
  (2) 다른 표 번호에 같은 걷기를 적용, (3) 실제 I 프레임 파싱 100%, (4) P 프레임.

### 갱신 4: I 프레임 문법이 끝났다

`div3.py`의 `parse_i`가 mari.avi의 I 프레임 669개를 **전부** 끝까지 파싱한다 (남는 비트 17–24 = 확장 머리 +
패딩; `rl/rlc/dc` 12가지 조합 모두). 인코더가 만든 32x32 잡음 프레임 60개도 전부 맞는다. 알아낸 문법:

- 머리: 종류(2) q(5) 조각코드(5, 0x17) rlc(012) rl(012) dc(1). MB마다 CBP 부호(`cbp_i_codes2.json`; 값은
  첫 MB의 계수 플래그이고, 심볼 = 플래그 xor 예측; 예측 `pred = (b == c) ? a : c`, a=왼쪽 b=왼쪽위 c=위),
  ac_pred(1), 블록 6개: DC(휘도 0–3 / 색차 4–5, dc 표 0/1; 119 레벨 + escape(8비트); 0이 아니면 부호 1),
  코딩된 블록이면 AC.
- AC: 표 `ac_labeled_{rl0,rl1,rl2,c0,c1,c2}.json` (휘도는 `rl`, 색차는 `rlc`); ESC 접두사 휘도 `0010110`/
  `001001010`/`0000011`, 색차 `000001101`/`101101001`/`00000110`. ESC 뒤 1비트: `1` = esc1
  (보통 부호 + `level += max_level[last][run]`), `01` = esc2 (보통 부호 + `run += max_run[last][level]`,
  **+1 없음**), `00` = esc3 (last 1, run 6, level 부호 있는 8비트; level 길이 필드 없음). 보통 부호/esc1/esc2
  뒤에는 부호 1비트.
- 스캔은 지그재그이고 run은 그 순서의 색인에서 1을 뺀 값 (`IDX`).
- 표를 얻은 방법의 교훈: 잎 판정은 "뒤에 run 0 기호를 붙여 블록을 끝낸 뒤, 접두사 다음 비트를 뒤집었을 때 차이가
  기저 하나(잔차 ≤ 2.0)"이며, 인코더가 쓰는 두 표(rl2, rlc1)의 정확한 부호 74/119개와 모두 일치한다. 길이에 따른
  Kraft 절단은 진짜 긴 부호를 잘라 내므로 쓰지 않는다.

남은 것: P 프레임 (머리: `use_skip(1) rl(012) dc(1) mv(1)`로 보이며 인코더 프레임에서 확인; MB: skip 비트,
mb_non_intra 부호, 움직임 벡터 표 2개, inter AC 표, P 안의 intra MB), 그리고 그 위의 모델.

### 갱신 5: P 프레임 시작

인코더로 찍은 P 프레임 (`enc_p.py`, 질감 있는 참조 + 0 움직임)에서:

- 머리: 종류 `01`, q(5), use_skip(1), rl(012), dc(1), mv(1). 이어서 MB마다 skip 비트(1 = 건너뜀).
  참조와 같은 프레임은 MB가 모두 skip이라 머리 12비트 + skip 비트만 있다 (2바이트).
- 코딩된 inter MB(블록 3만): `skip 0` + `11100`(MB 종류+CBP 부호와 움직임 (0,0) 부호가 합쳐 5비트) + AC.
  비트 뒤집기 민감도로 AC 시작을 찾았다 (`p_cbp.py`, `p_ac.py`). 평평한 참조에서는 움직임 부호의 길이를
  구별할 수 없어 질감 있는 참조가 필요하다 (평평하면 앞의 비트 하나가 움직임 부호에 흡수되어 가짜 잎이 생김).
- inter AC 표는 intra와 **다르다**: (run 0, level 1, last 1)이 `001111`+부호 (intra rl2는 `0111`). 인코더가
  내는 level 2 이상은 ESC (`0000000`…)로 보이며 구조는 intra와 다르다.
- `p_ac.py`가 같은 잎 판정(뒤집기 + 뒤에 run 0 기호)으로 inter 표를 걷지만 접두사 `0111…` 아래가 폭발한다
  (미해결 9663). 잎 판정에서 위치 (0,0)을 제외했고, 참조 예측을 빼서 부호 합을 본다.

남은 일 (P): inter AC 표 걷기 마무리(ESC 접두사 식별, 폭발 원인), mb_non_intra 표(skip 아닌 MB의 종류+CBP; intra MB 포함),
움직임 벡터 표 2개, P 안의 intra MB, 그 뒤에 실제 P 프레임 파싱 검증.
