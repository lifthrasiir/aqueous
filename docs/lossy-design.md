# 동치 손실 압축(`--lossy`) 설계

Aqueous는 기본적으로 모든 파일을 바이트 단위로 되돌린다. 이 문서는 재압축기가 남기는 기록 가운데 **그 파일을 읽는
어떤 프로그램도 신경 쓰지 않는 정보**를 버리고, 다르지만 동치인 파일을 내보내는 모드를 다룬다. 화질이나 음질을 깎는
보통의 손실 압축과 달리 읽는 쪽이 보는 내용은 바뀌지 않는다. 예: ZIP 항목의 DEFLATE 스트림을 정해진 인코더로 다시
만들고 컨테이너를 다시 쓴다. Minecraft region의 빈 섹터를 0으로 채운다.

구현은 `crates/aqr-compress/src/lossy/`(모듈 문서가 구조와 포맷별 재작성기를 설명한다)와 aqr의 `--lossy`이다. 끝낸
일의 경과는 git 이력에 있다. 상태 표기는 `docs/xform-design.md`와 같다. 이 문서는 구현된 것의 근거와 남은 일만 적는다.

---

## 1. 정의와 원칙

**동치.** 포맷마다 그 포맷을 읽는 프로그램이 보는 것을 *뷰*(view)라고 정의한다. 압축기는 입력 X 대신 R을 아카이브에
넣을 수 있고, 조건은 view(R) = view(X)이다. 아카이브는 R을 바이트 단위로 되돌리고(명세와 디코더는 손대지 않는다), 검증도
R을 기준으로 한다. 뷰의 예: ZIP은 항목의 순서, 이름, 메타데이터, 방식, 풀린 데이터, 주석. PNG는 청크와 IDAT를 이어
inflate해 필터를 되돌린 픽셀. Minecraft region은 칸마다 (타임스탬프, 압축 방식, 풀린 NBT). SQLite는 페이지의 셀과
b-tree 구조(빈 공간 제외). 파일 시스템은 파일 트리, 메타데이터, 내용, 할당된 메타데이터 블록.

**원칙.**

1. **읽는 쪽이 보는 것은 바꾸지 않는다.** 픽셀, 샘플, 텍스트, 메타데이터(EXIF, 타임스탬프, uid)는 그대로 둔다(§7).
2. **파일 전체를 이해할 때만 한다.** 바뀌는 바이트를 가리키는 크기, 오프셋, 체크섬을 모두 다시 쓸 수 있어야 한다. 모르는
   데이터 안에서 스캔으로 찾은 스트림(`scanning.rs`, TIFF 안의 SOI, SQLite blob 안의 zstd 프레임)은 길이가 바뀌면 모르는
   참조가 깨지므로 하지 않는다.
3. **명시적으로 고른다.** 기본값은 무손실이다. 손실의 종류는 이름으로 고르고, 지워진 데이터를 없애는 종류(`slack`)는
   따로 골라야만 한다.
4. **서명은 건드리지 않는다**(§5.2).
5. **실패를 숨기지 않는다.** 동치 검사를 통과하지 못한 파일은 무손실로 저장하고 알린다. 손실로 바뀐 파일은 아카이브에
   표시가 남는다(§4.1).
6. **이득이 있을 때만 쓴다.** 아카이브에서 차지하는 바이트가 X의 크기 이상이면 X로 되돌린다(§6.2).

## 2. 명령행

`aqr -c --lossy=coding,slack -o out.aqr inputs...` (`--lossy SPEC`도 된다.)

- `CLASS`는 `coding`, `slack`, `layout`, `all`. `CLASS:FORMAT[+FORMAT...]`로 포맷을 좁힌다(`coding:zip+png`). 포맷 이름은
  `formats.rs`의 이름. 값 없는 `--lossy`는 없다 **[확정]**. 짧은 옵션은 없다. 압축할 때만 쓴다(`-d`, `-t`, `-K`, `-I`와
  함께면 오류). `-A`와 함께 쓸 수 없다(`-A`는 장기 보존용) **[확정]**.
- `--no-check`는 아카이브를 풀어 보는 검증만 끈다. 동치 검사(§4.2)는 끄지 않는다.
- `-a`/`-s`: 바뀐 파일은 크기와 수정 시각으로 찾으므로 손실로 넣은 파일은 표시의 원본 크기와 비교한다.
- `--stats`: 종류와 포맷별 손실 파일 수, 줄어든 바이트, 동치 검사에 실패해 무손실로 돌아간 파일.

| 종류 | 하는 일 | 잃는 것 |
|---|---|---|
| `coding` | 압축 스트림을 정해진 인코더로 다시 만든다. 컨테이너의 크기, 오프셋, 압축된 바이트의 체크섬은 다시 쓴다 | 원본 인코더의 흔적 |
| `slack` | 구조가 가리키지 않는 바이트(빈 섹터, 빈 페이지, 할당되지 않은 클러스터, 패딩 꼬리)를 제자리에서 0으로 채운다 | 지워진 데이터, 복구와 포렌식 재료 |
| `layout` | 구조를 다시 배치한다(빈 칸 압축, 페이지 조각 모음, 안 쓰이는 옛 리비전 제거). 오프셋을 다시 쓴다 | `slack`과 같고, 배치가 바뀐다. **아직 없다** |

## 3. 구조: 정규형 R을 만들고 그대로 압축한다

손실 압축기는 입력 X를 받아 R(view(R) = view(X))을 만들고, R을 지금의 무손실 경로로 압축한다.

**방법 A(구현): 다시 쓰고 무손실로 압축.** X를 네이티브로 R로 다시 쓰고(재인코딩, 컨테이너 수정), R을 만드는 인코더를 aqr가
*정확히 예측하는 것*으로 골라 R의 기록이 거의 0이 되게 한다. 새 모듈도 새 식의 모양도 필요 없다. DEFLATE는
`aqr_flate::zlib::compress`(zlib 1.3.1과 바이트 단위로 같고 aqr-flate가 약 10바이트로 재현), LZMA는 `aqr_lzma::canonical`
(§6.2). 비용은 인코딩이 두 번이라는 것(다시 쓸 때와 R을 쪼갤 때의 parse).

**방법 B(미구현): 내용에서 바로 식을 만든다.** 재압축기가 내용만 넣고 풀 때 정규 인코더 모듈이 스트림을 만드는 식을 낸다.
방법 A가 듣지 않는 곳에 필요하다. 특히 aqr-png는 무손실 경로가 zlib 에뮬레이션이 아니라 원본의 LZ77 토큰을 남기므로
(에뮬레이션은 1–20 MB/s로 느리다, aqr-png FORMAT.md "Design notes"의 "Why the LZ77 parse is kept") R을 다시 넣어도 토큰 기록이 남는다. 픽셀에서
바로 식을 만들어야 이득이 난다.

**정규 인코더의 선택.** `coding`의 R은 원본보다 클 수 있다(7-Zip ultra의 LZMA, zopfli, zlib 9를 빠른 인코더로 다시 만들
때). 등급은 사용자가 고르지 않고 하나로 고정하며, 풀어 낸 파일이 원본과 비슷한 크기가 되는 쪽을 택한다(DEFLATE는 zlib
레벨 6: `store`는 훨씬 커지고 `fast`(레벨 1, 약 330 MB/s)는 조금 커진다). 원본의 방식은 지킨다(stored는 stored로).
**[확정]**

## 4. 아카이브와 검증

### 4.1 표시: 항목 메타데이터의 사용자 정의 키 [구현]

손실 표시는 aqr만의 정보이므로 명세의 키가 아니라 `aqr-entry-extra`의 **문자열 키**로 둔다(§4.3). **[확정]**

```cddl
aqr-entry-lossy = (
  ? "org.mearie.aqr.lossy" => {
    0 => [+ tstr],     ; classes: "coding", "slack", "layout"
    1 => uint,         ; size: 원본 X의 크기
    ? 2 => #6.18539(bstr .size 32),  ; hash: 원본 X의 SHA-512/256
  }
)
```

모르는 디코더는 이 키를 무시하고 R을 풀어도 맞다. `-t -v`, `-I`, `--json`은 손실 항목을 표시한다. `hash`(COSE 알고리즘 −17을
RFC 9054의 방식으로 18556 + (−17) = 18539 태그, 키 2의 다른 태그는 읽을 때 건너뜀)는 "이 파일이 그때의 원본과 같은가"를
확인하는 데 쓴다(나중의 `--diff`). 같은 X는 언제나 같은 R이 되므로 중복 제거는 R 사이에서 그대로 된다. 코드는 `lossy/mod.rs`의
`Mark`.

### 4.2 검증: 두 단계 [구현]

1. **R에 대한 무손실 검증**: 지금의 검증(`crates/aqr-compress/src/verify.rs`)이 기준만 X에서 R로 바뀐다.
2. **동치 검사**(`lossy/check.rs`): view(R) = view(X)를 **독립된 코드**로 확인한다(R을 만든 코드로 검사하면 같은 버그를 함께
   지나친다. `docs/xform-design.md` §6과 같은 이유). DEFLATE는 aqr-flate가 아닌 flate2(zlib-rs), LZMA는 liblzma, 컨테이너는 직접
   쓴 파서로 비교한다. 실패한 파일은 X로 넣고 항상 알린다.
   `slack`은 독립 검사가 어렵다(파일 시스템의 비트맵을 잘못 읽으면 같은 파서의 뷰에서도 살아 있는 블록이 빠질 수 있다). 그래서
   (a) 비트맵이 비었다고 하고 (b) 파싱한 어떤 구조도 가리키지 않는 바이트만 건드리며, 시험은 실제 도구로 한다(`sqlite3
   integrity_check`와 `.dump` 비교, `fsck_msdos`/`fsck_exfat`/`fsck_hfs`, `e2fsck -fn`, `ntfsfix -n`, olefile, `llvm-pdbutil`).

방법 B가 구현되면 사전 검증이 식을 평가하는 출력에 뷰 계산을 걸어야 한다(사전 검증은 지금 출력을 남기지 않는다). 큰
파일에서는 따로 설계한다.

### 4.3 사용자 정의 키 [구현]

명세의 "Extension keys"가 정한다. 다음은 명세에 없는 근거이다. 사용자 정의 키는 아카이브의 배치(블록, 구간, 오프셋)에 기대지
않는다(MUST NOT). 그래야 `--compact`처럼 내용과 메타데이터를 그대로 두고 다시 쓰는 프로그램이 모르는 키를 옮겨도 맞다. 내용을
바꾸는 프로그램은 모르는 키를 버린다(손실 표시의 원본 크기와 해시는 내용이 바뀌면 맞지 않는다). aqr-archive는 키의 텍스트와
값의 CBOR 바이트를 그대로 다시 쓴다(`tree::Extra::extensions`, 최상위는 `tree::ArchiveExtra`: 구간마다 있고 읽을 때 명세대로
병합). 다시 쓰기를 거부하는 것은 뜻을 모르는 정수 키뿐이다.

## 5. 대상 포맷

### 5.1 구현된 것과 후보

| 종류 | 포맷 | 상태 |
|---|---|---|
| `coding` | ZIP, gzip(`lossy/zip.rs`, `gzip.rs`): zlib 레벨 6 에뮬레이션으로 다시 deflate | 구현 |
| `coding` | `.lzma`, `.xz`, 7z(`lzma.rs`, `xz.rs`, `sevenz.rs`): `aqr_lzma::canonical` | 구현(§6.2) |
| `slack` | Minecraft region(`mca.rs`): 빈 섹터와 칸의 마지막 섹터에서 스트림 뒤 | 구현 |
| `slack` | SQLite(`sqlite.rs`): b-tree 빈 공간(freeblock은 4바이트 머리만 남김), freelist(trunk는 목록만), 마지막 overflow 꼬리. 헤더와 페이지 예약 바이트는 그대로. 비어 있지 않은 `-journal`/`-wal`이 함께 오면 그대로 둠(핫 저널을 되돌리면 비운 페이지가 다시 쓰임) | 구현 |
| `slack` | 디스크 이미지(`disk.rs`, `disk/`): OLE, FAT12/16/32, exFAT, NTFS(`$Bitmap`), ext2/3/4, HFS+. 볼륨마다 자기 파서로 읽고(aqr-disk와 독립), 빈 곳이 aqr-disk가 읽는 파일 범위와 겹치거나 구조가 조금이라도 이상하면(사슬의 고리, 두 번 쓰인 클러스터, 깨끗이 내려지지 않은 볼륨, 재생할 저널, 다른 FAT 사본) 그대로 둔다 | 구현 |
| `slack` | PDB(`pdb.rs`), asar(`asar.rs`): 파일이 가리키지 않는 데이터 | 구현 |
| `coding`(방법 B) | PNG(약 8%: raster 모델 14.46 MB 대 토큰 15.67 MB, codec-corpus의 200 KB 이상 17개), PDF의 FlateDecode(`/Length`와 xref를 다시 써야 함; 추정 5–15%) | **남음** |
| `coding`(방법 A) | LZ4 프레임과 mozlz4(재현 못 하는 HC와 linked block 스트림에서 9–18%), git pack(1–5%, 델타를 다시 짜는 것은 `layout` 이후), bz2(lbzip2, 7-Zip의 스트림), zstd 프레임 | **남음** |
| `slack` | APFS, ISO, 컨테이너(VHD, VMDK, DMG)의 안쪽 볼륨, OLE 외 문서의 빈 곳 | **남음** |
| `layout` | region 압축, SQLite 페이지 조각 모음, PDF의 죽은 객체와 리비전, asar 압축 | **남음** |

대상이 아닌 것: 기록이 이미 없는 것(snappy, gettext, clip의 타일, bz2의 libbzip2 출력, zlib을 정확히 따르는 스트림),
기록이 곧 내용인 것(JPEG 계수, MP3와 Vorbis의 양자화 값, ADPCM 니블, ProRes, 텍스처 블록, 텐서, GIF 픽셀), 인코더를 만들 수 없는
것(RAR, AZO), 바이트 자체가 정체성인 것(실행 파일의 Authenticode, aqr 자신의 Wasm 모듈, ISO의 익스텐트). 기록이 1–8%뿐이고
인코더가 없거나 바깥 참조가 있거나 서명이 흔한 것(CAB의 MSZIP, InstallShield, HDF5, `.zst` 프레임, LZO, LZX, XPRESS, MP3의
TAIL/GAPS, FITS)은 나중에 하거나 하지 않는다.

### 5.2 서명과 바깥 참조: 무손실로 둔다 [구현: `lossy/digests.rs`, `lossy/signatures.rs`]

저장된 바이트 위에 서명이나 해시가 있으면 그대로 둔다. 감지 대상: APK 서명 블록(`APK Sig Block 42`), MSIX/AppX의
`AppxSignature.p7x`/`AppxBlockMap.xml`, PDF의 `/ByteRange`가 있는 `/Sig`, 같은 디렉터리의 분리된 서명과 체크섬(`NAME.sig`,
`.asc`, `.sha256`, `SHA256SUMS` 같은 목록), 바깥 파일이 오프셋을 아는 경우(InstallShield `data1.hdr`, Unreal과 Unity의 팩,
VPK). JAR v1 서명, OOXML/ODF의 XML 서명, git의 객체 id는 풀린 내용에 대한 것이라 `coding` 뒤에도 유효하다. 걸리면 `--stats`와
`-v`에 이유를 알린다. 구현의 세부는 §8의 3.

## 6. 구현의 노트와 측정

- **R은 내용을 통째로 읽을 때 만든다.** `compress_tree`의 배치가 내용을 읽을 때(`Source::read`) R을 만들고 배치를 쓸 때까지
  쥔다(`Source::done`). 배치를 짜기 전에 보는 것(`together`, `lay_alike`, siblings)과 배치를 나누는 크기는 X의 것이다.
- **단일 파일도 트리로 넣는다.** 단일 파일 아카이브에는 표시를 남길 곳이 없다. 같은 파일이 트리로는 더 크다(Info-ZIP `-9`
  ZIP 7.2 MB가 `-8`에서 단일 4.74 MB, 트리 4.90 MB). 단일 파일에서는 손실의 이득이 이 차이에 먹힐 수 있다.
- **R의 DEFLATE 스트림은 어느 레벨에서나 zlib 에뮬레이션으로 넣는다.** aqr-flate는 에뮬레이션을 적응형 프로파일(레벨 7부터)에서만
  쓰고 정적 프로파일에서는 zlib 레벨 6의 스트림도 기록이 약 11%이다. 그래서 `--lossy`가 다시 쓴 파일만 적응형 프로파일에 레벨 6의
  파라미터를 힌트로 준다(`lossy::Rewritten`, DMG와 같은 방식: 기록 수십 바이트, probe 없음). 다시 쓰지 않은 파일은 지금처럼
  넣는다. 풀 때 더 느린 비용을 `--lossy`를 고른 쪽만 치르게 하려는 것이다(사용자의 결정). 레벨 4 미만에서는 DEFLATE 스트림을
  다시 만들지 않으므로 `coding`도 하지 않는다.
- **어떤 스트림을 다시 만드는가.** 레벨 6 이하에서는 zlib 레벨 6의 출력과 바이트 단위로 같지 않은 스트림을 모두 다시 만든다.
  레벨 7부터는 원래 스트림도 적응형으로 넣으므로 두 기록을 재서 R 쪽이 작을 때만 바꾼다(없으면 aqr-flate가 잘 예측하는 Info-ZIP의
  작은 파일에서 손해).
- **aqr-zip의 파서.** zip64 extra가 없는 로컬 헤더 뒤에 서명이 있는 긴 데이터 기술자가 오면 짧은 것으로 읽고 남은 8바이트를
  틈으로 둔다. 손실 경로는 이런 ZIP을 "data between the records"로 거절한다.
- **`coding`은 64 KiB 이상의 파일만 한다**(`lossy:coding-min`): 작은 파일은 되돌려질 뿐 배치를 다시 만드는 비용만 든다.
  `lossy:scan-max`는 §8의 3. 다시 쓰기는 재압축과 같은 heap 허용량 안에서 하고 32 MiB 이상은 하나씩 한다.

측정(M4, 내용 하나짜리 트리, 바이트, 무손실 → `--lossy`; 풀어 낸 파일은 원본보다 0.1–3.7% 커졌다):

| 파일 | 크기 | `-5` | 압축/풀기 명령어 |
|---|---|---|---|
| 7-Zip `-tzip -mx=9` ZIP | 6.96 MB | 5,496,988 → 4,908,250 (−10.7%) | 35 → 46 G / 5.0 → 7.6 G |
| Info-ZIP `zip -9` ZIP | 7.22 MB | 5,176,240 → 4,940,172 (−4.6%) | 34 → 46 G / 5.1 → 7.6 G |
| libdeflate-gzip `-12` tar.gz | 18.6 MB | 16,828,782 → 15,286,756 (−9.2%) | 148 → 188 G / 24.8 → 34.5 G |
| gzip `-9` tar.gz | 19.3 MB | 15,813,146 → 15,286,772 (−3.3%) | 150 → 188 G / 26.5 → 34.5 G |

`-8`에서는 −5.7%, −0.4%, −3.2%, 0이다(zlib의 것은 그대로 둔다). 슬랙: 합성한 SQLite(27.7 MB, 행의 1/3 삭제)는 `-5`에서
16,802,214 → 10,522,462(−37%), `mkntfs` 64 MB 볼륨(4 MB 무작위 파일 8개 중 4개 삭제)은 32,135,082 → 16,130,922(R을 ntfs-3g로
올려 SHA-256 일치), 64 MB FAT32는 48,129,708 → 24,124,612, 로컬 PDB 15개는 0.01–9.9%(대부분 1% 미만). 실제 Minecraft와 SQLite
DB의 이득은 사용자가 잰다(로컬 데이터가 없다).

### 6.2 LZMA의 정규 인코더와 이득이 없을 때의 되돌림 [구현]

**정규 인코더** = `aqr_lzma::canonical`: aqr-lzma의 기록이 예측하는 것을 언제나 고르는 인코더이다(LZMA2는 32 KiB 청크, 블록의
필터와 체크는 그대로, 검사는 liblzma로 둘 다 풀어 비교). 사용자의 결정: XZ Utils `-3` 정도면 충분하다. 이 저장소의 tar(41.8 MB,
사전 8 MiB)로 잰 결과:

| 파서 | 스트림 | aqr-lzma의 기록 |
|---|---|---|
| `xz --format=lzma -6`(원본) | 14,636,276 | 1.060 MB(7.2%) |
| greedy(그 자리에서 가장 긴 일치) | 17,452,667–17,580,659 | 0.044–0.080 MB |
| 채택: greedy + 멀리 있는 짧은 일치를 버림(길이 2는 거리 128, 3은 16 KiB, 4는 1 MiB 이상) + lazy(다음 자리가 2 이상 길면 리터럴) | 15,510,308 | 0.334 MB(−69%) |

`xz -0..-5`는 16.96 → 14.70 MB. 채택안은 `-3`(15.58 MB)보다 작고 `-6`보다 6% 크다. 시도하고 버린 것: 버리는 대신 그 거리 안으로
줄이기(15,710,013, 기록 237 KB: 나을 것이 없다), lazy 3 이상(15,536,338), xz처럼 값을 매기는 최적 파서(`-4`까지 3% 더 얻으려면 필요하고,
선택이 문맥에서 더 벗어나 기록이 다시 는다; 재지 않았다). 멀리 있는 짧은 일치를 버리는 것이 이득의 대부분이다(스트림 −10%). R은
원본보다 10% 남짓 크므로 그 데이터가 재압축될 때만 이득이다(같은 데이터의 `.xz` 둘: 229,244 → 118,640; 10 MB `.xz`는
4,420,950 → 4,262,312; 100 KB–3 MB는 R이 커서 되돌려진다).

**R이 이득이 없으면 X로 되돌린다** [구현]. 배치를 만든 뒤, 다시 쓴 파일 가운데 아카이브에서 차지하는 바이트가 X의 크기 이상이면
X로 그 배치를 다시 만든다(같은 내용의 다른 파일도 따라감, 표시 없음, `-v`에 "rewritten, it archived no smaller"). 크기 문턱은
두지 않는다. 비용은 그 배치를 두 번 만드는 것(4.44 MB의 7z: 45 → 95 G 명령어).

7z는 LZMA/LZMA2 폴더(앞의 BCJ, Delta 필터는 그대로)의 스트림을 다시 만들고 PackInfo의 크기(와 있으면 CRC)만 고치며 인코딩된
헤더는 같은 코더로 다시 인코딩한다. BCJ2, PPMd, BZip2, Deflate, 암호화된 폴더는 그대로 둔다.

**무손실 쪽의 연관된 수정**: 이 측정에서 무손실 아카이브가 파일보다 큰 일이 보였다(41.8 MB `.lzma`가 111.7%: "작을 때만" 판단을 층마다
해서, `.xz`와 tar 멤버 하나하나는 이기지만 합치면 tar 하나보다 컸다). 배치에 혼자인 파일이 재압축되었는데 차지하는 바이트가 파일
크기 이상이면 그대로 두고 다시 만든다(`-Z no-kept-larger`로 끈다). 혼자일 때만 하는 것은 한 파일의 몫이 다른 파일이 그 스트림에서
가져가는 것을 말해 주지 않기 때문이다(배치를 가리지 않으면 10gb `-5`가 2,437,777,215 → 2,464,160,095, 175 → 230 s로 나빠졌다).

남은 일: 소수의 파일로 된 작은 아카이브에서 모듈 블록이 파일보다 큰 것(aqr-alz 디렉터리의 189,144바이트 `.xz`가 313,933바이트, 그중
126 KB가 모듈). 7z 외의 컨테이너에서 같은 방법.

## 7. 범위 밖

다음은 읽는 쪽이 보는 것을 바꾸므로 이 모드에 넣지 않는다. 필요하면 `--lossy`와 별개의 이름으로 설계한다(`docs/hints-design.md`가
말하는 `-Y`).

- 미디어의 재양자화(JPEG, MP3, 텐서의 가수 자르기, 부동소수점 절단).
- 메타데이터 제거와 정규화(EXIF, ID3, gzip의 mtime/name, tar 헤더의 uid/uname/mtime, ZIP의 extra field).
- 파생 데이터의 재생성(PSD의 합성 이미지, clip의 미리보기 PNG, DWARF의 가속 테이블, Minecraft의 빛, Distant Horizons의 부모 LOD):
  정확히 재생성할 수 있으면 무손실로 할 일이고, 아니면 동치가 아니다.
- 텍스트의 정규화(줄 끝, 공백, 숫자 표기, JSON 키 순서).
- 바깥 컨테이너가 무손실인 채 안쪽 파일만 손실로 바꾸는 것(바깥의 CRC와 크기가 바뀐다). 지금은 아카이브의 최상위 항목만 대상이다.
  중첩은 바깥도 같은 종류로 다시 쓸 수 있을 때 따로 다룬다.

## 8. 열린 질문

1. ~~값 없는 `--lossy`의 기본값~~ **[확정]** 값을 반드시 받는다(§2).
2. ~~`hash`에 쓸 해시~~ **[확정][구현]** SHA-512/256(§4.1).
3. 분리된 서명과 체크섬의 감지(§5.2) **[구현]**(`lossy/digests.rs`, `lossy/signatures.rs`):
   - 다시 쓰는 파일마다 MD5, SHA-1, SHA-256, SHA-384, SHA-512, BLAKE2b-512를 한 번에 계산하고(256 KiB씩 각 해시에 차례로),
     그 바이트열이나 십육진 문자열(대소문자), base64(SRI의 `sha512-…`, npm과 yarn의 lockfile)가 함께 넣는 64 MiB 이하의 다른
     입력 어딘가에 있으면(Aho-Corasick, `lossy:scan-max`) 그대로 둔다.
   - 서명은 공개 키를 모르면 검증할 수 없으므로 아는 형식만 본다. OpenPGP의 분리 서명(`.sig`, `.asc`, `.gpg`)은 서명 패킷의
     "서명한 해시의 왼쪽 16비트"를 X와 서명의 해시된 부분으로 계산해 맞춰 본다(키 없이). minisign(`.minisig`)은 키 없이는 X에
     묶을 수 없으므로 이름과 형식으로만 본다.
   - 10gb의 `-5 --lossy all`(최종): 2,437,777,215 → 2,384,714,091바이트(−2.2%), 319.9 s(무손실 169.8 s), 16.73 T 명령어(9.60 T),
     다시 쓴 파일 368개 중 되돌림 39개, "data between the records"로 거절한 ZIP 109개, 다이제스트 단계 15.1 s에 6개 파일을 그대로
     둠. 이득 53.6 MB의 85%가 1 MiB 이상의 파일 29개이고 42%가 `enwik9.zip` 하나이다. heap 최대 4.74 GB.
   - 남은 비용은 큰 DEFLATE 스트림이다. `enwik9.zip`(1 GB의 데이터) 하나가 무손실 10.8 s, `--lossy coding` 51.1 s이고 풀면 3.90 GB가
     된다(322.6 → 234.8 MB). R을 만들 때와 넣을 때 모두 zlib 에뮬레이션이 한 스레드로 1 GB를 지난다. pigz처럼 조각마다 full flush한
     zlib 레벨 6이면 조각을 나란히 만들고 넣을 수 있고 에뮬레이터의 메모리도 조각만큼이 된다(미구현).

### 측정할 것

1. DEFLATE의 고정 레벨(원본과 비슷한 크기가 되는 레벨과 그 풀기 속도): 지금은 레벨 6으로 고정했고, aqr-png의 codec-corpus와
   aqr-zip의 172개 ZIP 전체에서 확인한 적은 없다.
2. 동치 검사의 비용(압축 시간에서 차지하는 비율).
3. Minecraft와 SQLite의 실제 아카이브 이득(`slack`의 전후, 스캔으로 재압축되던 옛 스트림의 몫을 뺀 값).

로컬 데이터만 쓴다. 네트워크 드라이브의 코퍼스는 사용자가 요청할 때만 쓴다.
