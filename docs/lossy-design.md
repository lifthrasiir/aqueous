# 동치 손실 압축(`--lossy`) 설계 [초안]

Aqueous는 지금 모든 파일을 바이트 단위로 되돌린다. 재압축기는 내용(압축을 푼 데이터, 픽셀, NBT)과 함께, 원본
인코더가 한 선택을 *기록*(parse record, 보정, 남은 바이트)으로 남겨 원본 바이트를 그대로 다시 만든다. 이 문서는 그
기록 가운데 **그 파일을 읽는 어떤 프로그램도 신경 쓰지 않는 정보**를 버리고, 다르지만 동치인 파일을 내보내는 모드를
다룬다. 화질이나 음질을 깎는 보통의 손실 압축과 달리, 읽는 쪽이 보는 내용은 바뀌지 않는다.

- 예: ZIP 항목의 DEFLATE 스트림은 어떻게 짜여 있든 같은 데이터로 풀린다. 원본의 parse를 기록하지 않고 내용만 저장한
  뒤, 풀 때 정해진 인코더로 다시 deflate하고 크기와 오프셋을 맞춰 ZIP을 다시 쓴다.
- 예: Minecraft의 region 파일에서 빈 섹터와 패딩에 남은 옛 쓰기의 조각은 게임이 읽지 않는다. 0으로 채운다.

상태 표기는 `docs/xform-design.md`와 같다(**[확정]**, **[잠정]**, **[제안]**, **[구현]**). 이 문서는 전부
**[제안]**이며, 따로 적지 않은 것도 그렇다. 수치의 출처는 각 크레이트의 README이고, 출처 없이 추정한 수치는
"추정"이라고 적는다.

## 1. 정의와 원칙

**동치.** 포맷마다 그 포맷을 읽는 프로그램이 보는 것을 *뷰*(view)라고 정의한다. 압축기는 입력 X 대신 R을 아카이브에
넣을 수 있는데, 그 조건은 view(R) = view(X)이다. R이 바이트 단위로 X와 다를 수 있다는 점만 빼면 나머지는 지금과
같다. 아카이브는 R을 바이트 단위로 되돌리고(명세와 디코더는 손대지 않는다), 검증도 R을 기준으로 한다.

| 포맷 | 뷰(예) |
|---|---|
| ZIP | 항목의 순서, 이름, 메타데이터, 방식(stored/deflated), 풀린 데이터, 주석 |
| gzip | 헤더 필드와 풀린 데이터 |
| PNG | 청크의 순서와 내용, 단 IDAT/fdAT는 이어 붙여 inflate하고 필터를 되돌린 픽셀 |
| xz, 7z | 블록/폴더 구조와 필터, 풀린 데이터, 무결성 검사의 종류 |
| Minecraft region | 각 칸의 (타임스탬프, 압축 방식, 풀린 NBT) |
| SQLite | 각 페이지의 셀 내용과 b-tree 구조(빈 공간 제외) |
| 파일 시스템 | 파일 트리, 메타데이터, 내용, 그리고 할당된 메타데이터 블록 |

**원칙.**

1. **읽는 쪽이 보는 것은 바꾸지 않는다.** 픽셀, 샘플, 텍스트, 메타데이터(EXIF, 타임스탬프, uid)는 그대로 둔다.
   양자화, 메타데이터 제거, 캐시 재생성은 이 모드에 넣지 않는다(§7).
2. **파일 전체를 이해할 때만 한다.** 재압축기가 파일의 0바이트부터 끝까지 구조를 알고, 바뀌는 바이트를 가리키는 크기,
   오프셋, 체크섬을 모두 다시 쓸 수 있어야 한다. 모르는 데이터 안에서 스캔으로 찾은 스트림(`scanning.rs`, 아무
   데이터 안의 raw deflate, TIFF 안의 SOI, SQLite blob 안의 zstd 프레임)은 길이가 바뀌면 모르는 참조가 깨지므로 하지
   않는다.
3. **명시적으로 고른다.** 기본값은 지금과 같은 무손실이다. 손실의 종류는 이름으로 고른다(§2). 지워진 데이터를 없애는
   종류(`slack`)는 따로 골라야만 한다.
4. **서명은 건드리지 않는다.** 저장된 바이트 위에 서명이나 해시가 있는 파일은 무손실로 둔다(§5.3).
5. **실패를 숨기지 않는다.** 동치 검사를 통과하지 못한 파일은 무손실로 저장하고 그렇게 알린다. 손실로 바뀐 파일은
   아카이브에 표시가 남는다(§4.1).

## 2. 명령행

```
aqr -c --lossy=coding,slack -o out.aqr inputs...
```

- `--lossy=CLASS[,CLASS...]`. `CLASS`는 `coding`, `slack`, `layout`, `all` 가운데 하나이다. `CLASS:FORMAT[+FORMAT...]`로
  포맷을 좁힐 수 있다(`coding:zip+png`). 포맷 이름은 `formats.rs`의 이름을 쓴다.
- 값 없는 `--lossy`는 `coding`이다. 지워진 데이터를 잃지 않는 종류가 이것뿐이기 때문이다.
- 짧은 옵션은 두지 않는다. 결과물을 바꾸는 옵션은 실수로 켜기 어렵게 긴 이름만 둔다.
- 압축할 때만 쓴다. `-d`, `-t`, `-K`, `-I`와 함께 주면 오류이다.

| 종류 | 하는 일 | 잃는 것 |
|---|---|---|
| `coding` | 압축 스트림을 정해진 인코더로 다시 만든다. 컨테이너의 크기, 오프셋, 압축된 바이트의 체크섬은 다시 쓴다 | 원본 인코더의 흔적(어떤 도구로 만들었는지) |
| `slack` | 구조가 가리키지 않는 바이트(빈 섹터, 빈 페이지, 할당되지 않은 클러스터, 패딩 꼬리)를 제자리에서 0으로 채운다 | 지워진 데이터, 복구와 포렌식에 쓸 재료 |
| `layout` | 구조를 다시 배치한다(빈 칸 압축, 페이지 조각 모음, 안 쓰이는 옛 리비전 제거). 오프셋을 다시 쓴다 | `slack`과 같고, 파일의 배치가 바뀐다 |

`layout`은 가장 나중에 한다(§6). 처음 두 단계는 `coding`과 `slack`만 다룬다.

### 2.1 다른 옵션과의 관계

- **`-a`, `-s`.** 바뀐 파일은 크기와 수정 시각으로 찾는다. 손실로 넣은 파일은 아카이브의 크기가 R의 크기이므로 매번
  바뀐 것으로 보인다. §4.1의 원본 크기와 비교한다. 같은 파일을 다른 `--lossy`로 다시 넣는 경우(무손실 아카이브에
  `-a --lossy`)에는 바뀌지 않은 파일을 다시 넣지 않는다. 다시 넣으려면 파일을 지우고 넣는다.
- **`-A`(보존용).** 함께 쓸 수 없다(오류). `-A`는 장기 보존을 위한 것이고 `--lossy`는 원본을 잃는다. **[확정]**
- **`--no-check`.** 아카이브를 풀어 보는 검증만 끈다. 동치 검사(§4.2)는 끄지 않는다. 동치 검사가 없으면 손실 모드는
  잘못된 파일을 조용히 만들 수 있다.
- **`--format zip` 등(aqr-pack).** 이번 범위에 넣지 않는다.
- **`--stats`.** 종류와 포맷별로 몇 파일이 손실로 들어갔는지, 아카이브에서 줄어든 바이트, 풀었을 때 크기의 변화
  (R과 X의 크기 차이)를 알린다. 동치 검사에 실패해 무손실로 돌아간 파일도 알린다.

## 3. 구조: 정규형 R을 만들고 그대로 압축한다

손실 압축기는 입력 X를 받아 식 F를 만든다. 조건은 view(eval(F)) = view(X)이다. R = eval(F)이고, 아카이브와 검증은 R을
원본처럼 다룬다. F를 만드는 방법은 둘이다.

### 3.1 방법 A: 다시 쓰고 무손실로 압축

X를 네이티브로 R로 다시 쓰고(재인코딩하고 컨테이너를 고친다), R을 지금의 무손실 경로로 압축한다. R을 만드는 인코더를
aqr가 *정확히 예측하는 것*으로 고르면, R의 기록은 저절로 거의 0이 된다. 새 모듈도, 새 식의 모양도 필요 없다.

- DEFLATE: `aqr_flate::zlib::compress`(zlib 1.3.1과 바이트 단위로 같다)로 다시 deflate한다. ZIP, gzip, zlib, git pack,
  Minecraft의 칸, HDF5 청크는 aqr-flate가 zlib 출력을 약 10바이트로 재현한다(aqr-flate README). 그래서 R의 기록은
  거의 없다.
- bzip2: aqr-bz2의 libbzip2 재구현으로 다시 압축한다(lbzip2, 7-Zip의 스트림이 대상이다).
- LZ4: `aqr-lz4`의 `block.rs`(liblz4의 `LZ4_compress_default`)로 다시 압축한다. HC 레벨과 linked block 프레임이 대상이다.
- zstd: `aqr_zstd::compress`(레벨 3의 에뮬레이션, 내용 256 KiB 미만)로 다시 압축한다.
- `slack`: 0으로 채운 R은 원래 경로 그대로 압축된다.

비용은 인코딩을 두 번 하는 것이다. 다시 쓸 때 한 번, R을 무손실로 쪼갤 때 parse 한 번이 든다. 처음에는 이 방법을
쓰고, 느린 곳만 방법 B로 옮긴다.

### 3.2 방법 B: 내용에서 바로 식을 만든다

재압축기가 내용만 넣고, 풀 때 정규 인코더 모듈이 스트림을 만드는 식을 바로 낸다. 예를 들어 PNG는 픽셀을 aqr-raw의
모델로 넣고, 풀 때 필터를 적용한 뒤 zlib으로 압축한다. 방법 A가 듣지 않는 곳에 필요하다.

- **aqr-png.** 무손실 경로가 zlib 에뮬레이션이 아니라 원본의 LZ77 토큰을 그대로 남긴다(aqr-png README "Why the LZ77
  parse is kept": 에뮬레이션은 1–20 MB/s로 느리다). 그래서 R을 다시 넣어도 토큰 기록이 그대로 남는다. 픽셀에서
  바로 식을 만들어야 이득이 난다.
- **aqr-lzma.** 정규 인코더를 "aqr-lzma의 예측이 고르는 것을 언제나 고르는 인코더"로 정의한다. 그러면 기록은 거의
  확실한 기호들만 남아 비용이 거의 없다(§6 측정 1). 이 경우 방법 A와 B는 같은 결과가 된다. 기록 형식은 그대로이고
  인코더만 새로 둔다.

어느 방법이든 R은 F를 평가해 나오는 결과로 정해진다. 따라서 모듈이 결정적이라는 것(R1)만으로 R은 플랫폼과 무관하게
같다. 풀 때의 인코더가 나중 버전에서 바뀌어도 아카이브는 자기 모듈을 지니므로 R은 그대로이다.

### 3.3 정규 인코더의 선택: 풀었을 때의 크기와 속도

`coding`의 R은 원본보다 클 수 있다. 7-Zip ultra의 LZMA, zopfli의 DEFLATE, zlib 레벨 9로 만든 PNG를 빠른 인코더로
다시 만들면, 아카이브는 작아지지만 풀어 낸 파일은 커진다. 인코더 수준으로는 세 등급을 생각할 수 있었다.

| 등급 | DEFLATE | 풀 때 | 풀어 낸 파일 |
|---|---|---|---|
| `store` | stored 블록 | 가장 빠르다 | 훨씬 커진다 |
| `fast` | zlib 레벨 1 | 빠르다(`zlib::compress` 빠른 레벨 약 330 MB/s) | 조금 커진다 |
| `default` | zlib 레벨 6 | 느리다(데이터 기준 수십 MB/s) | 원본과 비슷하다 |

등급은 사용자가 고르지 않고 하나로 고정한다. 풀어 낸 파일이 원본과 비슷한 크기가 되는 쪽을 택한다. DEFLATE라면
`default` 쪽이다. 구체적인 레벨과 파라미터는 포맷마다 압축률을 재고 정한다(§6 측정 2). **[확정]** 원본의 방식은
지킨다(stored는 stored로, deflated는 deflated로). 아카이브가 무손실보다 작아지지 않는 파일은 무손실로 둔다. 손실
경로는 이득이 있을 때만 쓴다.

## 4. 아카이브와 검증

### 4.1 표시: 항목 메타데이터의 사용자 정의 키

손실 표시는 일반 압축기가 알 필요가 없는 aqr만의 정보이다. 그래서 명세의 키로 정하지 않고, `aqr-entry-extra`의
**문자열 키**(사용자 정의 키, §4.3)로 둔다. **[확정]**

```cddl
aqr-entry-lossy = (
  ? "org.mearie.aqr.lossy" => {
    0 => [+ tstr],     ; classes: "coding", "slack", "layout"
    1 => uint,         ; size: 원본 X의 크기
    ? 2 => bstr,       ; hash: 원본 X의 내용 해시
  }
)
```

- 모르는 디코더는 이 키를 무시하고 R을 풀어도 맞다. 명세는 이 키에 대해 아무것도 정하지 않는다.
- `-t -v`, `-I`, `--json`은 손실로 들어간 항목을 표시한다. `-a`/`-s`는 `size`와 수정 시각으로 바뀐 것을 판단한다.
  `hash`는 "이 파일이 그때의 원본과 같은가"를 확인하는 데 쓴다(나중의 `--diff`).
- 같은 X는 언제나 같은 R이 된다. 따라서 파일 사이의 중복 제거는 R 사이에서 그대로 된다.

### 4.2 검증: 두 단계

1. **R에 대한 무손실 검증.** 지금의 검증(`crates/aqr-compress/src/verify.rs`, 사전 검증 기록과 해시)을 그대로 쓴다.
   기준만 X의 해시에서 R의 해시로 바뀐다.
2. **동치 검사.** view(R) = view(X)를 확인한다. 각 포맷이 `view`를 코덱 크레이트에 둔다(`encode` 기능). 뷰의
   다이제스트를 스트리밍으로 계산하며, 뷰 전체를 메모리에 올리지 않는다.
   - **독립된 코드로 검사한다.** R을 만드는 쪽과 같은 코드로 검사하면 같은 버그를 함께 지나친다(`docs/xform-design.md`
     §6과 같은 이유). DEFLATE는 aqr-flate가 아닌 다른 inflate(작업 공간의 flate2, zlib-rs)로, LZMA는 liblzma(aqr-pack이 이미
     빌드한다)로 푼다.
   - **`slack`은 독립 검사가 어렵다.** 파일 시스템의 비트맵을 잘못 읽으면, 0으로 채운 살아 있는 블록이 같은 파서의 뷰
     에서도 빠질 수 있다. 그래서 `slack`은 (a) 비트맵이 비었다고 하고 (b) 파싱한 어떤 구조도 가리키지 않는 바이트만
     건드린다. 시험은 실제 도구로 한다: `sqlite3 PRAGMA integrity_check`와 덤프 비교, `fsck`/`ntfsfix`(Linux VM).
     시험 데이터는 공개된 것과 직접 만든 이미지만 쓴다.

방법 A에서는 R을 다시 쓸 때 바이트가 손에 있으므로 그 자리에서 동치를 검사한다. 방법 B에서는 사전 검증이 식을 평가하는
출력에 뷰 계산을 걸어야 한다. 사전 검증은 지금 출력을 남기지 않기 때문이다. 큰 파일에서는 이 부분을 따로 설계한다.

### 4.3 사용자 정의 키 [구현]

명세의 "Extension keys"가 정한다. 정수 키는 명세의 몫이고, 문자열 키는 사용자 정의 키이다. 이름은 소유한 도메인을
뒤집은 것으로 시작하고(SHOULD), 값은 아무 CBOR이다. 다음은 명세에 없는 근거와 구현 노트이다.

- 이름에 도메인 다음 단계(`aqr`)를 두는 것은 같은 도메인의 다른 프로젝트와 겹치지 않게 하려는 것이다.
- 사용자 정의 키는 아카이브의 배치(블록, 구간, 오프셋)에 기대지 않는다(MUST NOT). 그래야 `--compact`처럼 내용과
  메타데이터를 그대로 두고 다시 쓰는 프로그램이 모르는 키를 옮겨도 맞다. 내용을 바꾸는 프로그램은 모르는 키를
  버린다. 손실 표시의 원본 크기와 해시가 그 예로, 내용이 바뀌면 더는 맞지 않는다.
- aqr-archive는 사용자 정의 키를 키의 텍스트와 값의 CBOR 바이트로 담아 그대로 다시 쓴다. 항목의 키는
  `tree::Extra::extensions`에, 최상위의 키는 `tree::ArchiveExtra`에 담는다. `ArchiveExtra`는 `archive-comment`도 담으며
  구간마다 있고(`SegmentWriter::set_archive_extra`), 읽을 때는 명세대로 구간들을 병합한다(나중 구간의 같은 키가
  대체한다). `--compact`와 `--move`는 이것들과 `comment`, `zip-extras`를 옮긴다. 다시 쓰기를 거부하는 것은 뜻을 모르는
  정수 키뿐이다. 장래 명세가 배치에 기대는 키를 정할 수 있기 때문이다.

다음은 대상이 아니다.

- **기록이 이미 없다.** snappy, gettext, clip의 타일, bz2의 libbzip2 출력, zlib을 정확히 따르는 스트림. 이 경우는 다른

- **기록이 곧 내용이다.** JPEG 계수, MP3와 Vorbis의 양자화 값, ADPCM 니블, ProRes, 텍스처 블록, 텐서, GIF 픽셀.
- **인코더를 만들 수 없다.** RAR(unrar 라이선스), AZO.
- **바이트 자체가 정체성이다.** 실행 파일(Authenticode, 코드 서명), aqr 자신의 Wasm 모듈(해시로 식별된다), ISO(배포용
  체크섬, 익스텐트).

### 5.2 포맷별로 다시 써야 하는 것

- **ZIP.** 로컬 헤더, 중앙 디렉터리, zip64, 데이터 기술자의 압축 크기, 이후 모든 오프셋, EOCD. CRC는 풀린 데이터에
  대한 것이라 그대로이다. aqr-zip이 이미 모두 파싱하고 예측한다. 맨 앞에 다른 데이터가 붙은 ZIP(SFX)은 제외한다.
  ODF와 EPUB의 `mimetype`은 stored이므로 방식을 지키면 그대로 남는다.
- **PNG.** IDAT의 길이와 CRC(이미 유도한다), APNG의 fdAT 순번, Apple의 `iDOT`(둘째 IDAT의 오프셋을 다시 계산한다.
  그럴 수 없으면 그 파일을 제외한다).
- **xz.** 블록의 압축 크기, 인덱스, 푸터. 검사값은 풀린 데이터에 대한 것이다. **7z**는 `PackInfo`의 크기, 폴더의 CRC,
  인코딩된 헤더, `NextHeaderSize`/`NextHeaderCRC`, 시작 헤더 CRC이다(aqr-7z가 파싱한다).
- **Minecraft.** 빈 섹터와 각 칸의 마지막 섹터에서 스트림 뒤를 0으로 채운다. 헤더(위치, 타임스탬프)는 그대로이다.
- **git pack.** pack의 SHA-1 트레일러와 `.idx`의 CRC-32(모듈이 이미 유도한다), `.rev`. `.bitmap`과 `multi-pack-index`가
  같이 있으면 그 세트는 제외한다. pack 파일 이름의 해시가 새 체크섬과 달라도 git이 받아들이는지는 확인해야 한다.

### 5.3 서명과 바깥 참조: 무손실로 둔다

| 감지 | 대상 |
|---|---|
| ZIP 중앙 디렉터리 앞의 `APK Sig Block 42` | APK v2/v3/v4 서명 |
| `AppxSignature.p7x`나 `AppxBlockMap.xml` 항목 | MSIX/AppX(블록 맵에 압축 크기가 있다) |
| `/ByteRange`가 있는 `/Sig` 사전 | PDF 전자 서명 |
| 같은 디렉터리의 `NAME.sig`, `NAME.asc`, `NAME.sha256`이나, `SHA256SUMS`처럼 이름을 담은 목록 | 분리된 서명과 체크섬(`siblings.rs`로 형제 파일을 본다) |
| 바깥 파일이 오프셋을 아는 경우 | InstallShield `data1.hdr`, Unreal과 Unity의 팩, VPK |

JAR v1 서명, OOXML과 ODF의 XML 서명, git의 객체 id는 풀린 내용에 대한 것이라 `coding` 뒤에도 유효하다. 위 감지에
걸리면 무손실로 두고 `--stats`와 `-v`에 이유를 알린다.

## 6. 단계

1. **기반.** `--lossy` 파싱(`-A`와 함께면 오류),
   `aqr_compress::Options::lossy`, 손실 표시와 `-a`/`-s`의 비교, R 기준의 검증,
   동치 검사의 틀, `--stats` 보고.
   - 첫 포맷은 Minecraft `slack`(파일 전체를 이미 파싱하고 이득이 크다)과 ZIP/gzip `coding`(방법 A,
     `zlib::compress`)이다.
2. **PNG**(방법 B: 픽셀과 정규 deflate 모듈)와 **PDF**의 FlateDecode(`/Length` 직접 값부터, xref는 그다음).
3. **LZMA**(xz, `.lzma`, 7z): 예측을 그대로 따르는 정규 인코더.
4. **`slack` 확장**: SQLite, OLE, PDB, asar, 그리고 비트맵 파서와 함께 NTFS, FAT, ext, HFS+, APFS.
5. **`layout`**: region 압축, SQLite 페이지 조각 모음, PDF의 죽은 객체와 리비전, asar 압축.

### 6.1 1단계의 구현 [구현]

`crates/aqr-compress/src/lossy/`(모듈 문서가 구조를 설명한다)와 aqr의 `--lossy`. 설계와 달라진 점과 알게 된 것:

- **R은 내용을 통째로 읽을 때 만든다.** `compress_tree`의 배치가 내용을 읽을 때(`Source::read`) R을 만들고, 배치를
  쓸 때까지 쥔다(`Source::done`). 배치를 짜기 전에 보는 것(`together`, `lay_alike`, siblings)은 X를 본다. 배치를 나누는
  크기도 X의 것이다.
- **단일 파일도 트리로 넣는다.** 단일 파일 아카이브에는 메타데이터가 없어 표시를 남길 곳이 없기 때문이다. 그런데 같은
  파일이 트리로는 더 크다. Info-ZIP `-9`의 ZIP(7.2 MB)이 `-8`에서 단일 파일로는 4.74 MB, 트리로는 4.90 MB이다(손실과
  무관하게 원래 있던 차이이다). 단일 파일에서는 손실의 이득이 이 차이에 먹힐 수 있다.
- **R의 DEFLATE 스트림은 어느 레벨에서나 zlib 에뮬레이션으로 넣는다.** aqr-flate는 zlib 에뮬레이션을 적응형 프로파일
  (레벨 7부터)에서만 쓴다. 레벨 6까지의 정적 프로파일에서는 zlib 1.3.1 레벨 6의 스트림도 기록이 스트림의 약 11%이다
  (다른 인코더의 스트림과 비슷하다). 그래서 `--lossy`가 다시 쓴 파일에서만, 그 스트림을 적응형 프로파일로 넣고 레벨 6의
  파라미터를 힌트로 준다(`lossy::Rewritten`, DMG와 같은 방식). 파라미터를 찾지 않으므로 기록은 수십 바이트이고, probe도
  거치지 않는다. 다시 쓰지 않은 파일은 지금처럼 넣는다. 적응형 프로파일은 풀 때 더 느린데, 이 비용을 `--lossy`를 고른
  쪽만 치르게 하려는 것이다(사용자의 결정). 레벨 4 미만에서는 DEFLATE 스트림을 다시 만들지 않으므로(`inflated`)
  `coding`도 하지 않는다.
- **어떤 스트림을 다시 만드는가.** 레벨 6 이하에서는 zlib 레벨 6이 만든 것과 바이트 단위로 같지 않은 스트림을 모두 다시
  만든다. 원래 스트림은 정적 프로파일의 기록(약 10%)을 치를 것이기 때문이다. 이 경우 deconstruct도 하지 않는다. 레벨
  7부터는 원래 스트림도 적응형 프로파일로 넣으므로, 두 스트림의 기록을 재서 R 쪽이 작을 때만 바꾼다. 이 비교가 없으면
  Info-ZIP의 작은 파일들처럼 aqr-flate가 잘 예측하는 스트림에서 손해를 본다.
- **표시에 `hash`는 아직 넣지 않는다**(§8의 질문 2).
- **동치 검사**(`lossy/check.rs`)는 직접 쓴 파서와 flate2(zlib-rs)로 한다. 검사에 실패한 파일은 X로 넣고 항상 알린다.
- **aqr-zip의 파서.** zip64 extra가 없는 로컬 헤더 뒤에 서명이 있는 긴 데이터 기술자가 오면, 짧은 것으로 읽고 남은
  8바이트를 틈으로 둔다. 손실 경로는 이런 ZIP을 "data between the records"로 거절한다.

측정은 M4에서 내용 하나짜리 트리로 했다(크기는 바이트, 무손실 → `--lossy`, 명령어 수는 압축과 `-K`의 것).

| 파일 | 크기 | `-5` | 압축 | 풀기 | `-8` |
|---|---|---|---|---|---|
| 7-Zip `-tzip -mx=9` ZIP(이 저장소의 `crates/`) | 6.96 MB | 5,496,988 → 4,908,250 (−10.7%) | 35 → 46 G | 5.0 → 7.6 G | 5,142,634 → 4,847,728 (−5.7%) |
| Info-ZIP `zip -9` ZIP(같은 것) | 7.22 MB | 5,176,240 → 4,940,172 (−4.6%) | 34 → 46 G | 5.1 → 7.6 G | 4,899,404 → 4,880,180 (−0.4%) |
| libdeflate-gzip `-12` tar.gz(`codecs`, `crates`, `spec`) | 18.6 MB | 16,828,782 → 15,286,756 (−9.2%) | 148 → 188 G | 24.8 → 34.5 G | 15,731,418 → 15,225,512 (−3.2%) |
| gzip `-9` tar.gz(같은 tar) | 19.3 MB | 15,813,146 → 15,286,772 (−3.3%) | 150 → 188 G | 26.5 → 34.5 G | 같다(zlib의 것이라 그대로 둔다) |

`-8`의 수치는 레벨 6 이하의 규칙을 넣기 전의 것이다(레벨 7부터는 바뀌지 않았다). 풀어 낸 파일은 원본보다 0.1–3.7%
커졌다(zlib 레벨 6). Minecraft `slack`은 로컬 데이터가 없어 테스트로만 확인했다.

### 측정할 것

1. **LZMA의 정규 인코더.** 예측을 그대로 따른 스트림의 크기(원본 7-Zip/xz 대비 풀어 낸 크기), R의 기록 크기, 인코딩
   속도. 대상은 aqr-lzma README의 `.tar.lzma`와 7z 폴더이다.
2. **DEFLATE의 고정 레벨.** 원본과 비슷한 크기가 되는 레벨(5–9, memLevel)을 찾고, 그 레벨에서 풀 때의 속도를 잰다. 대상은 aqr-png의 codec-corpus, aqr-zip의
   172개 ZIP, enwik9.zip이다.
3. **Minecraft와 SQLite의 실제 아카이브 이득.** `slack`의 전후 비교이며, 옛 스트림이 스캔으로 재압축되던 몫을 뺀 값이다.
4. **동치 검사의 비용.** 압축 시간에서 차지하는 비율.

로컬 데이터만 쓴다. 네트워크 드라이브의 코퍼스는 사용자가 요청할 때만 쓴다.

## 7. 범위 밖

다음은 읽는 쪽이 보는 것을 바꾸므로 이 모드에 넣지 않는다. 필요하면 `--lossy`와 별개의 이름으로 따로 설계한다.

- 미디어의 재양자화(JPEG, MP3, 텐서의 가수 자르기, 부동소수점 절단).
- 메타데이터 제거와 정규화: EXIF, ID3, gzip의 mtime/name, tar 헤더의 uid/uname/mtime, ZIP의 extra field.
- 파생 데이터의 재생성: PSD의 합성 이미지, clip의 미리보기 PNG, DWARF의 가속 테이블, Minecraft의 빛, Distant
  Horizons의 부모 LOD. 정확히 재생성할 수 있으면 이미 무손실로 할 일이고, 아니면 동치가 아니다.
- 텍스트의 정규화(줄 끝, 공백, 숫자 표기, JSON 키 순서).
- 바깥 컨테이너가 무손실인 상태에서 안쪽 파일만 손실로 바꾸는 것. 바깥의 CRC와 크기가 바뀌므로, 처음에는 아카이브의
  최상위 항목만 대상으로 한다. 중첩은 바깥도 같은 종류로 다시 쓸 수 있을 때 따로 다룬다.

## 8. 열린 질문

1. 값 없는 `--lossy`의 기본값을 `coding`으로 할지, 값을 반드시 받을지.
2. 손실 표시의 `hash`에 쓸 해시: `chash`(내용 해시, 합성된다)로 할지, 사용자가 `sha256sum`과 비교할 수 있는 SHA-256으로 할지.
3. 분리된 서명의 감지(§5.3)를 어디까지 할지. 같은 디렉터리만 볼지, 압축하는 입력 전체를 볼지.
