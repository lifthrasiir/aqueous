# Aqueous 전처리기(transform) 설계

Aqueous의 WebAssembly 기반 전처리기(RarVM의 현대판)의 설계이다. 여기서 정한 것은 대부분 명세(`spec/index.bs`)에
들어갔고, 명세가 규범이다. 이 문서는 명세에 없는 것만 다룬다: 그렇게 정한 근거와 실측, 명세로 옮기지 않은 구현 노트,
남은 질문, 그리고 진행 중인 제안(지금은 §5.5의 태스크 메모리 v2). 명세에 있는 내용은 그 절을 가리키기만 한다.

절과 항목의 상태 표기는 다음과 같다.

- **[확정]** 정해져 있거나 명시적으로 합의된 것
- **[잠정]** 방향은 합의했으나 세부가 열려 있는 것
- **[제안]** 제안되었으나 아직 검토하지 않은 것
- **[구현]** 명세와 코드에 들어간 것(근거와 노트만 남긴다)

크레이트의 배치와 역할은 `CLAUDE.md`와 각 크레이트의 README가, 재압축기의 포맷은 각자의 `FORMAT.md`가 적는다.

## 0. 배경과 전제

- RarVM은 실제로는 범용 VM으로 거의 쓰이지 않았다. unrar는 표준 필터를 CRC로 알아본 뒤 네이티브로 실행했고, RAR5에는
  VM이 없다. 교훈은 둘이다. 쓰이는 필터의 대부분은 소수의 표준 필터이고, VM의 가치는 장기 보존을 위한 *규범적 정의*와
  롱테일 확장성에 있다.
- 범용 VM이 정당화되는 대표 사례는 BCJ나 delta 같은 고정 필터가 아니라 **DEFLATE 재압축**이다. zlib 버전과 파라미터
  조합이 너무 다양해서 고정 필터로는 감당이 안 되고, bit-exact 재구성에 encoder 에뮬레이션이 필요하다.
- 실측 참고치(M4, 단일 스레드).
  - disfilter 디코더의 Wasm은 8 KB, zstd로 3.2 KB이다.
  - aqr-flate 재구성: 정적 프로파일 6이 평문 기준 123 MB/s(프로파일 0–9: 111–185 MB/s), 적응형 프로파일 10이 53 MB/s.
  - 포맷별 재압축기의 네이티브 해제(원본 파일 기준): png 89, jpeg 89(progressive 47), mp3 114, flac 157–241,
    psd 103–142, pdf 142–186, sqlite 415, obj 373 MB/s. 전처리기는 이 수준을 깎지 않아야 한다(R5).
  - 같은 역변환을 wasm32로 돌리면 네이티브 대비 JIT에서 1.24–1.69배, 인터프리터에서 20–34배 느리다(§5.7).

## 2. 개요

아카이브는 두 함수로 이루어진 객체로 볼 수 있다. 엔트리 목록을 돌려주는 함수와 엔트리의 바이트를 돌려주는 함수이다.
Aqueous에서 둘은 다음과 같이 표현된다.

```
엔트리 테이블 (정적 데이터)            — 경로, 메타데이터, 크기, leaf 블록 위치 (메타데이터 블록)
엔트리 식 (제약된 함수, 노드망)       — slice / concat / pack / apply / patch, 출력 체크섬 (formula 블록)
물리 저장 (seekable zstd 프레임)     — slice가 가리키는 해제된 주소 공간 (non-leaf 블록)
모듈 (결정적 Wasm, 해시로 식별)       — apply가 부르는 순수 함수
리소스 (모델 blob, 해시로 식별)       — apply가 모듈에 넘기는 공유 데이터
```

- 엔트리 목록은 함수가 아니라 정적 테이블이다(§4.1).
- 식은 파일마다 formula 블록 하나이고, 식이 참조하는 데이터는 그 뒤에 둔다. 그래서 앞에서부터 스트리밍으로 풀 수 있다(§4.7).
- 엔트리의 바이트는 일차(first-order) 함수 식이다. 재귀, 변수, 빌트인 연산이 없고 모든 노드가 출력 크기를 선언한다(§4.2).
- 식의 리프는 물리 저장의 해제된 바이트 구간이다. zstd는 식의 노드가 아니라 그 아래의 저장 계층이다(§3).
- 식은 지연 평가된다. 실행 전체가 Kahn process network(KPN)를 이루므로 출력은 스케줄링과 무관하다(§4.3, §5.4).
- 디코드 쪽에서는 Wasm 모듈이 규범이고, 네이티브 구현은 해시로 식별되는 최적화이다(§5.7).

> **근거.** `foo.txt.gz`를 저장하면 인코더는 평문, flate 레코드, gzip 메타데이터로 나눈다. 바이트 함수는 대략
> `gzip(flate(평문, 레코드), gzip 메타데이터)`이다. 이것을 그대로 형식으로 옮기면 생기는 문제가 위 제약의 이유이다.
>
> - **목록이 함수이면** 신뢰할 수 없는 코드를 돌려야 목록이 나오고(R3), 목록만 보는 비용이 디코드 비용이 된다(R6).
> - **zstd 해제가 식의 노드이면** 리프마다 프레임이 따로 생겨 작은 조각들이 문맥을 공유하지 못한다. "랜덤 액세스 단위 =
>   max(프레임, apply)"(§4.3)도 깨진다.
> - **파생값을 식으로 계산하려 하면** fan-out이 생긴다(gzip의 CRC-32, §4.4). 빌트인 연산은 명세 면적을 키운다(R2).
> - **"함수"를 이루는 언어가 커지면** 표준화 대상이 프로그래밍 언어가 된다(R2). 그래서 노드 종류를 한정한다.

## 3. 물리 저장 [확정]

블록과 프레임은 명세 "Content blocks"와 하위 절에 있다. 프레임 크기는 랜덤 액세스 단위 상한(§4.3, §6)이 정하며 고정된
기본값은 없다(§7의 12번). 사전이 비solid 구조(R6)의 압축 손실을 메우는 주된 수단이다. 병렬 압축과 해제는 프레임
단위이고 프레임이 독립이므로 출력이 스레드 수와 무관하다. 엔트리 식의 리프 `slice`는 non-leaf 블록의 해제된 바이트를
오프셋으로 가리키며 프레임과 정렬할 필요가 없다. 그래서 작은 slice 여러 개가 한 프레임에 나란히 놓이고, 프레임
오버헤드는 slice가 아니라 프레임 수에 비례한다.

> **근거.**
>
> - 압축할지 말지는 zstd 블록 안의 결정이므로, 전부 zstd로 처리한다고 정해도 표현력을 잃지 않는다.
> - 프레임을 자유롭게 조정할 수 있으면 사전 학습과의 긴장이 풀린다(모든 exe의 `ST_OP` slice를 같은 사전의 프레임들에).
> - 재압축기가 컨테이너 안에서 쓰던 내부 zstd는 이 계층으로 넘어왔다. 레벨이나 long-distance matching도 아카이브
>   인코더의 프레임 결정이 된다.

> **실측: solid, 프레임 크기, 사전.** `scripts/zstd_dict_*.py`, 결과는 `scripts/zstd-dict-*.md`와 `.json`.
> libzstd 1.5.7 레벨 3, 경로순 파일을 N바이트 프레임에 파일 경계를 지키며 묶고, 공유 사전(64K–1M, fastCover)을 쓰거나
> 쓰지 않았다(사전 크기 포함). 표본은 rustdoc HTML 558 MB, cargo registry `*.rs` 579 MB, macOS SDK 헤더 123 MB,
> Python stdlib 37 MB, zstd의 github_users 7.5 MB.
>
> - 파일마다 프레임을 두면 solid 대비 1.13–5.34배, 사전을 쓰면 1.05–1.73배이다. cargo처럼 거의 같은 파일들 사이의
>   중복은 사전이 잡지 못한다(같은 프레임에 모으거나 `patch`, §4.3).
> - 프레임을 키우면 사전의 이득이 줄어 16 MB 이상에서 0이 된다. rustdoc, 사전 없음 → 1M 사전(solid 대비): 파일마다
>   4.56× → 1.73×, 64K 2.23× → 1.44×, 1M 1.20× → 1.12×, 16M 1.010× → 1.009×.
> - 파일 하나를 꺼내는 속도는 프레임 크기에 따라 급격히 떨어진다(평균 10–20 KB 파일): 파일마다·16K 0.7–1.8 GB/s,
>   64K 0.2–0.8 GB/s, 1M 23–90 MB/s, 16M 1–16 MB/s. zstd는 블록(최대 128 KB) 단위로 해제하기 때문이다.
> - 같은 꺼내기 속도에서는 16K–256K 프레임 + 사전이 파일마다 프레임 + 사전보다 일관되게 작다(§7의 11번).

## 4. 엔트리와 엔트리 식

### 4.1 엔트리 테이블 [확정]

명세 "Metadata block", "Content blocks", "Formula block"에 있다. 경로, 심링크, 파일별 체크섬, 같은 내용 파일의 중복
제거는 아카이브의 것이고, 모듈은 파일 *내용*만 만든다.

### 4.2 노드 [구현]

노드의 종류와 인코딩, 크기와 자원 선언은 명세 "Formula data"와 "Formula evaluation"에 있다. 명세는 식을 스택 기계로
적는다. 이 문서는 다음 표기로 쓴다.

```
node := slice(offset, len) | concat(node, ...) | pack(node, ...) | apply(module#, resources, params, [input, ...]) | patch(node, node)
```

```
PE:   concat(slice(0,0x400), apply(disfilter, {}, {origin,is64}, [slice(a0,l0), ..., slice(a27,l27)]), slice(...))
gzip: concat(slice(gzip 헤더), apply(flate-set, [R6], {02}, [slice(평문), slice(레코드), concat()]))
```

컨테이너 층은 모듈이 아니라 `concat`으로 표현한다. 모듈은 순수 함수이고 서로를 모르므로 링크가 없다.

> **근거.** disfilter는 실행파일의 *일부*에만 적용되므로 앞단에서 파일을 쪼개야 한다. 이것을 모듈이 하면 변환 그래프가
> 네트워크 문제가 되고 모듈끼리 링크하는 단계까지 필요해진다. 그런데 디코드 쪽의 splitter는 사소하다. 어디서 자를지는
> 인코더가 정해 기록했고 디코더는 이어 붙이기만 한다. 그래서 디코드 쪽 합성 구조는 **인코드 시점에 확정된 정적 식**이다.
> "모듈이 orchestrator처럼 느껴진다"는 것은 선언적 데이터를 명령형 코드로 표현하고 있다는 신호이다.

### 4.3 평가 의미론 [구현]

평가는 명세 "Formula evaluation"에 있다(구현은 `docs/eval-design.md`). 지연 평가의 규칙은 다음과 같다(`x[a:b]`는
Python식 구간).

```
slice(o, n)[a:b]      = slice(o+a, b-a)
concat(x, ys...)[a:b] = x[a:b]                                   if b <= len(x)
                      = concat(ys...)[a-len(x) : b-len(x)]       if a >= len(x)
                      = concat(x[a:], concat(ys...)[:b-len(x)])  otherwise
apply(...)[a:b]       = apply(...)를 b까지 평가한 출력의 [a:b]
patch(s, d)[a:b]      = patch(s, d)를 b까지 평가한 출력의 [a:b]
```

- `slice`와 `concat`은 실체화 없이 접힌다. 컨테이너 층을 `concat`으로 쓰면 그 층의 비용은 0이다.
- `apply`와 `patch`는 strictness 장벽이다. 그래서 **랜덤 액세스 단위는 `max(프레임 크기, 가장 큰 apply 노드)`**이고,
  인코더는 "랜덤 액세스 단위 상한" 하나로 둘을 함께 제한한다(§6).
- **부분 디코드 진입점 [보류].** 모듈이 `apply(…)[a:b]`의 재작성 규칙을 스스로 제공하는 장치이다(상태를 리셋하는
  지점의 색인: disfilter의 call cache 리셋, aqr-flate의 세그먼트와 체크포인트).
- 다른 파일의 내용은 import로 가져온다(명세 "Import block", "Overlay archives and imports"). 같은 세그먼트 안의 앞
  파일을 base로 쓰는 방법은 아직 없다(§7의 10번).
- 독립된 서브식의 병렬화는 호스트가 맡고, 모듈 내부의 병렬성은 §5.5이다.

> **근거: 포맷별 재압축기는 대부분 파일 하나가 최소 랜덤 액세스 단위이다.** jpeg(재인코딩 청크가 비트 단위로 이어
> 붙는다), mp3(bit reservoir), psd(평면이 파일 전체에 퍼짐), sqlite(인덱스 복원에 테이블 전체), flac(잔차 모델이
> 프레임에서 프레임으로), obj(블록에 걸친 예측 상태), pdf(토큰 코더 상태가 스트림 사이로). git은 반대로 파일마다 따로
> 복원할 수 있지만 비용이 의존 관계(delta 체인)로 정해진다. 상태를 주기적으로 리셋하는 비용은 aqr-obj에서 64 MB 구간
> 0.35%, 32 MB 0.9%, 8 MB 2.1%였다.

> **근거: 파일 사이의 참조.**
>
> - **엔트리 번호로 가리키는 `ref(file#)`는 두지 않았다.** 메타데이터 블록이 세그먼트 끝에 있어서 스트리밍 디코더는
>   번호가 어느 leaf인지 모르고, 뒤 세그먼트가 그 경로를 바꾸면 의미도 흔들린다. 같은 내용은 `file_offset` 중복 제거가
>   맡으므로 남는 것은 B = f(A, patch) 꼴뿐이다.
> - **세그먼트 밖은 블록이 아니라 경로로 가리킨다.** 블록 수준의 교차 참조는 세그먼트 자기완결성을 깬다. 경로로
>   가리키면 앞선 세그먼트(증분 백업)와 외부 base가 같은 장치가 된다.
> - **외부 base는 별도 포맷(overlay archive, magic 변형)이다.** 파일만으로는 풀 수 없는 입력이므로 열자마자 알아야
>   한다. 전체 트리가 아니라 overlay인 것은 반대 방향을 표현할 수 없어서이다(tombstone으로 트리 전체를 바꿀 수 있다).
> - **Patch는 모듈이 아니라 명령이다.** 디코더의 zstd 블록 디코드에서 사전 자리만 식의 값으로 바꾼 것이라 Wasm 없는
>   디코더도 delta를 풀고 속도도 네이티브 zstd 그대로이다. 블록 속성으로 두면 블록 체크섬 때문에 블록을 혼자 검증할 수
>   없다. libzstd 1.5.7은 match offset을 사전 시작과만 비교하므로 "source 전체와 지금까지의 출력"을 참조할 수 있다.
> - **base 쪽 정변환도 아카이브에 들어간다.** 분석된 수준에서 diff하려면 디코더가 base를 분해해야 한다
>   (Courgette/Zucchini, puffin). 결정은 압축기가 params로 기록하고 모듈은 자르기만 한다. diff에 좋은 표현(disfilter
>   스트림, Huffman만 푼 토큰)은 압축에 좋은 표현(aqr-flate 레코드)과 다르다.

### 4.4 엔트리 안의 공유 [보류]

명세의 식은 모든 값이 정확히 한 번 쓰이는 트리이다. 공유(DAG)를 넣는다면 앞선 값을 다시 push하는 명령 하나로 넣고,
공유 노드에서 나가는 간선마다 용량 C("C면 충분하다", 인코더가 재서 기록, 디코더는 더 써도 된다)를 선언한다. 파생값
(체크섬, 길이)은 빌트인 노드 없이 저장하거나 그것을 계산하는 모듈이 만든다.

> **근거: 보류한 이유.** 동기였던 파생값은 모듈이 만들거나(flate-set의 파라미터가 gzip 트레일러, ZIP의 CRC와 크기, zlib의
> Adler-32를 유도한다) 저장한다. 파일 안의 중복은 모듈이, 엔트리 사이의 공유는 import와 다중 출력이 맡는다. 반면
> 비용은 구체적이다. 트리에서는 교착이 생길 수 없지만, 공유가 있으면 C를 과소 선언했을 때 유한 채널 KPN이 인위적
> 교착에 빠지고, 모든 구현이 교착 탐지를 갖춰야 한다. 스택 기계는 사용 횟수가 1인 SSA이므로 나중에 제약만 풀면 DAG가
> 되어 포맷을 깨지 않는다. KPN에서 채널 용량을 늘리면 블로킹이 줄 뿐 새 교착이 생기지 않으므로 C를 하한 보장으로
> 정할 수 있고, 필요한 C는 소비자들의 진행 차이(부모 구조와 데이터)로 정해지므로 모듈의 성질이 아니다.

### 4.5 합성과 융합 [잠정]

- 범용 내용물의 기본 경로는 식을 통한 합성이다(`apply(flate-set, [평문 식, 레코드, …])`의 평문 쪽에 다른 노드).
- 속도가 중요한 포맷별 모듈은 다른 재압축기를 *소스 수준 라이브러리*로 포함해 층을 융합해도 된다. 대가는 모듈 크기와
  모듈 사이의 코드 중복이다. 코드는 공유하지 못하지만 모델은 리소스로 공유할 수 있다(§5.6).
- 임베디드 파일은 출력 안의 연속된 구간이므로 식으로 끌어올린다. 각 재압축기의 `formula`가 그렇게 한다.

> **근거.**
>
> - **aqr-png는 일부러 합성하지 않는다.** 풀고, 평문을 이미지 모델로, aqr-flate로 스트림을 재현하는 합성은 PNG 기준
>   1–25 MB/s였다. 그래서 LZ77 토큰을 픽셀 문맥으로 코딩한다(한 모듈 안의 융합).
> - **aqr-pdf는 스트림마다 고른다.** full(합성), tok(토큰 재코딩, 융합), dup(파일 안 중복) 중 *크기 + λ·시간*이 작은
>   것을 시간 예산 안에서. 모두 합성하면 CC 표본에서 0.810에 29 / 55 MB/s, 예산을 건 계획은 0.864에 157 / 186 MB/s였다.
>   PDF 스트림은 풀면 2–12배로 커지기 때문이다.
> - **aqr-zip은 합성이다.** DEFLATE 본문은 flate-set 하나가 이어서 만들고 zip-recons가 그 출력을 받는다. 엔트리마다
>   노드를 두면 식이 엔트리당 5–10 B 늘어서 색인을 택했다. flate-set의 파라미터 `04`가 본문마다 CRC-32와 크기를 그
>   앞에 두어, zip-recons가 로컬 헤더를 본문보다 먼저 쓴다(그래서 둘 다 부분형이다, aqr-zip `FORMAT.md`).
> - **바이트만 오가는 인터페이스의 비용.** 합성을 잘게 할수록 모듈 사이의 중간 표현(토큰 직렬화, 계수 배열)이 저마다
>   동결해야 할 포맷이 된다(R2). 융합을 막지 않는 이유가 하나 더 있는 셈이다.

### 4.6 다중 출력 `apply` [구현]

`apply`의 출력 k개, formula 블록의 출력 여럿, 모듈의 출력별 메모리는 명세 "Formula data", "Formula evaluation",
"Module execution"에 있다. 쓰는 곳은 차분 이미지 세트(`png-set`)와 클래스별 패치(`Formula::merge_classes`)이다.
남은 것: 엔트리를 꺼낼 때 의존 폐포의 바이트 상한(랜덤 액세스), 출력별 진입점(§4.3의 부분 디코드와 같은 장치).

> **근거: 차분 이미지 세트(2026-10-26).** 같은 그림의 레이어를 켜고 끈 변형 PNG(Clip Studio Paint, RGBA 683.7 MB,
> 같은 크기 그룹이 13–88장)에서 부모와 다른 픽셀은 4–18%이지만 그 차이가 행의 74–91%에 걸친다.
>
> - 압축된 바이트로는 거의 맞지 않는다. PNG 파일에 zstd -3 `--patch-from`을 걸면 11%만 준다(Huffman 트리, 블록 경계,
>   비트 위상).
> - LZ77 토큰은 맞는다. 풀린 데이터의 256 B 구간이 같은 비율인 부모를 최대 신장 트리로 고르면 같은 위치에서 같은
>   토큰이 85.0%이다.
> - 참조 체인이 깊다(트리 깊이 13–21). 풀린 데이터에 `--patch-from`을 체인 길이 D로 제한하면 685.5 MB가 D=1 303–310,
>   D=4 157–163, 무제한 128–131 MB이다. 그래서 그룹 하나를 장마다 출력 하나인 `apply`로 둔다. 남는 제약은 DFS 순서로
>   풀 때 살아 있는 조상의 바이트이다.

### 4.7 블록 구성과 스트리밍 [구현]

세그먼트, 블록 부류와 타입, 체크섬, 블록 배치 규칙은 명세 "Content blocks", "Formula block", "Formula data"에 있다.

> **근거.**
>
> - **formula가 앞에 온다.** 데이터 뒤에 오면 디코더가 formula까지 데이터를 모두 버퍼링해야 한다. 재압축기는 어차피
>   파일 전체를 분석하고 검증한 뒤에 기록하므로 먼저 쓰는 비용이 없다.
> - **수명.** non-leaf 블록이 모든 참조자보다 뒤에 오면, 블록이 도착할 때 참조자가 모두 알려져 있다. 그래서 참조
>   횟수(`refs`)는 중복 정보이다.
> - **chunk를 두지 않는다.** `concat`이 non-leaf 블록 여럿을 이으면 파일 안 랜덤 액세스가 되고 필요한 블록만 풀린다.
>   프레임마다 compressed와 uncompressed를 고를 수 있고, 작은 파일 묶기(§7의 11번)와 장치가 같다. 대가로 프레임 색인이
>   formula에 들어가지만, 프레임당 비용(압축된 블록 크기 2–4 B)이 seekable format의 seek table(8–12 B)보다 작다.
> - **non-leaf 블록의 체크섬은 필수이다**(명세 "Data block"의 노트). 손상이 resource failure로 나타나지 않게 하려고
>   선택에서 필수로 바꿨다. 실제로 푸는 단위가 non-leaf 블록이므로 깊이 1이면 충분하다.
> - **formula의 출력 체크섬은 선택이다.** 저장 이후의 손상은 블록 체크섬이 잡으므로, 출력 체크섬이 더 검증하는 것은
>   `apply`의 평가뿐이고 인코더의 왕복 검증과 서로 대신할 수 있다.
> - **formula를 따로 압축하는 손실**은 zstd 사전이 메운다(formula 하나에 대략 7–9 B).
> - **세그먼트의 자기완결성.** 모듈, 리소스, 사전은 세그먼트마다 한 번 저장된다. 중복은 자기완결성의 대가이다.

## 5. 모듈 실행 환경

명세 "Module execution"이 규범이다. 메모리 추정(지금의 선언 방식)은 `docs/arena-design.md`, Wasm 실행의 격리는
`docs/sandbox-design.md`에 있다.

### 5.1 Wasm 프로파일 [확정]

Wasm 3.0 core를 deterministic profile로 실행하고, 3.0에서 더해진 기능은 multiple memories와 I/O 메모리의 64비트 주소만
허용한다(명세). 역변환 경로에서 libm 초월함수는 쓰지 않고 올바르게 반올림된 상수 표를 쓴다 [잠정]. 인코더가 비트
동일성을 검사할 때는 NaN을 따로 다뤄야 한다.

> **근거.**
>
> - **SIMD128은 남긴다.** WAH JIT는 SIMD를 컴파일하고(WAH 8199b6b), `+simd128` 빌드가 SIMD 없는 빌드와 같은 속도로 돈다.
>   aqr-raw의 LMS 단(FLAC, PCM)은 simd128 경로로 63 MB FLAC가 2.25 → 0.63 s, PCM 17 MB가 0.28 → 0.12 s였다
>   (`i32x4.dot_i16x8_s`의 합이 NEON처럼 2^32로 감긴다). simd128은 그 함수들에만 `target_feature`로 켠다. 모듈 전체를
>   `+simd128`로 빌드해도 다른 모듈은 잡음 밖으로 달라지지 않고 크기만 0.3% 컸다.
> - **relaxed SIMD는 뺀다.** 같은 일을 하는 non-relaxed 명령이 있어 얻는 것이 없고, deterministic profile을 잘못 구현한
>   엔진에서 결과가 갈릴 여지만 생긴다.
> - **작업 메모리에서 memory64를 뺀다.** wasm32에서는 가드 페이지 덕에 경계 검사가 사실상 공짜다.
> - **libm.** 플랫폼마다 마지막 ulp가 다를 수 있고, 네이티브 빌드(시스템 libm)와 wasm32 빌드(모듈의 libm)가 갈려
>   네이티브 치환의 동치(§5.7)가 깨진다. aqr-jpeg의 DC 예측 가중치 `cos()`를 상수 표로 바꿨다.
> - **부동소수점은 역변환 경로에 있다**(jpeg의 DC 예측, obj의 법선, sqlite의 실수, psd의 블렌드). 교훈: 정규 NaN 차이는
>   인코더가 "네이티브에서 왕복이 된다"고 판단한 것을 Wasm 디코더가 뒤집는 형태로 나타난다(sqlite의 f32 → f64 승격은
>   NaN을 그 경로로 보내지 않도록 인코더를 고쳤다).

### 5.2 자원 [확정]

- 형식은 한계를 선언하고 디코더는 정책으로 집행한다(R4). `memory.grow`가 선언된 최대치 안에서 반드시 성공해야 결정성이
  유지된다(명세).
- **메모리.** 적용의 메모리 한도는 모든 메모리의 합계이고 실행 전에 알 수 있다. 그 값을 인코더가 어떻게 정하는지와,
  태스크가 있을 때 그 값을 정하기 어려운 문제는 §5.5에서 다룬다.
- **시간.** fuel(명령 개수)은 명세에 없다. 블로킹 import(`request`, `commit`)와 `heartbeat`가 체크포인트이다.
- 스택 고갈, 시간 초과, 선언 초과는 의미론이 아니라 **자원 실패**이다.

> **근거.** 명령 개수 기반 fuel은 DoS 방어로서 naive하고(실제로 막아 보며 확인했다), 명세에 넣으면 모든 구현이 명령
> 단위로 똑같이 계량해야 해서 JIT가 사실상 불가능해진다. 시간 제한의 집행 비용은 엔진의 몫이다(Cranelift의 epoch 검사
> 8–19%, §5.7).

### 5.3 데이터 전달과 ABI [구현]

메모리 import(작업, 파라미터, 리소스, 입력, 출력), 전체형과 부분형, 창과 ring, `request`/`release`/`commit`/
`heartbeat`/`log`는 명세 "Module execution"에 있다. 부분형인 모듈: `flate-inflate`, `flate-set`, `bcj-delta`,
`zip-recons`(2026-11). 창은 모듈이 `entry! { part fn … windows(…) }`로 선언하고 aqr-ld가 import의 maximum으로 바꾼다.

**구현 노트.**

- `slice` 리프는 블록을 풀어 소비자의 창에 복사한다. 자식 `apply`의 출력은 간선마다 복사 한 번이다.
- 전체형에서 전체형으로 가는 간선은 출력 메모리를 소비자의 import로 넘길 수 있다(꼬리는 0으로).
- 부분형의 평가는 값의 그래프 위에서 스레드와 큐(배압 16 MiB)로 한다. 출력이 여럿인 생산자의 간선은 기다리게 하지
  않고 넘치는 바이트를 파일에 내보낸다(`docs/streaming-encoder-design.md`).

> **근거.**
>
> - **데이터 전달.** 미리 지정된 메모리 + 오프셋, 모듈이 노출한 allocator, 모듈이 읽어 들이는 pull 중 첫 번째를 택했다.
>   multiple memories가 별도의 이름 공간을 주므로 allocator 의미론이 필요 없다. pull은 seek(pread)과 모듈이 고른 버퍼
>   크기가 성능을 좌우하는 문제를 부른다.
> - **`mod W` 창.** 절대 오프셋을 유지하며 호스트가 [0, lo)를 반납하는 방법은 Wasm 메모리를 줄일 수 없어 구현마다
>   다르다. 창이면 ring buffer가 그대로 개념이 되고 메모리가 W로 고정되어 예산과 맞물린다. 대가는 wraparound와
>   `memory.copy`의 분할이다.
> - **창은 `request`와 `commit` 안에서만 바뀐다.** 생산자 출력을 소비자 창으로 별칭하면 가시 구간 밖의 바이트가
>   스케줄에 따라 달라지고, 그것을 읽는 버그 모듈은 인코더의 왕복 검증(한 가지 스케줄)으로 잡히지 않는다(R1, R2).
> - **ring 창은 모듈의 속성이다.** 선형 창은 데이터 길이로 정해지고, 고정 ring(deflate의 32K)은 모듈의 것이다.
>   데이터에 따라 달라지는 창은 작업 메모리로 옮겼다. 네이티브 구현도 같은 W로 돌아야 놓은 바이트를 읽는 모듈이
>   어디서나 같은 값을 본다.
> - **입력 슬롯은 정적이다.** 가변 개수는 `pack`(명세 "Packed byte sequences")이나 이어 붙인 스트림 + 색인으로 한다
>   (flate-set의 색인, aqr-git의 스트림 10개).
> - **출력은 임의 쓰기다.** aqr-psd(평면을 함께 디코드), aqr-sqlite(overflow 페이지를 셀과 함께), aqr-raw(PCM 제자리).
> - **I/O 메모리는 memory64.** 4 GiB가 넘는 PSB나 SQLite는 출력 하나가 wasm32의 한계를 넘는다.
> - **전체형을 따로 둔 이유.** g(f(x))에서 출력 메모리를 넘겨주는 것이 복사와 구별되지 않으려면 "입력은 처음부터
>   채워져 있고 출력은 종료 시점 내용"이라는 정의가 필요하다. 두 entry를 함께 export하는 것은 금지했다(memory import는
>   모듈 단위이고, 호스트가 경로를 고르면 두 경로가 다를 때 디코더마다 결과가 갈린다).
> - **진단은 nop인 `log` 하나이다.** 결과가 호스트의 표시 방식에 좌우되지 않게 하기 위해서이고, `fatal`은
>   `log` + `unreachable`이다.

### 5.4 블로킹과 일시 정지 [잠정]

명세는 `request`, `commit`, `join`, `send`, `recv`가 기다릴 수 있다는 것만 정한다. 구현은 엔진의 일시 정지, 파이버,
노드마다 OS 스레드 중 무엇이든 되고, 노드망이 KPN이므로 출력은 같다. 일시 정지는 import 지점의 협조적 방식으로
충분하다(선점은 시간 예산의 장치이다). 레퍼런스 디코더의 wasmtime 경로는 파이버(`call_async`)이다(§5.5).

- **요구 구동(pull) 스케줄링.** 바이트열마다 소비자가 하나인 트리라면 한 스레드로 돌 수 있다. 소비자의 `request` 안에서
  호스트가 생산자를 중첩으로 재개하고, 생산자의 `commit`은 바이트를 호스트 버퍼에 옮긴 뒤 양보를 청한다. 생산자 하나에
  소비자가 여럿이 되면(다중 출력, 채널) 비울 소비자가 스택에 없으므로 진짜 블로킹이 필요하다. 레퍼런스 디코더는 부분형
  적용을 자기 스레드에서 큐로 잇는다(§5.3).

> **근거: 엔진의 현황(2026-10).** wasmi는 `call_resumable`, wasmtime은 `call_async`(파이버)로 호스트 함수 안에서 멈춘다.
> wasm3는 Wasm 호출이 네이티브 재귀라 스레드 방식만 된다. WAH는 실행 전체의 일시 정지와 재개(`wah_start`/
> `wah_resume`)는 있지만 호스트 함수 *안에서* 멈추지 못한다. 확장안은 재시도 의미론이다: call 직전에는 늘 POLL이 있으므로
> 호스트 함수가 "아직 실행하지 않음"을 돌려주면 IP를 call로 되돌려 SUSPENDED로 들어가고, 재개하면 같은 호출을 다시
> 실행한다(bulk 연산의 `WAH_BULK_YIELD`가 이미 그렇다). ABI에서 우회(`request`가 "준비 안 됨"을 돌려주고 모듈이
> 양보)하는 방법은 엔진의 사정이 ABI로 새어 나오므로 택하지 않는다.

### 5.5 모듈 내부 병렬성

#### 태스크와 채널 [구현]

결정적 fork-join(task)과 task 사이 채널은 명세 "Module execution"의 "Tasks"에 있다. 공유 메모리, 원자 연산, 락은 없고
Wasm threads도 쓰지 않는다. task 수와 분할은 데이터로 정하며 모듈은 스레드 수를 볼 수 없다. 결과는 join 결과와 채널
메시지로만 오가므로 스케줄과 무관하다(KPN).

**구현 노트.**

- **aqr-api와 aqr-ld.** aqr-ld가 만드는 `aqr_task`가 `__stack_pointer`를 `arg & -16`으로 놓고 aqr-api의 `aqr_task_body`를
  부른다. `arg`는 인라인되지 않는 `spawn_record`의 프레임에 둔 기록(task가 부를 함수와 클로저)이다. 그 프레임이
  호출자들보다 아래에 있어서, 클로저가 빌린 것은 task의 스택 위쪽에 그대로 남는다(`spawn` 안에 두었더니 인라인된
  호출자의 지역 변수를 task의 스택이 덮었다).
- **aqr-common.** `pool::par_map_apart`가 Wasm에서 항목마다 task를 돌리고 결과를 `wire::Wire`로 바이트로 만든다. 그 밖의
  `par_map`, `scope`는 Wasm에서 직렬이다. 모듈 바이너리는 스레드 수를 상수로 주고(`whole!(slots N, …)`, flate-set은 8),
  출력은 그 수와 무관하다. `OnceLock` 표는 `spawn` 전에 부모가 만들어 두면 사본으로 물려받는다.
- **wasmtime(aqr-decompress).** task 하나가 Store 하나이고, 모든 인스턴스를 `call_async`로 돌리며 `join`, `send`,
  `recv`는 async 호스트 함수이다. 실행기(`exec`)는 적용하는 스레드와 aqr-common `pool`의 워커들이 깨어난 future를 poll하는
  것이고, task 수와 OS 스레드 수가 분리된다. 큐가 비었고 poll 중인 스레드도 없는데 첫 future가 끝나지 않았으면 교착이다.
  waker는 잠금을 푼 뒤에 깨우고(인스턴스의 drop이 채널을 잠그는 재진입), 끝난 적용에 남은 future는 실행기가 약한
  참조로 기억했다가 drop한다(waker와 Store의 순환 참조).
- **작업 메모리의 사본(`cow`).** macOS는 `vm_copy`로 스냅샷과 task 메모리를 CoW로 복사한다. Linux에는 익명 private
  메모리를 fork 없이 CoW로 스냅샷하는 방법이 없어서 0이 아닌 페이지만 복사한다. Windows는 `docs/sandbox-design.md`.
  `spawn`이 묶음인 것은 이 복사를 task마다가 아니라 spawn마다 한 번으로 하려는 것이다.

> **근거: 측정(M4, 2026-10-27).** 48 MB 텍스트를 gzip -6한 8.0 MB를 모든 모듈을 wasmtime으로 돌려 풀었다. flate를
> 직렬로 두면 0.74–0.77 s, 세그먼트 배치를 task로 돌리면 0.45 s, 스냅샷을 CoW로 하자 0.37–0.41 s(네이티브 10코어
> 0.15 s). task 하나의 준비(instantiate, 143 MB 작업 메모리 생성과 스냅샷 복사)가 memcpy로는 10–13 ms로, task가 하는
> 일(세그먼트 약 1 MiB)과 비슷했다. CoW로 0.05–0.9 ms가 되었다.
>
> **근거: FLAC과 PCM의 파이프라인.** aqr-raw `audio::par::apart`가 네이티브 파이프라인과 같은 단계를 task와 채널로 돈다
> (앞단, 오차 디코드, LMS가 task 하나씩, 작업 task 다섯이 배치 `k mod 5`). wasmtime에서 FLAC 63 MB가 직렬 2.25 s →
> SIMD128 0.63 s → 파이프라인 0.40–0.43 s(네이티브 0.19 s), PCM 17 MB가 0.28 → 0.12 → 0.07 s(0.02 s). 시험
> `pipelines_fail_alike`가 모든 스트림을 차례로 망가뜨려 네이티브와 Wasm이 같이 실패하는지 본다.
>
> **근거: 옮기지 않은 파이프라인.** Wasm 속도와 모듈 크기를 함께 재서 판단했다. png-recons의 블록 writer(6.6 MB PNG
> 0.125 → 0.127 s, 블록 +2.5 KB), psd-recons의 행 reader와 writer(59 MB 1.27 → 1.24 s, 78.1 → 82.4 KB), mp3의 사이드
> 정보(네이티브에서도 1→10스레드가 0.17 → 0.16 s).
>
> **근거: 채널의 규칙.** `try_recv`, select, 받는 쪽 닫기는 없다(결과가 도착 시점에 달린다). task의 실패는 바로 적용의
> 실패이다(실패한 task를 기다리던 다른 task가 영원히 기다리면 자원 실패가 invalid archive로 바뀐다). 끝날 때 닫히는 것은
> 보낸 적이 있는 채널뿐이므로 보낼 것이 없을 수도 있는 task는 직접 닫는다.
>
> **근거: 10 GB 벤치마크(2026-10-27).** 2.669 GB 아카이브를 네이티브 16.1–16.8 s, `--wasm` 26.2–29.2 s에 풀었다(최대
> footprint 2.55 → 5.67 GB). 모듈별로는 대부분 1.8배이고, exe-recons/x86만 6.4배였다(적용 2095번 각각에 입력 메모리
> 46개를 만들고 채우는 약 7.5 ms).

#### 태스크의 메모리: `aqr_spawn_v2` [제안]

**문제.** 메모리 한도를 실제 사용에 맞게 정할 수 없다.

- 명세의 task는 spawn한 인스턴스의 작업 메모리 *전체*의 사본에서 시작한다. Wasm 메모리는 줄지 않으므로 사본은 부모가
  그때까지 쓴 최대치(high-water)이고, 부모가 쥐었던 큰 버퍼가 모두 task마다 들어간다.
- 적용의 메모리 한도는 부모, task, 채널 메시지의 합 하나이고, 동시 실행 수(슬롯)는 spawn한 인스턴스마다 센다. 그래서
  사용량이 "동시에 도는 task 수 × 각 task가 시작할 때의 부모 크기"에 달리고, 중첩 spawn에서는 슬롯이 단계마다 곱해진다.
- 인코더가 선언하는 한도는 모듈마다 손으로 쓴 추정 함수(`docs/arena-design.md`)이다. 사용량이 부모의 할당 이력과 스케줄에
  달리므로 추정은 근사가 될 수밖에 없다. 2026-11-06 flate-set을 부분형으로 옮기며 본 것: 처음 추정이 10스레드 실측보다
  낮아 실패했고(배치 버퍼를 task 8개가 복사), 고친 뒤에도 한도가 실측의 1.7–66배로 흩어졌다(text.gz 4.3배, ZIP의 쥔
  스트림은 task 사본 때문에 830 MB를 쓰다가 task를 끄고 66 MB). exe-recons/x86은 지금도 추정이 실측보다 작다(cygwin의
  ZIP에서 0.71–0.96배).
- 네이티브에서 할당을 재는 방식(allocator double)으로 바꿔도 같은 이유로 결정적이지 않다. task의 사용량이 그 task를
  spawn할 때의 부모 크기와 스케줄에 달리기 때문이다.

**제안.** task가 무엇을 받는지를 부모가 정하고, task의 메모리 한도를 task 종류(클래스)마다 따로 둔다.

1. **`aqr_spawn_v2(class, nregions, regions, arg, n)`.** `regions`는 부모 작업 메모리의 레코드 배열이고, 레코드 하나가
   12 B: `le32 src`, `le32 len`, `le32 dst`.
   - spawn할 때 레코드들과 그것이 가리키는 부모의 바이트를 읽는다(그 뒤 부모가 바꾼 것은 task에 보이지 않는다).
   - task는 새 인스턴스이다(데이터 세그먼트, global의 초깃값). 작업 메모리는 초기 크기에서 레코드들의 `dst + len`을
     덮도록 키우고, 레코드 순서대로 [`dst`, `dst + len`)에 부모의 [`src`, `src + len`)을 쓴다(겹치면 뒤의 것).
   - 진입과 결과는 지금과 같다(`aqr_task(arg, i)`, `aqr_result`, 핸들의 `join`과 `take`). `arg`는 숫자 하나이므로, 그것이
     가리키는 기록(task가 부를 함수와 클로저, 공유 조각의 주소와 길이)도 레코드가 덮어야 한다.
   - 이 바이트들과 task가 더 키운 메모리가 그 클래스의 한도에 든다.
2. **기존 `aqr_spawn(arg, n)` ≡ `aqr_spawn_v2(0, 1, [(0, |W|, 0)], arg, n)`**, |W|는 spawn할 때의 작업 메모리 크기이다.
   지금의 동작 그대로이고, CoW는 구현의 최적화로 남는다.
3. **클래스는 `aqr_task_slots`로 선언한다.** 그 custom section의 바이트 k가 클래스 k의 동시 실행 수이다(0부터). 지금의
   한 바이트 섹션은 "클래스 0만"이 되어 기존 모듈이 그대로 맞는다.
4. **동시 실행 수는 클래스마다 적용 전체에서 센다**(지금은 spawn한 인스턴스마다).
5. **task는 자기 클래스보다 큰 클래스만 spawn한다**(적용의 인스턴스는 아무 클래스나).
   - 적용 전체에서 슬롯을 세면, 같은 클래스의 task를 spawn하고 join하는 task가 슬롯을 쥔 채 기다려 교착할 수 있다.
     기다리는 task를 세지 않으면 그 메모리가 상한에서 빠진다.
   - 클래스가 비순환이면 가장 큰 클래스는 기다리지 않고 끝까지 돌므로 교착이 없고, 상한이 중첩 깊이와 무관하다.
6. **한도는 클래스마다.** `Apply`의 메모리 한도가 1 + (클래스 수)개가 된다: 적용의 인스턴스, 그리고 클래스마다 task
   하나. 적용 전체의 상한은 **인스턴스 + Σ_k (클래스 k의 동시 실행 수 × 클래스 k의 한도)**이고 스케줄과 무관하다.
   한도가 하나인 적용(이미 나온 아카이브)은 지금의 규칙(합계 하나, 슬롯은 인스턴스마다, 중첩 허용)을 따른다.
7. **한도를 재서 정한다.** 사전 검증은 적용을 모두 네이티브로 돌린다(`docs/streaming-encoder-design.md`의 4단계). 그때
   할당자 double이 인스턴스의 최대치와 클래스마다 task의 최대치를 재고, 인코더는 그것에 여유를 더해 선언한다.
   v2의 task는 받은 바이트와 자기가 키운 것만 쓰므로 그 최대치가 부모의 크기와 스케줄에 달리지 않는다. 클래스 0(전체
   사본)의 task는 spawn할 때의 인스턴스 크기 + 자기 증가로 잰다.
   - 남는 오차는 네이티브와 wasm32의 차이(포인터 너비, 구조체 배치, dlmalloc)이다. 표본(`aqr-decompress-memory`)으로
     비율을 재서 여유를 정하고, `estimates_hold`가 부분형 적용까지 확인하게 한다(지금은 입력을 기록하지 않아 건너뛴다).
   - 사전 검증이 돌리지 않는 적용(기록으로 대신하는 것)만 추정 함수를 쓴다.
   - [정함] 두 가지로 잰다. 기본은 double + 보정 여유(싸다). 높은 레벨에서는, 그리고 보정과 시험에서는 사전 검증을
     Wasm(wasmtime)으로 돌려 인스턴스와 task의 최대치를 그대로 읽는다. v2에서는 이 값이 결정적이므로 정확하고, 저장할
     모듈 자체를 검증하는 것이기도 하다(§6). 비용은 압축 명령어 약 +10%와 모듈 컴파일(모듈마다 0.3–0.6 s; 미리 컴파일한
     것을 두거나 캐시한다).

**aqr-api와 aqr-common 쪽.** task 코드가 받는 것은 지금도 `&[u8]`이므로 주소만 바뀐다. aqr-api는 공유할 조각을 task의
초기 메모리 끝 위(`memory.grow`가 더할 자리)에 놓는 레코드를 만들고, 기록에 새 주소를 적어 넘긴다. dlmalloc은 메모리
끝 뒤로 자라므로 겹치지 않는다. `par_map_apart`에 공유할 조각을 명시하는 형태를 더하고, 모듈은 이득이 큰 것부터 옮긴다.

**순서.**

1. 할당자 double: 지금의 추정이 모듈마다 실측과 얼마나 다른지 잰다(여유와 각 단계의 효과를 정하는 근거).
2. 명세와 호스트: `aqr_spawn_v2`, 클래스, `Apply`의 한도 목록. wasmtime 경로와 aqr-api의 에뮬레이션.
3. flate-set을 v2로: task 8개가 사본 전체 대신 세그먼트의 데이터만 받는다. 이어서 task를 쓰는 다른 모듈(prores, fasta,
   flac/pcm, jpeg 등) 중 이득이 큰 것.
4. 한도를 측정으로 선언한다. 추정 함수는 위의 대비책으로만 남는다.

**남은 질문.**

- 채널 메시지는 어느 한도에 넣는가. 지금은 적용 전체의 합에 든다. 큐는 호스트의 것이므로 인스턴스의 한도에 넣는 것이
  단순하다.
- 동시 실행 수를 적용 전체에서 세면 같은 클래스의 task들이 시작하는 순서가 서로 다른 spawner 사이의 시점에 달린다.
  출력은 KPN이므로 같지만, 채널로 서로를 기다리는 task들(파이프라인)이 모두 돌 수 있는지는 시작 순서에 달릴 수 있다.
  "파이프라인은 같은 spawn의 task끼리"로 묶을지, 그런 클래스의 동시 실행 수를 spawn 하나의 task 수 이상으로 요구할지.
- [정함] `Apply`의 한도 목록: 지금의 `memory_limit`(적용의 인스턴스) 뒤에 LEB128 `n`과 클래스마다 한도 `n`개(모두
  LEB128). `n`이 모듈의 `aqr_task_slots` 길이와 다르면 invalid archive이다.

> **근거: 사본을 다르게 하는 것이 필요한 이유.** 2026-11-06의 측정(Wasm, 10스레드, 작업 메모리의 최대): flate-set이
> enwik8.gz에서 322 MB(배치 데이터 + 쌓인 토큰 + 쓰는 중인 출력이 task 8개에 복사), 데이터를 앞에 두는 ZIP에서
> 830 MB(쥔 스트림이 복사; task를 끄자 66 MB). 같은 일을 네이티브로 하면 flate-set이 쥐는 것은 133 MB이다(1 GB 스트림
> 해제). 차이는 거의 모두 task가 쓰지 않는 바이트의 사본이다.

> **근거: post-init 스냅샷을 버렸던 이유와 다시 꺼낸 이유.** 예전 안은 task가 post-init 스냅샷에서 시작하고 명시된 입력
> 범위만 복사받는 것이었다. 그때는 병렬 경로가 모두 부모의 파생 상태(flate의 세그먼트 목록과 모델과 평문, sqlite의
> 테이블별 행, mp3의 프레임 목록)를 참조로 빌려서 전체 사본이 더 단순했다. v2는 전체 사본을 영역 하나로 표현해 그
> 단순함을 남기고, 메모리를 아낄 모듈만 영역을 좁힌다.

### 5.6 모듈과 리소스 [구현]

module 블록과 resource 블록은 명세에 있다. `apply`는 `(모듈, 리소스들, 파라미터, 입력)`이고, 모듈을 고치지 않고 모델만
재학습하거나 교체할 수 있다. 리소스는 *모델*이고 데이터는 아니다(데이터 성격의 공유 표는 입력 슬롯으로 넘긴다).

> **근거.** aqr-flate의 모델 파일(λ별 규칙 카탈로그 10개, 정적 코드의 기본 모델, 적응형 prior)은 `FORMAT.md`가
> SHA-256으로 고정하고 프로파일 번호로 부른다. 프로파일 0–9는 같은 코드에 다른 카탈로그를 쓰므로, 이미 "모듈은
> 그대로, 모델만 교체"하는 사례였다. flate-set은 이것을 리소스 둘(규칙, 기본 모델 또는 prior)로 받는다.

### 5.7 규범, 실행 엔진, 네이티브 치환 [잠정]

- **Wasm 모듈이 규범이고, 레퍼런스 디코더는 표준 모듈마다 네이티브 구현을 갖는다.** 모듈 해시로 알아보고 치환한다
  (aqr-decompress `known`). 순서: 해시를 아는 모듈은 네이티브, 모르는 모듈은 JIT, JIT가 없으면 인터프리터.
- 네이티브 구현은 같은 Rust 소스의 네이티브 빌드이다. 규범 wasm의 AOT 컴파일(wasm2c + C 컴파일러)도 방법이다(동치가
  거의 공짜이고 JIT가 금지된 플랫폼에서도 된다).
- 모듈의 일부(핫스팟)만 호스트 함수로 치환하는 방식은 두지 않는다. 치환은 모듈 단위이다.
- **적합성 수준 [제안].** 0: 모듈 없음(`slice`, `concat`만). 1: 사양 부록에 해시로 동결된 표준 모듈만(Wasm 엔진 없이
  네이티브 구현만으로 디코더를 만들 수 있다). 2: 임의의 모듈. 수준은 정확성이 아니라 쓸 수 있는 속도의 보장이다.
- **작성 지침.** 핫 루프에서 예측하기 어려운 분기는 산술식이나 `core::hint::select_unpredictable`로 쓴다. wasm32 백엔드가
  select를 분기로 바꾸기도 하고, 모든 엔진이 이를 되돌리지는 않는다.

> **근거: JIT만으로 충분하지 않은 이유.** 2배 안이라도 차이가 보이고(100 MB/s가 60–80 MB/s), iOS처럼 JIT가 제약된
> 플랫폼에서는 인터프리터(20–34배)만 남는다.
>
> **근거: 엔진별 실측**(M4, 1스레드, 10회 중 최솟값을 세 번 잰 것의 최솟값, 2026-10-22, 저장소 a8d37dc, WAH 1f1a054.
> 값은 초, 괄호는 네이티브 대비. 입력은 섞인 말뭉치 5.8 MB를 zlib -6한 2.19 MB의 flate 재구성과 1.58 MB baseline JPEG).
>
> | | 네이티브 | WAH JIT | WAH JIT + 가드 페이지 | Cranelift | Cranelift + epoch |
> |---|---|---|---|---|---|
> | flate 프로파일 6 | 0.0621 | 0.132 (2.13×) | 0.105 (1.69×) | 0.097 (1.56×) | 0.118 (1.89×) |
> | flate 프로파일 10 | 0.129 | 0.220 (1.70×) | 0.194 (1.50×) | 0.185 (1.43×) | 0.200 (1.55×) |
> | jpeg | 0.0163 | 0.0278 (1.71×) | 0.0245 (1.50×) | 0.0202 (1.24×) | 0.0226 (1.39×) |
>
> - 인터프리터는 WAH 20–34배, Pulley 24–31배. wasm2c + clang -O3는 1.05–1.32배로, wasm32라는 형식 자체의 비용에 가깝다.
> - 남은 격차: flate는 wasm32 자체(32비트 주소 확장, 스필, 조건 비교)가 1.32배로 고르게 퍼져 있었다. jpeg는 엔진의 코드
>   생성(부호 검사가 `csel` 대신 분기로 나오고 Cranelift가 되돌리지 못함)이 전부였고, 분기 없는 식으로 바꿔 Cranelift
>   1.25배가 되었다. Cranelift의 인라이닝, Spectre 완화, opt level은 효과가 없었다.
>
> **근거: 일부만 치환하지 않는 이유.** 상위 함수는 대부분 포맷 고유의 모델 루프(flate의 `code_range`, jpeg의 `walk_dec`,
> png의 `lit_run`)이고 심볼마다 적응형 모델 상태를 읽고 쓴다. 잘라 내면 그 상태까지 호스트가 가져야 해 사실상 모듈
> 전체를 치환하게 된다. 잘게 불리는 범용 커널(rANS, 비트 I/O)은 호출 비용(WAH JIT의 호스트 함수 27 ns, 게스트 함수
> 3.2 ns)이 이득을 넘는다.

## 6. 인코더 [잠정]

정변환은 압축기의 네이티브 코드여도 된다. 아카이브에는 역변환과, base를 분해하는 정변환(§4.3)만 들어간다. 디코드 쪽의
단순함은 인코더가 다음을 모두 정해 기록하는 데서 온다.

- **분해와 식 구성.** 어디를 자르고 어떤 모듈을 적용할지, 합성할지 융합할지(§4.5).
- **물리 배치.** 프레임 분할, 사전, 레벨(§3). 사전을 쓰는 프레임은 레벨을 지정해 만든 CDict
  (`ZSTD_createCDict(dict, level)` + `ZSTD_CCtx_refCDict`)로 압축한다. `ZSTD_CCtx_loadDictionary`는 쓰지 않는다.
- **블록 순서**(명세 "Block order"), **랜덤 액세스 단위 상한**(§4.3).
- **시간 예산 계획.** 시계가 아니라 추정치로 계획해야 출력이 재현된다.
- **왕복 검증.** 기본값으로 저장할 역변환을 실제로 돌려 원본과 비교한다(`docs/streaming-encoder-design.md`의 4단계:
  사전 검증은 내용 해시를 기록하고 최종 검증은 해시로 한다).
- **자원 선언.** 메모리 한도(§5.5의 제안: 재서 정한다), 공유를 넣는다면 간선 용량 C(§4.4).

> **근거.**
>
> - 정변환과 역변환이 서로 다른 코드이므로 검증이 필요하다. 재압축기들도 네이티브로 같은 일을 한다(aqr-sqlite는 압축
>   시간의 약 1/5, aqr-obj는 약 1/3).
> - 같은 소스로 빌드한 네이티브 구현으로 검증하면 저장할 모듈이 아니라 그 구현을 검사한다. 둘의 동치는 따로 시험한다
>   (aqr-decompress의 Wasm 시험이 모듈마다 네이티브와 Wasm의 출력과 실패를 비교한다).
> - 시간 예산 계획은 aqr-pdf와 aqr-git이 비용 모델로 이미 한다(§7의 5번).
> - **사전을 붙이는 방법.** `ZSTD_CCtx_loadDictionary`는 내부 CDict를 레벨 없이 만들어, 입력 크기와 무관하게 사전용 작은
>   테이블을 쓴다. binary-tree 계열(레벨 15 이상)에서 손해가 크다(32 MB 입력이 사전 없이 907 KB, 64K 사전으로
>   1,052 KB). 레벨을 지정한 CDict는 입력이 크면 사전을 입력에 맞는 테이블로 다시 읽어 1M 사전으로 886 KB가 된다.

## 7. 열린 질문

번호는 다른 문서와 명세가 가리키므로 바꾸지 않는다.

1. **ABI의 남은 것.** 툴링 다리(멀티 메모리 접근을 import로 쓰고 빌드 뒤 `memory.copy 0 k`로 치환)가 wraparound와 쪼개진
   `memory.copy`를 모듈 작성자에게서 숨길 수 있는지. 부분형의 출력 창이 ring일 때 아직 확정하지 않은 구간을
   [committed, committed + W)까지 쓸 수 있는지. 부분형 모듈의 창을 task에 줄지(명세의 Issue; §5.5의 v2와 함께 본다).
2. **엔트리 식 모델의 검증.** 해결: 모든 재압축기가 컨테이너 없는 모듈(`formula`)로 쪼개졌고, 반례(aqr-png의 융합,
   다중 출력)는 §4.5와 §4.6이 다룬다.
3. **블로킹의 구현.** WAH에 재시도 의미론을 넣을지(§5.4). 공유 간선, 다중 출력, 채널이 있으므로 WAH로 레퍼런스 경로를
   만들려면 필요하다.
4. **성능.**
   - 명세 ABI(memory64 I/O 메모리) 그대로인 모듈의 WAH JIT 측정. memory64 접근은 가드 페이지를 켜도 경계 검사를 한다.
   - SIMD가 이득인 모듈의 WAH JIT 측정(wasmtime에서는 LMS 3.6배).
   - 부동소수점이 많은 모듈(psd, obj)에서 NaN 정규화의 비용.
   - 네이티브 구현의 동치를 무엇으로 시험할지(말뭉치의 차등 시험, 퍼징).
5. **비용 선언의 형태.** "출력 바이트당 명령 수" 같은 힌트가 디코더의 실행 전 시간 예산 검증(§5.2)에 쓸 만한지.
   aqr-pdf의 선형 비용 모델은 표본 전체로 실측과 몇 % 이내, 파일별로 약 10% 흩어진다. aqr-git은 시계 없이 분해와 복원
   시간을 추정해(rms 9.3%, 14.2%) 입력 크기 × 10 ns/B 안에 들도록 다시 만들 zlib 스트림을 고르고, 예산에 넣는 *순서*
   (아끼는 바이트 / 시간)가 예산만큼 중요했다. 선언한다면 ns가 아니라 기계 독립 단위여야 한다.
6. **표준 모듈과 리소스를 아카이브에서 생략할지.** 사양 부록에 바이트째로 동결한 경우에 한해. 장기 보존과 작은
   아카이브의 오버헤드가 맞선다(작은 아카이브에서는 모듈 바이트가 지배적이다; 계획 중인 내장 사전은 `CLAUDE.md`).
   적합성 수준 1(§5.7)의 목록과 그 버전을 어디에 적을지.
7. **중첩 깊이와 노드망 크기의 상한.** 포맷마다 따로 정하고 있고(aqr-jpeg, aqr-psd 깊이 3, aqr-compress의 깊이),
   서로 다른 포맷의 중첩을 합산하는 장치와 import와 `patch` 사슬의 길이 상한이 없다. 모듈 *안*의 의존 사슬(aqr-git의
   delta 체인)도 있다.
8. **명세의 남은 TODO.** 모듈의 식별 해시와 인터페이스 세부는 명세의 Issue로 남아 있다. 세그먼트 안의 앞 블록
   역참조는 10번.
9. **다중 파일 변환.** 해결에 가깝다: aqr-git은 팩 하나(와 그 `.idx`/`.rev`)만 받고, 경로와 같은 내용은 아카이브의
   것이다. 다중 출력은 PNG 세트에 쓴다(§4.6). 아카이브 인코더가 어떤 파일 집합을 변환 하나에 넘길지는 포맷마다 정한다.
10. **세그먼트 안의 역참조와 스트리밍 [제안].** 같은 세그먼트 안의 앞 파일을 base로 쓰는 경우(명세 "Formula data"의
    Issue). formula에 앞쪽 non-leaf item의 목록을 하나 더 두고 `slice`로 읽으며, 앞 파일의 출력이 필요하면 그 formula의
    명령을 복사해 넣는다(보존 대신 재계산, 비용이 식에 드러난다). 스트리밍 디코더가 쥘 것은 zstd의 Window_Size처럼
    저장된 바이트 기준의 역참조 거리 상한 W로 미리 선언한다. 앞 블록을 찾는 후보는 (메타데이터의 `file_offset`으로
    찾는 앵커 leaf, 그 뒤의 정방향 ordinal)이다. 참조되는 leaf data 블록에는 체크섬이 있어야 한다.
11. **작은 파일 여러 개를 프레임 하나에.** 지금은 non-leaf 블록 하나에 묶고 파일마다 `slice` 하나인 formula를 둔다
    (`aqr`의 solid 블록). 묶은 파일 목록을 직접 가리키는 leaf 형태를 따로 둘지는 열려 있다(§3의 실측).
12. **랜덤 액세스 단위 상한의 기본값.** 파일을 하나씩 GB/s로 꺼내려면 16K 이하 + 사전, 대량 해제가 주라면 16M 이상이다
    (§3). 하나의 기본값을 둘지, "랜덤 액세스 우선"과 "대량 해제 우선" 같은 프로파일을 둘지. `apply` 크기도 같은 상한에
    묶이므로 모듈 출력에 대해서도 같은 측정이 필요하다.
