# 파일 사이의 공유: 풀어야 보이는 중복

압축된 컨테이너 안에 든 비슷한 데이터(한 프로그램의 여러 버전 설치 파일, 패치 묶음)는 풀어야 서로
겹친다. aqr-compress의 판단은 항목 하나씩 내려지므로 "이것을 풀면 다른 파일에서 풀린 것과 겹친다"는
사실이 반영되지 않는다. 이 문서는 그 판단들에 배치 안의 공유를 반영하는 방법의 근거와 남은 일이다.
끝낸 일의 경과는 git 이력에 있다.

## 1. 사례: WinUHA 2.0 설치 파일 넷

`X:\WinUHA_Setups` (Inno Setup 4.0.0a, 4.0.5, 4.1.8, 5.0.4; 4.51 MB). 4.0의 둘은 zlib 청크, 4.1 이후의
둘은 LZMA 하나로 파일 데이터를 담고, 안의 주 실행 파일은 PECompact 1.x나 UPX로 이미 압축돼 있다.
기본 레벨(`-Z no-smaller`: 판단을 모두 "받음"으로 강제한 상한):

| | 크기 |
|---|---|
| 처음(2026-11-15, `ee9ab9e4`) | 4,233,874 B |
| 지금까지의 작업 뒤(이 문서의 4.1, 4.3) | 4,078,930 B (목표 4.1 MB 달성) |
| `-Z no-smaller` 상한 | 4,016,994 B (-9: 3,889,466 B) |
| 조각을 파일로 나눠 잰 값 + CALL 필터 되돌림 + Setup.e32 해제 | 3.59 MB |

남은 몫(4.079 → 4.017 MB)은 대안을 둘 수 없는 문맥에서 거절된 것들과 probe의 거절이다(§4.3.5).

## 2. 판단이 내려지는 곳

| 지점 | 무엇을 정하나 | 공유를 보나 |
|---|---|---|
| (a) `Probe::pays` (aqr-formula `probe.rs`) | 코딩된 스트림을 풀지 (zlib, LZMA, `inno_pays`) | `held_by_others`의 0/1뿐(원본 입력의 앵커 99%) |
| (b) `smaller` 판정 (aqr-compress `verdict.rs`) | 만든 formula를 받을지 | 원본 입력에 99% 든 스트림만 공짜 |
| (c) `laid`의 `compresses_each` (`archive.rs`) | 4 KiB 이상 스트림을 `Compressed`로 강등 | 4.1의 압축 시험으로 본다 |
| (d) `merge_plan` (aqr-formula) | 같은 class·kind의 스트림을 블록에 합침 | `Compressed`는 제외 |

요구 조건(지금도 설계를 묶는다): **결정성**(같은 입력과 옵션이면 같은 아카이브; 배치의 파일은 병렬로
만들어지므로 판단은 `laid`에서 formula의 순서로 한다), **회귀 없음**(공유 없는 입력은 같은 아카이브),
**임의 접근**(합치는 것은 공유가 확인된 경우만, 크기는 `opt.block`), **비용**(앵커 계산 수준).

## 4. 수단

(번호는 코드의 주석이 가리킨다: `choose.rs` 등.)

### 4.1 친족: 강등 예외 [구현]

`archive.rs`의 `kin`(`-Z kin:trial`). 강등 후보마다 같은 class·kind의 다른 스트림 샘플을 raw prefix로
두고(가까운 것부터 최대 `kin:prefix` 4 MiB, 가장 가까운 것을 샘플 바로 앞에) 샘플이 레벨 3
(`kin:level`)에서 1/32 이상 줄면 강등하지 않는다. 면한 스트림은 `Unknown`으로 남아 `merge_plan`이 기존
키로 합친다(다른 class끼리의 합치기는 하지 않는다).

- 부결: **앵커로 친족 재기.** WinUHA의 강등되는 큰 `x86/OP`는 버전끼리 합치면 3–5% 주는데, 64바이트
  앵커의 공유는 0.5%, 8바이트 조각도 3%였다(겹침이 짧은 일치들로 퍼져 있음). 레벨 1 시험은 이득의
  절반만 잡았고, prefix를 거꾸로 두면 거의 같은 쌍도 놓쳤다.
- 효과: 10gb의 UPX PAQ 48개 버전(3.88 MB): 기본 3,856,646 → 3,432,372 B(−11.0%), -9 −13.5%.
  `10gb/progs` 186.51 → 182.81 MB(35.3 → 36.0 s), `10gb/2011` −0.3%. WinUHA는 그대로. 스레드 수를
  바꿔도 같은 아카이브.

### 4.2 예비 해제로 공유 지도 만들기 (지점 a, b) [제안, 안 함]

판단 전에 위치를 아는 코딩된 스트림(Inno의 청크, NSIS 블록, deflate 본문, xz/zstd 프레임)을 미리 풀어
앵커를 등록하고, `Held`의 0/1을 비율(`shares(data, except) -> f64`)로 넓혀 (a)의 `pays(shared + files())`와
(b)의 `free`에 쓰자는 안. 풀기를 두 번 하지 않으려면 메모리 한도 안에서 풀린 바이트를 남긴다.

측정(WinUHA): `smaller`가 거절하는 것은 두 부류다. 풀린 데이터 대 코딩된 원본(4.0의 zlib 청크,
Setup.e32)은 공유 비율이 판단을 바꾸는 쪽이며 이것만 강제로 받으면 기본 4,156,812 / -9 4,102,266 B,
즉 이 안이 낼 수 있는 몫은 상한의 1/3–1/2이다. 같은 데이터의 x86 formula 대 원본 PE는 양쪽 공유 비율이 같아
비율로 갈리지 않는다. 부결: "형제가 있으면 여유 x 안에서 받기"는 크기가 여유에 단조롭지 않았다(기본
4% → 4,189,896, 10% → 4,194,738 B; -9 4% → 4,268,770 B로 지금보다 큼, 20% → 3,902,154 B). 이 부류는
4.3이 맡았다. 4.2는 4.3.5에서 필요해질 때 한다.

### 4.3 배치 단위 재판정: `Node::Either` [구현]

아깝게 진 항목(formula가 원본보다 크지만 `kept × (1 + slack)` 이하)은 **두 형태를 모두 남기고**(`Either`:
`kept` 원본 슬라이스, `made` 만든 formula), 배치가 다 만들어진 뒤 `laid`에서 실제 압축으로 고른다.

- 표현: aqr-formula `Node::Either`(`node.rs`)와 `Formula::resolve`. 메모리에만 있고 `laid` 밖으로 나가면
  오류다(`unresolved alternative`). 대안을 곁의 표가 아니라 노드로 한 이유: 스트림을 합치고 번호를 다시
  매기는 일(`merge_classes`, `compact`, `embed`, `place`)이 양쪽을 저절로 지난다.
- 남기기: `verdict.rs`의 `Verdict::{Take, Close, Reject}`. `Close`는 `-Z defer:slack`(0.25), `defer:min`(16 KiB),
  예산 `defer:budget`(남긴 formula 스트림이 한 문맥 데이터의 2배까지; 절반이던 때는 formula의 스트림이
  데이터보다 커서(x86 분할 등, 4.0 설치본은 1.4배) 대부분 `Reject`였다)일 때. 남기는 곳은 스캔의 조각,
  콘텐츠가 통째로 한 형식인 경우, 스캔이 지고 안에 대안이 있는 경우의 셋이다. 스캔의 조각은 `Close`를 위로
  올리지 않고 `scan_with`가 감싼다(올리면 호출하는 쪽의 대체 경로를 건너뛴다).
- 고르기(`choose.rs`): 대안마다 안쪽부터, 각 쪽의 바이트를 class별로 모아 같은 class의 배치 안 다른 스트림
  (`defer:prefix` 1 MiB; 4 MiB와 결과가 같고 더 빠름)을 prefix로 두고 기본 레벨로 압축해 작은 쪽을
  (같으면 `kept`) 고른다. 모두 원본에서 시작해 살아 있는 스트림만 prefix로 삼아 결정이 안 바뀔 때까지
  (`defer:rounds` 4회) 되풀이한다(WinUHA -9 4,140,704 → 4,134,996 B). 묶기(likeness)로 하려던 설계는
  원본 쪽 바이트가 평가해야 나오므로 하지 않았다. 형제가 없으면 `kept`가 이겨 지금과 같은 아카이브다.
- 결과(기본 레벨): WinUHA 4,233,874 → 4,078,930 B, `10gb/progs` 182,808,039 → 182,700,885 B(−107 KB),
  `10gb/2011` 대안 없음. 시험은 대안마다 만들어(힙 최고치 3.48 → 1.51 GB) 시간은 WinUHA 0.30 → 0.31 s.
- 함정(고쳤고 회귀 시험이 지킨다): `Undo`가 남긴 대안을 받아진 것으로 세면 -9에서 LZMA 분할이 안 되돌려짐;
  `make_later`가 `close`인 내용을 잘라 내면 원본 쪽이 부모의 class가 아닌 스캔의 `raw` 틈이 됨(`progs`의
  PNG가 그랬다: +124 KB); 스캔이 찾은 파일이 모두 대안이면 원본과 비교하지 않고 통째로 남긴다(`scanned`).

#### 4.3.5 probe의 거절 [남음]

probe(`inno_pays`, zlib의 `member`)가 미리 거절하면 formula를 만들지 않아 남길 것이 없다. WinUHA 기본
레벨에서 이 몫은 약 88 KB다. `exe:inno-defer`(기본 꺼짐)로 거절된 Inno 분할도 남겨 고르게 해 보았으나
판정이 다시 거절해(Beta, RC1) 크기는 같고 시간만 0.31 → 0.49 s였다. 하려면 배치 안에 그 데이터의 친족이
있을 때로 한정해야 하고, 그 답은 4.2의 공유 지도가 준다.

### 4.4 국소 수정: `Undo` [구현]

코딩된 스트림을 풀었는데 그 데이터의 재압축이 버려지면 푼 것을 되돌려 원래 스트림을 둔다
(`context.rs`의 `Undo`, `recompress_sealed`가 `nested()` 직후 되돌림; 등록하는 곳은 exe.rs의 `inno_undos`뿐).
RC1 같은 파일째 원본이 사라진다. WinUHA -9 4,288,244 → 4,208,354 B.

## 7. 열린 질문

- **4.2와 4.3.5**: 위. 공유 지도의 비용(예비 해제 시간, 지도 메모리)은 10gb 전체에 `--stats`로 재야 한다.
- **kin 비율/그룹 한도**: 압축 시험으로 바뀌어 비율 기준은 없다. 다른 class끼리 합치기는 안 한다.
- **배치 경계**: 공유는 배치 안에서만 쓸 수 있고 `together`가 원본 머리 64 KiB로 묶는다. 4.0과 4.1의
  로더가 다르면 같은 배치에 못 들어갈 수 있다. 큰 입력에서는 풀린 데이터의 머리로 묶어야 할 수 있다.
- 배치의 위쪽 파일(UPX PAQ들, 설치 파일 자체)은 sealing으로 만들어져 대안을 못 남긴다.
- 공유 없는 대조군(10gb의 설치 파일과 ZIP류, `ALZip1237.exe`)과 스레드 수를 바꾼 바이트 비교로 회귀를 본다.

## 8. 손잡이 (`-Z`)

`-Z NS:help`가 기본값과 함께 보여 준다. 이 작업의 것: `exe:[no-]inno-zlib`(4.0의 zlib 스트림),
`exe:[no-]inno-undo`(4.4), `exe:[no-]inno-defer`(꺼짐; 4.3.5), `kin:[no-]trial`, `kin:prefix`, `kin:level`,
`defer:slack|no-slack|min|budget|prefix|rounds`, `defer:choose=trial|made|kept`(made/kept는 측정용 강제).
측정용 강제는 upstream의 옵션이다: `-Z probe=off`, `-Z no-smaller`(모두 받기), `-Z merge-probe=`(아주 큰
값이면 강등을 끈다).
