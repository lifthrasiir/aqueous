# 로그: 줄의 템플릿과 필드 (aqr-log)

로그와 숫자가 많은 텍스트를 줄마다 템플릿 하나와 그 필드로 나누어 저장하는 재압축기 `aqr-log`(모듈
`log-recons`)의 근거와 실측, 남은 일이다. 포맷의 규범은 `codecs/aqr-log/FORMAT.md`(구현 **[구현]**)가 적고
고르기는 `crates/aqr-compress/src/made.rs`의 `table`이다. 끝낸 일의 경과는 git 이력에 있다.

## 1. 배경

2026-11-14에 numerus 0.1.0(숫자·로그 전용 상용 압축기)을 공개 데이터와 견주었다. 목적은 평가가 아니라 정보
엔트로피 최소값의 프록시였고, 코퍼스는 따로 준비했으며 EULA(경쟁 아카이버 개발에 사용 금지) 때문에 제3자를 통해
압축률만 전달받았다. 그때 aqr는 줄 단위 로그에서 크게 졌다(openssh 4.83% 대 numerus 2.17%; 공백 구분 표는 aqr-xsv가
받게 돼 있었다). 프로토타입은 `scripts/log_probe.py`(토큰을 공백으로 자르고, 숫자열을 가린 꼴이 드문 토큰은 문자열
변수, 나머지는 템플릿 + 숫자 변수, 열마다 예측기 중 작은 것; 스트림 크기는 zstd -9, xz로 재면 10-25% 낙관적).

시도했고 버린 변형(xz 기준): 숫자열만 가린 줄 전체를 템플릿으로(NASA에서 템플릿 57만 개, 7.41%로 xz -9보다 나쁨);
템플릿 ID의 MTF(openssh 1.27 → 1.31%로 나쁨); 키별 예측기(같은 mote의 앞 줄과의 차는 바로 앞 줄과의 차와
같았다: 8.62 MB 대 8.62 MB). 드문 토큰의 임계 T는 둔감하다(T=256..16384에서 1.18–1.14%). 열마다 예측기를 고르면
openssh 1.16 → 0.97%.

## 2. 설계에서 정한 것 [구현]

- **모듈** `log-recons` 1: whole 모듈, 64 MiB 세그먼트(줄 경계)마다 적용 하나, 템플릿과 열은 세그먼트마다 새로
  시작. 메모리 계획은 params의 세 수(템플릿·열·줄당 최대 숫자 수)와 입력·출력 길이에서 정확히 나온다
  (`log_plans_hold`).
- **토큰 판정의 순서**: 수가 먼저다(`1.5e-07` 같은 드문 꼴의 수가 문자열로 가지 않게). 토큰 전체가 aqr-num이 받는
  수면 수 슬롯, 아니면 숫자열이 18자리를 넘거나 꼴이 R = max(64, 줄 수/500)번보다 적게 나오면 단어, 아니면
  템플릿에 두고 숫자열마다 슬롯. 표지 0x01 숫자열, 0x02 단어, 0x03 수, 0x04 시각, 0x05 IPv4(이 바이트가 든 줄은 raw).
- **`columns`** 는 열마다 길이와 예측기만 적고 `widths`·`types`의 길이는 `nums`에서 나온다(열마다 다섯 길이를 적던
  것이 apache에서 14.1 → 9.5 KB).
- **예측기**: 열마다 그대로 / 열의 앞 값과의 차 / 바로 앞 raw 아닌 줄의 같은 번호 숫자와의 차 / (IPv4) 최근 64개
  주소 목록의 인덱스(모든 주소 열이 공유). 인코더가 `nums`의 zstd -1 크기로 고른다.
- **구분자**: 토큰을 공백 외에 `;`, TAB, `,`에서도 자른다(인코더 선택이고 모듈은 그대로). 세그먼트 앞 1 MiB를
  공백만 / 넓은 구분자로 코딩해 zstd -3 합이 작은 쪽을 쓴다: 산문과 소스는 `,` `;`가 문장 부호라 잘게 쪼개면
  템플릿이 줄마다 달라져 커진다(10gb에서 고르기 없이는 mingw의 C 헤더가 log로 넘어가 +100 KB). 소수쉼표(`4,216`)면
  `,`를 구분자에서 뺀다(256 KiB의 쉼표 수 > 점 수이고 천 단위 후보 이하가 아닐 때).
- **패딩 소수**(`42283.58000000` → 정수 + `%.8f`), **시각**(표지 0x04, 정수 하나, 소수가 있으면 열 둘: 마이크로초가
  섞인 합친 정수의 차보다 낫다, intel_lab −278 KB), **열의 단위**(정수가 모두 gcd의 배수면 몫만): 세부는
  FORMAT.md §5와 `crates/aqr-num/README.md`. 패딩 소수는 득실이 불분명해 열마다 표본 1024개를 두 방식으로 코딩해
  zstd -1로 잰 쪽을 쓴다. 줄 끝의 CR은 템플릿의 바이트다.
- **고르기**(`table`): aqr-jsonl과 aqr-xml(`docs/xml-design.md` §2) 다음에, 표본(2 MiB 이하면 전체, 아니면 256 KiB
  창 8개를 처음부터 끝까지; 앞 1 MiB는 SMARD prices에서 스트림이 261 B뿐이라 오판했다)을 aqr-log와 aqr-xsv로
  코딩해 스트림의 zstd -3 합을 표본 자체의 zstd -3와 견준다. aqr-xsv가 aqr-log 이하면 xsv, aqr-log가 표본 이하
  (`LOG_PERCENT` = 100; 85%는 156개 −10.8 MB, 100%는 272개 −11.9 MB)면 log, 아니면 aqr-wrt. 산문과 소스는 120%
  이상이라 wrt로 간다. 두 후보가 다 받는 파일에서는 표본이 갈라 주지 못한다.

## 4. 남은 일

(CLAUDE.md와 `codecs/aqr-log/README.md`가 이 절을 가리킨다.)

- **IPv6**, 그리고 주소 뒤의 포트 같은 이웃 정수와의 결합. aqr-xsv의 열에 든 IP는 아직 글자다.
- **aqr-xsv에 열의 단위(gcd)와 주소**: SMARD처럼 4분의 1 단위 값이면 log가 훨씬 작아(load_2 535,732 → 389,698)
  고르기에서는 log가 이기지만, 따옴표 있는 CSV의 같은 열은 xsv에서 그만큼 못 줄인다.
- **에포크 초/밀리초**는 정수라서 하지 않았다. 시간대를 값으로 두는 로그(열 안에서 오프셋이 바뀜)는 정수 옆에 값이
  하나 더 있어야 해서 하지 않았다.
- **수가 숫자열보다 못한 열을 표본으로 가리기**(패딩 소수와 같은 시험): 시각이 작은 열(`,00 ,25 ,50 ,75`의 분수),
  SMARD load처럼 디지트 런이 정수보다 잘 눌리는 파일.
- **구분 고르기의 표본(앞 1 MiB)과 스트림마다 고르는 zstd 레벨**: load_1의 `nums`가 z12 대 z3 사이에서 뒤집히면
  같은 내용이 0.5% 달라진다. 인코더의 레벨 선택이 표본에 흔들린다.
- **천 단위 구분**: 공백·`'`·인도식 lakh는 받지 않는다. 영어식(`1,234.56`)은 aqr-xsv(따옴표 안)에서만 쓰이고
  aqr-log는 `,`를 구분자로 자른다.
- **Drain식 군집**(위치가 고정된 단어 변수): 드문 토큰 규칙으로 아직 충분하다.
