# 모듈 메모리: 아레나와 상한

모듈(Wasm, 복원 쪽)이 적용 하나에 쓰는 working memory를 입력으로부터 계산할 수 있는 값으로 묶고,
그 값을 `apply_memory_limit`로 선언하기 위한 설계. 메모리 모델 자체(메모리의 종류, 한도의 계산,
태스크가 working memory를 복사하는 규칙)는 spec의 "Module execution"과 "Tasks"가 정한다.

## 현황 (2026-10-29)

측정은 `aqr-decompress-memory`(`crates/aqr-decompress/examples/memory.rs`)와
`scripts/module-memory.sh`의 표본으로 한다. 아래 숫자는 working memory 최대치 / m (출력 길이)이고,
두 개면 호스트 스레드 1 · 8에서 잰 값이다. 상한에는 스레드 수가 들어가지 않는다(아래 "태스크와 한도").

- 할당자는 std의 dlmalloc이다. Wasm 메모리는 줄지 않으므로 최대치는 dlmalloc의 high-water다.
  해제한 블록 사이의 구멍, `Vec`이 2배로 자랄 때 옛 블록과 새 블록이 함께 있는 순간, 미리 잡았지만
  쓰지 않은 용량(페이지는 이미 늘어나 있다)이 모두 들어간다.
- 태스크는 spawn 시점의 페이지 전부를 복사한다. 그래서 spawn 전에 무엇이 할당돼 있었는지가
  동시에 떠 있는 태스크 수만큼 커진다. 파이프라인(flac, pcm)은 채널로 묶여 있어 태스크가 모두 떠 있다.
- 2단계(할당 순서와 용량)에서 줄인 것: flac 37 → 13, pcm 22 → 6, lzma 102 → 64, sqlite 22 → 13
  (스레드 8), flate-set(gzip) 50 → 37 (스레드 8), x86 5.4 → 2.8, lz4 5.2 → 4.2, lzo 5.3 → 4.0.
- 남은 큰 것: lzma 64(체인 12·D), flate-set 37(태스크마다 D), fits-rice 31(Pyramid의 i64 버퍼),
  png-set 27.5, jpeg 24–26(줄무늬 태스크의 계수 버퍼), bcn 25(출력 m을 spawn 전에 잡음).

## 목표

1. **상한을 계산할 수 있다.** 인코더가 formula를 만들 때 아는 값(params, 입력·리소스·출력 길이,
   그리고 필요하면 params에 넣은 개수)만으로 모듈의 최대치를 위에서 묶고, 그 값을 선언한다.
   측정값과의 차이(초과분)가 작고 원인이 열거돼 있어야 한다.
2. **초과분이 작다.** 성장의 이중 점유, 해제 구멍, 쓰지 않은 용량을 구조로 없앤다.
3. **모듈 크기와 네이티브 속도를 해치지 않는다.** 모듈 바이트는 아카이브마다 붙고, 알려진 해시는
   네이티브로 돈다(CLAUDE.md의 Modules 절).

## 라이브러리

permissive 라이선스면 써도 된다(링크되는 우리 코드의 라이선스를 제약하지 않는다).

| 후보 | 하는 일 | 맞는 점 | 맞지 않는 점 |
|---|---|---|---|
| bump-scope | 범프 아레나, scope와 checkpoint(그 지점으로 되감기), `BumpVec`·`FixedBumpVec`, allocator-api2 0.2–0.4 | 단계별로 쓰고 버리는 작업 공간에 딱 맞는다. 위로 범프할 때 마지막 할당은 제자리에서 자란다. 고정 용량 컬렉션이 있다 | 청크가 차면 2배 크기의 새 청크를 잡는다. 상한을 지키려면 기반 할당자(base allocator)로 새 청크를 막아야 한다 |
| bumpalo | 범프 아레나, allocator-api2 | 이미 Cargo.lock에 있다(wasmtime 경유) | 전체 `reset()`만 있고 지점으로 되감기가 없다. 청크를 늘린다 |
| talc | dlmalloc류 전역 할당자, wasm용 소스, 고정 영역 claim | 전역 할당자를 바꾸면 API 변경이 없다. 크기를 줄이는 기능 플래그가 있다 | 범용 할당자라 상한을 주지 못한다. 단편화와 성장 문제는 그대로다 |
| allocator-api2 | 안정판에서 쓰는 `Allocator` 트레이트와 `Vec<T, A>`·`Box<T, A>` | 아레나를 std 꼴 컬렉션으로 쓰게 해 준다 | `Vec<T, A>`는 std `Vec<T>`와 다른 타입이다 |

**권고: bump-scope**(allocator-api2 기능과 함께).
- 기반 할당자는 계획한 크기의 영역 하나를 한 번만 내주는 것으로 둔다. 그러면 청크가 더 늘지 않고, 넘치면 할당이 실패한다.
- 전역 할당자는 당분간 dlmalloc을 그대로 둔다. talc로 바꾸는 것은 모듈 크기만 보고 따로 잰다. 상한 문제와는 관계가 없다.

## 기존 `Vec`은 어떻게 되는가

std `Vec<T>`(전역 할당자)는 그대로 쓴다. 안정판에서는 std `Vec`을 아레나에 놓을 수 없다
(`allocator_api`는 nightly다). 그래서 버퍼를 셋으로 나눈다.

1. **작은 것**(입력 크기와 무관하거나 작은 상수): std `Vec` 그대로. 상한에서는 모듈별 상수 하나로 묶는다.
2. **입력에 비례하지만 크기를 미리 아는 것**: std `Vec`을 정확한 용량으로 한 번 잡고 다시 자라지 않게 한다.
   2단계에서 한 일이 이것이다. 아레나 없이도 상한을 계산할 수 있다.
   (출력 길이 m, 원시 이미지 크기처럼 params와 길이에서 나오는 값)
3. **크기를 미리 모르거나 단계마다 쓰고 버리는 것**: 아레나에 둔다.
   예: png-set의 참조, fits Pyramid의 단계별 버퍼, bcn의 평면, jpeg 줄무늬의 계수.
   - `FixedBumpVec`(고정 용량)이나 `BumpVec`(마지막 할당이라면 제자리에서 자람)을 쓴다.
   - scope가 끝나면 되감는다. 그러면 해제 구멍 없이 다음 단계가 같은 페이지를 다시 쓴다.

**타입이 갈리는 데 따른 비용**
- `&[T]`로 읽는 코드는 그대로 둔다. 아레나 컬렉션도 슬라이스로 deref된다.
- `&mut Vec<u8>`에 이어 쓰는 함수(싱크)는 고쳐야 합니다.
  - 아레나로 옮기는 경로에서만 `&mut dyn` 싱크나 슬라이스를 받도록 바꾼다.
  - 제네릭으로 풀면 할당자 타입마다 사본이 생겨 모듈이 커진다. CLAUDE.md의 단형화 원칙에 따라 `dyn`을 기본으로 한다.
- 모듈 출력은 `aqr_api::whole`이 `Vec<u8>`을 받아 출력 메모리로 복사한다.
  - 출력은 std `Vec`을 정확한 용량으로 잡는 방식(2번)을 기본으로 둔다.
  - 필요하면 `whole`이 슬라이스를 받게 넓힌다.
- 할당자 타입은 `&Bump` 하나만 쓴다. 아레나 컬렉션은 몇 개의 큰 버퍼에만 쓰고, 성장 코드가 필요 없는 곳은 `Fixed*`를 쓴다.
  모듈 크기 변화는 바꿀 때마다 잰다.

## 상한과 초과분

모듈마다 메모리 추정 함수를 두고, 모듈 값(aqr-formula의 `Module`, 이름과 버전)이 그것을 가리킨다.

```
Module::memory_usage_in_pages(params, resource_lens, input_lens, output_lens) -> u64
```

- **계약.** 인코더(aqr-compress)는 이 값을 `apply_memory_limit`로 선언한다. 디컴프레서가 그만큼을 주지 못하면
  시작 전에 resource failure로 거절하고, 시작했으면 한도 안의 `memory.grow`는 반드시 성공한다(spec
  "Module execution"). 그래서 모듈은 추정치만큼의 메모리가 늘 있다고 가정할 수 있다.
  추정치를 넘는 것은 모듈이 자기 계획을 어긴 경우뿐이다.
- **위치.** 함수 본체는 각 코덱의 인코더 쪽(`formula.rs`, `encode` 기능)에 둔다. 디코딩 코드(`module.rs`)에는
  압축 해제에 쓰는 것만 둔다. 모듈이 버퍼 크기를 정하는 계산(`plan` 같은 것)이 있으면 추정 함수가 그것을
  빌려 쓴다. 그러면 상한과 실제 할당이 같은 계산에서 나온다.
- **단위.** 페이지(64 KiB)다. spec의 메모리 크기 단위와 같고, 페이지 반올림 초과분을 흡수한다.

상한의 구성:

```
W = c0                     (데이터 세그먼트와 스택: 모듈마다 고정, 측정값의 바닥)
  + I                      (aqr_api::whole의 입력·리소스 사본)
  + Σ 계획한 버퍼           (2번과 3번의 크기, params와 길이에서 계산)
  + c_small                (1번의 상수, 모듈마다)
P = W_main + Σ_태스크 (W_spawn + 태스크의 계획 버퍼) + 채널 메시지 (용량 × 최대 길이)
```

초과분이 생길 수 있는 곳과 그 처리:

| 원인 | 크기 | 처리 |
|---|---|---|
| `memory.grow`의 페이지 단위 | 성장마다 64 KiB 미만 | 아레나 영역을 한 번에 잡으면 한 번만 생긴다 |
| dlmalloc의 청크 머리와 단편화(작은 것) | 측정해야 안다 | `c_small`에 측정값과 여유를 둔다. 표본 측정이 이를 검증한다 |
| 큰 버퍼 사이의 해제 구멍 | 지금은 크다(예: bcn의 밉 평면) | 단계별 버퍼를 아레나 scope에 두면 사라진다 |
| `Vec`의 2배 성장(빈 용량, 이중 점유) | 최대 3배 | 2번은 정확한 용량으로, 3번은 아레나의 제자리 성장이나 고정 용량으로 없앤다 |
| 아레나 청크의 2배 성장 | 최대 2배 | 기반 할당자가 영역 하나만 내주게 해 없앤다 |
| 태스크 사본 | W_spawn × 동시 태스크 수 | 상한에 들어간다. spawn 전에 할당하는 것을 줄이는 것이 핵심이다(2단계) |
| 크기를 모르는 출력(토큰 수 등) | 위로 묶은 만큼 | params에 개수를 넣거나(형식 변경), 길이로부터 위로 묶는다(예: 토큰 ≤ 바이트) |

이렇게 하면 상한은 "계획 + 상수"가 되고, 초과분은 페이지 단위와 `c_small`의 여유뿐이다.
`c_small`만은 코드로 증명하지 못하고 측정으로 정한다. 작은 할당이 입력에 비례해 많아지는 경우(블록마다 `Vec` 하나 같은)는
상수가 아니므로 계획 버퍼로 옮겨야 한다.

**검증.** 측정 표본마다 추정치 ≥ 측정값이고 추정치 / 측정값 ≤ 1.2 정도인지를 확인한다.
- `aqr-decompress-memory`에 상한 열을 더한다.
- `#[ignore]` 테스트로 둔다. 표본과 결과는 `cache/`에 있다.

## 태스크와 한도

인스턴스마다 동시에 도는 태스크는 최대 모듈의 task slots개다(spec "Tasks"). 슬롯 수는 모듈이 커스텀 섹션
`aqr_task_slots`로 선언한다. bin이 `whole!(slots N, …)`으로 적으면 매크로가 섹션을 내고 같은 N을 디코딩 코드의
스레드 수로 넘긴다. aqr-ld는 태스크를 쓰는 모듈에만 섹션을 남기고 검증한다. 지금은 모두 8이다. 나머지는 그 인스턴스가 spawn한
순서대로 자리가 날 때 시작하고, 시작 전에는 메모리가 없다.

"running"은 CPU 위에서 돈다는 뜻이 아니라 시작해서 끝나지 않았다는 뜻이다. 슬롯에 자리가 있으면 호스트는
다음 태스크를 시작해야 한다. 스레드가 적은 호스트는 8개를 번갈아 돌릴 뿐 떠 있는 인스턴스 수를 줄이지 못한다.
따라서 상한에 호스트의 스레드 수는 들어가지 않는다. 태스크 항은 언제나 `min(slots, n)·W_spawn + 태스크별 계획 버퍼`이고,
중첩 spawn(태스크 안의 spawn)은 단계마다 slots가 곱해진다. 표본의 "스레드 1 · 8" 측정 차이는 태스크가 빨리 끝나 덜
겹친 결과일 뿐 상한이 아니다.
파이프라인은 단계가 8개를 넘으면 교착(잘못된 아카이브)이 되므로, flac·pcm(태스크 8개)이 상한이다.

`task_slots` 테스트가 이 상한을 정확히(본체 4페이지 + 태스크 8개 + 메시지) 검증한다. 샌드박스 워커도 같다.

## png-set: 아레나 없이 풀림

27.5·m(678 MB)이던 set.tar(24.6 MB 출력)가 9.4·m(232 MB)가 됐다(`f591e33`).
- 원인: 깊이 0의 부모 이미지를 다시 만들며 남기는 참조(`model::Reference`, 토큰마다 10 B)가 빈 벡터에서
  2배씩 자랐다. 깊이 1의 태스크들은 그 high-water를 통째로 복사했다.
- 해결: 레이아웃이 디코딩 전에 블록별 토큰 수를 알려 주므로(`ntok`), 참조를 그만큼 한 번에 잡는다.
  형식은 바뀌지 않았다. 처음에는 params에 토큰 수를 넣으려 했으나 필요 없었다.
- 남은 것: 참조 자체(원시 바이트마다 약 10 B)와, 그것을 자식 태스크마다 복사하는 몫이다.
  참조를 매치만 적는 꼴로 압축하면 계수가 준다. 리터럴이 참조 데이터의 바이트를 요구하는지 확인해야 한다.

교훈: 크기를 미리 계산할 수 있는 것은 아레나보다 정확한 용량(버퍼 분류의 2번)이 더 싸다.
아레나는 크기를 미리 모르는 것과, 단계마다 쓰고 버리는 작업 공간이 있는 곳에만 쓴다.
후보: fits Pyramid의 단계 버퍼, bcn의 밉 평면, jpeg 줄무늬의 계수, flate-set의 배치 토큰.

## 다음 순서

1. `Module::memory_usage_in_pages`를 이미 정확한 용량을 쓰는 모듈들(exe, xsv, fasta, zip, git, pdf, png, …)부터 만든다.
   하네스에 상한 열과 검증 테스트를 더한다.
3. 인코더가 `apply_memory_limit`를 선언하게 한다. 지금은 `aqr-formula`의 `MEMORY_LIMIT` 상수다.
4. 아레나가 필요한 곳(위 후보)에 bump-scope를 넣는다. aqr-common에서 `no_std` Wasm 빌드와 모듈 크기를 먼저 확인한다.
   기반 할당자는 영역 하나만 내주는 것으로 한다.
