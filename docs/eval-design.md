# aqr-formula 평가기의 메모리 설계 초안

`aqr-formula`의 아카이브 디코더(`aqr::decode`)가 formula를 평가하면서 쓰는 메모리를 다룬다. 같은 디코더가 aqr-compress의 최종 검증(`finish`)과 aqr-decompress의 `decompress()`에 쓰인다.
절과 항목의 상태 표기는 `xform-design.md`와 같다.

- **[확정]** 논의 전부터 정해져 있었거나 논의 중 명시적으로 합의된 것
- **[잠정]** 방향은 합의했으나 세부는 열려 있는 것
- **[제안]** 제안되었으나 아직 검토하지 않은 것

관련:

- `spec/index.bs` §Formula evaluation: 스택의 값은 완전히 평가된 바이트열로 정의되고, 지연·스트리밍·부분 평가는 결과를 바꾸지 않는 구현 전략이다. 이 문서는 그 구현 전략만 다룬다.
- `spec/index.bs` §Module execution: 전체형과 부분형 모듈, 입출력 메모리의 크기, 메모리 한도.
- `xform-design.md` §4.3(평가 의미론), §5.3(데이터 전달과 구현 노트), §5.4(요구 구동 스케줄링).

---

## 0. 목표와 전제

- **목표.** 평가에 쓰이는 큰 버퍼의 최대 동시 점유를 실행 전에 계산할 수 있게 하고, 그 값이 곧 실제 최고 수위가 되게 한다.
- **wasm 선형 메모리는 줄지 않는다.** 디코더를 wasm32로 빌드하면 할당기의 최고 수위가 그대로 메모리 점유가 된다. 범용 할당기(dlmalloc 등)에서는 큰 버퍼를 놓은 자리에 크기가 다른 버퍼가 들어가지 못해 수위가 더 오를 수 있다(단편화).
- **크기는 모두 미리 알려져 있다.** 블록의 크기(블록 헤더와 zstd 크기 델타), literal의 길이, `apply`가 선언한 출력 크기, 그리고 그 합인 `concat`의 크기가 모두 그렇다. formula 블록은 평가 전에 모두 읽힌다(6bd8c25).
- **값은 정확히 한 번 쓰인다(명세).** 그래서 formula 블록 하나는 명령의 트리이고, 평가 순서는 명령 순서로 정해진다. non-leaf 블록만 여러 slice와 여러 formula 블록에 걸쳐 공유된다.

## 1. 현재 상태 (2026-10-23, 측정)

VS Code macOS 빌드(266 MB, 8스레드)에서 할당기 집계 기준으로 쟀다.

| | 최대 | 최대인 곳 |
|---|---|---|
| `compress()` | 1.97 GB | 최종 검증 중(재압축 중의 최대는 1.93 GB) |
| `decompress()` | 2.00 GB | ZIP 모듈 실행 중 |

`decompress()`가 시작할 때 이미 쓰이고 있던 0.58 GB(측정 프로그램이 쥔 원본과 아카이브)를 빼면, 최대일 때 평가기가 쥔 것은 다음과 같다.

| 버퍼 | 크기 | 비고 |
|---|---|---|
| ZIP 모듈 입력(데이터) | 683 MB | `concat` 151개 부분, 그중 680 MB가 간격 블록의 slice |
| ZIP 모듈 입력(레코드) | 10 MB | |
| ZIP 모듈 출력 | 267 MB | 곧 파일 |
| ZIP 모듈 내부 | 약 410 MB | aqr-zip과 aqr-flate의 작업 메모리 |

> 이번 세션에 이미 고친 것: 블록을 선언 크기로 풀기(f05304c, −396 MB), slice와 literal 복사 제거(e4e5643), 첫 leaf 출력 복사 제거(7365a8d), 마지막 slice 뒤 블록 해제(6bd8c25, −695 MB). 모두 이 문서의 어느 설계든 포함할 것이라 먼저 했다.

## 2. 설계

### 2.1 정적 계획 [제안]

평가 전에 formula 블록을 읽으면서 값마다 크기를, 버퍼마다 수명을 계산한다.

- 버퍼는 세 종류이다. 통째로 푼 non-leaf 블록, 실체화된 `apply` 입력, `apply` 출력이다.
- 블록의 수명은 첫 slice부터 마지막 slice까지이다(지금 6bd8c25가 동적으로 하는 일).
- 나머지 버퍼의 수명은 트리 순회에서 정해진다.
- 이로써 최대 동시 점유(모듈 내부 작업 메모리 제외)가 실행 전에 나온다. 디코더는 이것을 자기 한도와 비교해 실행 전에 resource failure를 낼 수 있다.

### 2.2 실체화는 모듈 입력과 최종 출력에서만 [제안]

- slice, literal, `concat`은 조각의 목록으로 두고 복사하지 않는다. 지금 slice와 literal은 이미 그렇고, `concat`은 복사한다.
- 바이트가 실제로 한곳에 모여야 하는 곳은 둘뿐이다.
  - 전체형 모듈의 입력 메모리
  - 최종 출력(2.4에서 싱크로 바꾸면 이것도 없어진다)
- 모듈 입력은 선언된 크기로 버퍼를 먼저 잡고, 자식을 그 안에 바로 평가해 넣는다(`emit(node, sink)`). 자식 `apply`의 출력은 간선마다 한 번 복사된다(xform §5.3 구현 노트와 같다).
  - 입력 하나가 자식 `apply`의 출력 그 자체이면, 그 출력 버퍼를 복사 없이 넘긴다.

### 2.3 블록을 소비자에게 바로 풀기 [제안]

- 블록의 slice들이 평가 순서대로 오프셋이 늘어나며 한 번씩만 읽힌다면, 블록을 통째로 풀지 않는다. zstd 스트리밍 해제로 소비자 버퍼에 바로 풀고, slice 사이의 바이트는 작은 창에 풀어 버린다.
- 그렇지 않은 블록(되읽거나, 여러 formula 블록이 공유하는 블록)은 지금처럼 통째로 풀어 마지막 slice 뒤에 놓는다.
- 어느 쪽인지는 2.1의 계획에서 정한다.
- VS Code의 간격 블록(695 MB)이 앞의 경우이다.
  - 최종 검증은 ZIP 모듈을 돌리지 않으므로(memo), 그 최대는 `concat`을 만드는 순간일 것이다(추정).
  - 그 순간의 블록과 `concat` 1.38 GB가 0.68 GB가 되고, `compress()`의 최대는 재압축 쪽 1.93 GB로 내려간다(추정).

### 2.4 출력을 싱크로 [제안]

- `decode_into(c, natives, sink)`는 최종 출력을 조각으로 내보낸다. `decode`는 `Vec` 싱크를 쓰는 래퍼가 된다.
- aqr-compress의 검증은 원본과 비교하는 싱크를 쓴다. 출력 사본이 필요 없다.
  - memo에 원본의 범위로 남은 출력(8bf4d02)은 원본과 비교할 필요도 없다. 그 범위를 확인된 것으로 넘기면 된다.
- aqr-decompress는 파일에 바로 쓰는 경로를 가질 수 있다.

### 2.5 부분형 네이티브 모듈 [제안]

2.2–2.4까지 해도 VS Code `decompress()`의 최대는 ZIP 모듈 실행 순간 그대로이다(입력 693 MB, 출력 267 MB, 내부 약 410 MB). 이것을 줄이려면 모듈 자체가 입력을 앞에서부터 읽고 출력을 앞에서부터 내야 한다.

- 네이티브 모듈 API에 부분형을 더한다. 입력은 끌어오는 reader, 출력은 밀어내는 sink이다. Wasm 부분형 모듈의 `request`/`commit`(명세)에 대응한다.
- 요구 구동 스케줄링(xform §5.4)이면 스레드 없이 돈다. 노드망이 트리이기 때문이다.
- 후보는 데이터를 순서대로 다루는 모듈이다.
  - aqr-zip: 엔트리를 순서대로 쓴다.
  - aqr-flate: 이미 `reconstruct_into(…, sink)`가 있다.
  - aqr-lz4, aqr-snappy: 블록 단위로 순차적이다.
- 그러면 VS Code에서 데이터 블록 → ZIP 모듈 입력 → ZIP 모듈 출력 → 싱크가 창 크기로 흐르고, 남는 것은 모듈 내부 작업 메모리이다.
- 전체형 모듈(xform §5.3의 psd, sqlite 등)은 출력 버퍼를 호스트가 선언 크기로 주는 형태로 바꾼다(`apply(…, out: &mut [u8])`). 그래야 2.6의 영역에 들어간다.

### 2.6 수명별 영역(arena) [제안]

큰 버퍼를 범용 할당기에서 떼어 내, 정적 계획(2.1)대로 하나의 연속 영역에 둔다.

- **스택 영역.** 트리 후위 순회에서 버퍼 수명을 LIFO로 맞출 수 있다. `apply` 하나는 다음 순서로 평가한다.
  1. 입력 버퍼를 잡는다.
  2. 자식을 그 안에 평가한다. 자식의 버퍼는 그 위에 쌓였다가 내려간다.
  3. 출력 버퍼를 잡고 모듈을 돌린다.
  4. 출력을 부모의 싱크로 내보낸다.
  5. 출력과 입력을 위에서부터 놓는다.
- 이러면 bump 할당기 하나로 되고, 단편화가 없으며, 영역 크기는 2.1의 최대치와 같다.
- 통째로 푼 블록(2.3에서 남는 것)은 수명이 트리를 가로지르므로 LIFO가 아니다. 영역 바닥에 미리 잡거나(첫 slice 전부터 차지한다) 범용 할당기에 둔다.
- **일반 오프셋 계획기(대안).** 수명 구간이 알려진 버퍼들에 오프셋을 정적으로 배정한다(TFLite의 arena planner처럼 크기순 greedy). 블록까지 한 영역에 넣을 수 있지만 더 복잡하고, 최적 배정은 NP-hard라 휴리스틱이 된다.
- 모듈 내부 작업 메모리는 영역 밖(범용 할당기)이다. Wasm 모듈이 되면 인스턴스마다 자기 메모리를 가진다.

## 3. 단계

1. 정적 계획: 크기와 수명, 최대 동시 점유를 계산하고 검사만 한다(2.1).
2. 블록을 소비자에게 바로 풀기(2.3).
3. 출력 싱크와 검증 비교 싱크(2.4).
4. 네이티브 모듈 API: 전체형 출력 버퍼, 부분형(aqr-zip, aqr-flate부터)(2.5).
5. 영역(2.6).

1–3은 모듈 API를 건드리지 않는다. 4는 모든 재압축기의 `formula::decode`에 걸친다. 바꾸지 않은 모듈은 복사하는 어댑터로 감싸 둘 수 있다.

## 4. 열린 질문

1. 영역: 스택 영역(블록은 따로)과 일반 오프셋 계획기 중 어느 쪽인가.
2. 네이티브 모듈 API: 전체형의 출력 버퍼와 부분형의 reader/sink를 둘 다 들일 것인가. 부분형을 먼저 넣을 모듈은 어느 것인가.
3. 정적 계획의 최대치로 실행 전에 거절하는 것을 명세에 넣을 것인가. 지금 명세는 `apply`마다의 메모리 한도만 둔다.
4. 이 문서를 따로 둘 것인가, `xform-design.md` §5 아래로 옮길 것인가.

## 5. 범위 밖

- 재압축 중의 최대(1.93 GB)는 aqr-zip 인코드 안에 있다(aqr-zip이 식을 내놓은 직후에 잰 값). aqr-flate 분해의 작업 메모리(155 MB 스트림에 약 0.8 GB, 이전 측정)가 큰 몫일 것이다. 따로 다룬다.
