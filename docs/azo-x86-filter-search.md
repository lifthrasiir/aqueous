# AZO의 x86 필터: CRC만으로 찾기

ALZip의 AZO(EGG 방식 3)는 스트림 플래그의 bit 0이 켜지면 블록마다 x86 필터를 건다. 규격(OctopusET의
EGG 문서, A.12)의 필터도 LZMA SDK의 BCJ도 CRC-32가 맞지 않았다. ALZip을 분해할 수는 없으므로 코퍼스의
CRC-32 일치 여부만으로 변형을 좁혔다.

**결과**: E8/E9, 상위 바이트 00/FF, 기준은 옵코드 위치 `i` 자체, 빼기(부호화 방향), little-endian,
bit 24 확장, **변환 여부와 무관하게 5바이트 건너뜀**, 블록마다 위치 0부터, 0F 8x 없음, 저장 블록에도
필터 적용(필터 뒤에 저장 여부를 정함). 정의는 `codecs/aqr-azo/FORMAT.md` §2.6, 구현은 `codecs/aqr-azo`
(`split`이 필터를 풀어 스트림의 데이터가 파일 그대로가 된다: 모듈 반영 끝).

## 자료

x86 플래그가 켜진 AZO 스트림은 코퍼스(`F:\Data\aqr-corpus\egg`)에 4개뿐이다(alzgg의
`*_sys_optimized.egg`): 실제 `.sys` 73560 B와 594264 B(블록 경계), `MZ`+난수 524288 B와 1048576 B(저장
블록이라 필터 출력이 그대로 보인다). 원본은 없어서 판정은 전체 파일의 CRC-32뿐이다.

## 탐색의 요약

도구: `codecs/aqr-azo/examples/x86_search.rs`(변형 전수 탐색), `x86_dump.rs`(필터 출력 덤프).

1. 규격 필터(`i += 5`는 변환했을 때만) 주변의 변형 23040개(옵코드 집합, 상위 바이트 조건, 기준 위치,
   더하기/빼기, 엔디언, 상위 바이트 처리, 건너뛰기, 블록 간 위치 이음, LZX식 E8)를 전수 시험: 전부 불일치.
2. 실제 코드의 구조 분석: 같은 호출 대상이 같은 값으로 반복되고, 그 값이 가리키는 곳이 함수 시작이므로
   출력은 절대 주소이고 기준은 `i`(off 0). 옵코드가 아닌 즉치값의 E8도 (의미를 안 보고) 변환된다.
3. CRC의 아핀성으로 지점별 판정(난수 파일, 후보 36개): 어느 부분집합을 변환해야 목표 CRC가 나오는지
   풀어 보니 `빼기, off 0`에서만 해가 있고, 36개 중 앞 3–4바이트 안에 다른 E8/E9가 있는 두 지점만
   변환되지 않았다 → 변환하지 않을 때도 5바이트를 건너뛴다 (LZX/CAB의 E8과 같은 습관).
4. 건너뜀을 일반 경로에 넣어 다시 돌리니 네 파일 모두 일치.

남은 변형을 가른 증거: 0F 8x 없음(실제 코드 두 개가 `ops=2`를 배제), bit 24 확장(블록 2개짜리 실제
코드가 32비트 그대로/24비트만을 배제), 블록마다 위치 0부터(블록 2개짜리 둘이 이어짐을 배제), 변환 시
5바이트 건너뜀(실제 코드가 1을 배제).

## 확인되지 않은 것

- 블록 끝: `N < 5`이면 아무것도 안 하고 `i < N − 4`로 마지막 4바이트의 창을 안 보는 것은 규격 A.12를
  따른 경계일 뿐이다. 네 스트림에는 `N < 5`인 블록도, 마지막 4바이트 안의 후보도 없었다.
- 부호화기 방향 `filter`는 ALZip의 출력과 비교한 적이 없다 (코퍼스는 복호 방향만 시험). 복호기가
  `D[i+4]`의 00/FF를 필터된 주소에서 판정해도 되는 것은 bit 24 확장이 그 값을 지키기 때문이라는 추론이다.
- `.com` 파일(AZO를 고르는 다른 형식)과 16비트 코드는 코퍼스가 없다.
